# Plan: desktop keys screen (#145)

## Objective

`RemoteKeyClient` speaks every `remote.*` key method to the paired desktop,
but no screen calls it. Add a Desktop keys screen, reached from the device
detail screen while a desktop session is up: the desktop's backends, then the
keys of a backend, then a key detail with its info, its public key, a
sign-then-verify test on a fixed message, and `remote.attestKey`.

## Slices, in order

1. **Plan** (this file).
2. **Controller** — `ui/DesktopKeysController.kt`, view-free:
   - `DesktopKeysSource`, the calls the screen makes, with an adapter over
     `RemoteKeyClient` (the client is final, so tests fake the interface);
   - `DesktopKeysState` (no session, loading, backends, keys, detail,
     failed) and `DesktopKeyError`, a typed error mapped from
     `ProtocolException` codes and transport failures;
   - `open`, `chooseBackend`, `chooseKey`, `signTest`, `attest`, `back`.
   Tests (`DesktopKeysControllerTest`): no session, loading, backend list,
   key list, key detail, sign-then-verify (valid and invalid), attestKey
   result fields, typed desktop error, cancellation rethrown; and over a real
   `RemoteKeyClient` with the scripted sender, opening sends
   `remote.listBackends` and choosing a backend sends `remote.listKeys`.
3. **Screen** — `ui/DesktopKeysActivity.kt`, `activity_desktop_keys.xml`,
   `item_desktop_key.xml`, `layout_desktop_key_detail.xml`,
   `strings_desktop_keys.xml`, the manifest entry; the accessor
   `XKeyGattService.remoteKeyClient()` (null without a desktop session, one
   cached client per active router); an entry button on
   `DeviceDetailActivity` shown only while that device's desktop session is
   up.
4. **Docs** — `docs/remote-key-access/architecture.md` names the screen and
   the methods it sends.

## Review fixes

Each lands as a failing test, then the fix.

1. **One desktop per screen.** Device detail passes the device's peer public
   key. The controller captures the session's client on the first step and,
   before every request, refuses and clears its state when the service's
   confirmed peer or client differs, so no request reaches another desktop.
2. **One client per router.** `requestDeviceAttestation` goes through the
   same cached client as the screen, so overlapping
   attestation and key calls never share a request id.
3. **The entry follows the session.** Device detail watches
   `desktopSessionUp` while started and shows the button only while this
   device's session is connected and confirmed.

## Second review fixes

Each lands as a failing test, then the fix.

1. **Identity and client from one snapshot.** `DesktopSessions.session()`
   returns the confirmed peer and the client of its own transport together.
   The confirmed peer is one field shared by BLE, TCP and USB, so it answers
   only while exactly one transport has a connection (established or still
   handshaking) and that one is established; otherwise null. A per-transport
   peer would need GattServer, StreamPairingSession and the handler, which
   this row does not edit; with two desktops connected at once the screen
   shows no session until one goes away.
2. **One client per live router.** `DesktopSessions` keeps a client per
   router (weakly held), so A, then B, then A reuses A's client and its
   request ids; an outstanding A request keeps its reply.
3. **Keys with no public half.** `chooseKey` keeps the key info when the
   desktop refuses public export (unsupported format, export failed,
   invalid algorithm, operation denied); the detail opens with no public
   key and shows why. Link failures still fail the step.

## Third review fixes

Each lands as a failing test, then the fix.

1. **Identity bound to its transport.** GattServer and StreamPairingSession
   (through TcpHsmServer and UsbAccessoryServer) each report the peer their
   own session confirmed; `DesktopSessions.session()` pairs the first
   established transport's client with that transport's own peer, never the
   request handler's shared field. A BLE `stop()` clears its peer, so A on
   TCP after B's BLE stops names A, not B. This replaces the earlier
   one-connection-only rule.
2. **Request ids live on the router.** `BidirectionalMessageRouter` holds the
   id counter and `RemoteKeyClient` takes it from there, so a client rebuilt
   on the same router after a collection never reuses a cancelled request's
   id and never takes its late reply.

## Known gaps

Both gaps below were closed by binding each session's client to its
connection (the fix after the merge of row/144-remote-share, 3a97fb7).

- **Same desktop reconnecting: closed.** `session()` captures the
  transport's `ConfirmedConnection` at the peer check, and connections compare
  by identity. A request checked on A's old connection is refused on A's next
  one, and a fresh `session()` binds a new client to the new connection.
- **Last-moment swap: closed.** The transport senders used to pick their
  connection again at send time: `GattServer` read `noiseSession` and
  `StreamPairingSession` (behind TcpHsmServer and UsbAccessoryServer) read
  `activeConnection`. So if desktop A disconnected and paired desktop B
  reconnected between the check and the write, A's request (for example
  `remote.sign` with A's backend and key ID) was encrypted to B. The session
  client now sends only through `MessageSender.sendEncryptedMessageOn(captured,
  data)`. The transport checks that the captured connection is still current
  and confirmed for the same peer, at the admission that consumes the nonce,
  and otherwise writes nothing and throws `ConnectionChangedException`.
  Regression tests: "A disconnecting and B reconnecting between the check and
  the send never reaches B", and "a request checked on A's connection never
  goes out on A's next connection" in `DesktopSessionsTest`.

## Connection binding audit

Every path in this row that sends a `remote.*` request to a desktop.

| Path | Sends through | Verdict |
|---|---|---|
| `DesktopSessions.session().client` (desktop keys screen) | `ConnectionBoundSender`: `sendEncryptedMessageOn` with the connection captured at the peer check | Bound. A swapped or ended connection refuses the send. |
| `DesktopSessions.attestDevice` | `session()` peer check, then that session's bound client | Bound, as above. |
| `DesktopSessions.client()` with a confirmed peer | The same bound client, captured from the live connection; null when the live connection does not confirm the transport's peer | Bound. |
| `DesktopSessions.client()` before a peer is confirmed | The transport sender unbound | Open by design: no peer has been checked, so there is no connection to bind to. Callers that need a specific desktop must use `session()`. |
| `DesktopKeysController` `checked` source (listBackends, listKeys, getKeyInfo, getPublicKey, sign, verify, attestKey) | `ownSource()` before each request: the session must still be this screen's peer with the same client, then that client's `ConnectionBoundSender` | Bound. After a reconnect `session()` returns a new client, so `ownSource()` sees a different source and the step stops with the session-changed state instead of sending. |
| `DesktopKeysActivity.currentSession` | Adapts `desktopSession()`'s client; sends nothing itself | No send of its own. |
