# Plan: SPEC row media-signing (#258)

## Objective

Ship SPEC row `media-signing`: a foreground service watches MediaStore,
hashes new photos and videos, signs them and embeds the signature in EXIF
or XMP, with an auto-sign toggle and key choice. Videos and PNG/WebP photos
embed the signature in XMP, not in a sidecar file (#200).

## Step 31: camera captures are written through a granted write request

- A capture another app owns (the camera's) is not xKey's to rename over: READ_MEDIA_* gives no write. `MediaPublisher.writeAccess` reads its owner; media xKey owns (or any media before Android 11) keeps the path write. Other media is written only through `MediaPublisher.writeGranted`, the one choke point: it refuses without the user's grant and writes the signed bytes through the content URI.
- The auto-signer signs through `XmpMetadataHelper.signMedia`. Without a grant it writes nothing and queues the capture (`MediaWriteAuthorizations`, kept under the app's files); a notification opens `MediaWriteRequestActivity`, which asks for every queued capture in one `MediaStore.createWriteRequest` and then signs the granted ones (content hash rechecked first) or drops them on a refusal.
- Sweep: co-sign and Share-sheet saves replace only `file:` URIs by path and copy everything else to a document the user creates, so they need no grant.
- Tests: CameraMediaWriteAuthorizationTest (request, grant, embed; refusal; changed media; owned media keeps its path; the service signs only through `signMedia`) and the instrumented CameraMediaWriteAuthorizationInstrumentedTest (media the shell created asks for write access).
- Out of this lane: the review's key-namespace migration scope finding waits for a decision.

## Step 32: code review round 3 fixes

- Scope: the key-namespace migration (schema 14, `KeyEntity.materialNamespace`) and the key, credential, key-use audit and trust-store deletion changes leave this row. Their files are back to main's behaviour, and their tests with them. Media signing uses none of them: the app and both test sets compile without them. The key-deletion notes in earlier steps describe work that now belongs to its own rows.
- A granted write keeps a durable record. The capture's current bytes are copied and synced to `media-recovery/granted-<sha256 of URI>.bak`. A synced `.uri` record naming the capture follows, and only then is the capture overwritten. Success or a verified restore deletes the record, then the backup. A record left by a process that died, or by a restore that failed, is put back at the next start (`MediaSigningService.onCreate`), before every retry (`publishGranted`), and before the capture is staged again (`MediaPublisher.grantedSection` in `signMedia`). Recovery and granted writes share one lock.
- The destructive write checks the capture it is about to overwrite. `writeGranted` takes the signed source's canonical hash and refuses with `SourceChangedException` when the backed-up current capture differs, so an edit saved after staging is kept. `signMedia` is the only caller (a source scan checks this), and a direct call is refused the same way.
- Tests (CameraMediaWriteAuthorizationTest): a kill mid-overwrite is recovered at the next start and before the retry, a capture edited after staging is refused and keeps the edit, and a direct `writeGranted` call refuses an edited capture.
- Limit: Java cannot sync the recovery directory itself, so the record's rename relies on the filesystem keeping renames in order.

## Step 33: code review round 4 fixes

- A capture is rewritten only from its original bytes. Without ACCESS_MEDIA_LOCATION, MediaStore serves a foreign capture with its location left out. `MediaPublisher.openOriginal` is the one read of a capture that is staged, backed up or checked after a restore: it reads `MediaStore.setRequireOriginal(uri)` and throws `OriginalUnavailableException` when the permission is missing. `signMedia` stages through it and `writeGranted` backs up through it, so nothing is written from the redacted view. The manifest declares the permission, the write-request screen asks for it before the write request, and the auto-signer hashes the original wherever it is readable.
- A recovery must succeed before a capture is staged or written. `recoverInterruptedWrite` throws `RecoveryPendingException` when the restore fails or the grant is gone. `publishGranted` then keeps the request queued, and a refused request keeps a capture that is not restored yet, so a later grant can restore it.
- Tests: CameraMediaWriteAuthorizationTest (a foreign geotagged JPEG keeps its location when signed and when an interrupted write is put back; without location access nothing is written; a failed recovery keeps the request and a later one restores and signs; direct calls refuse; a source scan for the read choke point) and MediaWriteRequestActivityTest (location access is asked first).
- Limit: the auto-signer cannot ask for a permission. Without location access, a foreign capture is refused when the write is attempted, not when it is signed.

## Step 34: code review round 5 fixes

- An edit of a capture's metadata alone is refused. The canonical hash leaves out a JPEG's APP and COM segments, so it cannot show a location or orientation edited after staging. `MediaPublisher.StagedSource` is the one "changed since staging" check: `StagedSource.of` checks the staged snapshot against the signed hash and takes a SHA-256 of the whole file before anything is embedded; `writeGranted` takes it and refuses the backed-up current capture unless both still match (`requireUnchanged`).
- A recovery record that cannot be read leaves the recovery pending. Every record read goes through `GrantedWriteJournal.readRecord`; `target()` throws instead of returning null, so `recover` keeps the record and the backup and `recoverInterruptedWrite` throws `RecoveryPendingException`. Only a restore that succeeded clears them. `recoverInterruptedWrites` skips an unreadable record for a later pass.
- Tests (CameraMediaWriteAuthorizationTest): a geotagged JPEG relocated between staging and backup is refused and keeps the edit; a record read that fails leaves the record, the backup and the queued request, and a later recovery puts the capture back.

## Step 35: code review round 6 fixes

- A capture edited after an interrupted write keeps the edit. The journal links the bytes being written (`GrantedWriteJournal.written`) beside the backup, and recovery restores only content an interrupted in-place write can leave: the written bytes up to some point, then the backup's (`interruptedWriteExplains`). Anything else was saved since: the backup is set aside as `kept-*.bak`, the record is cleared, and signing meets the changed-source check and is refused.
- A write-request queue that cannot be read or parsed is never taken as empty. `read` returns empty only when there is no store; otherwise it throws `IOException`, so `add` and `remove` change nothing and fail, and the caller logs the capture as not queued.
- Tests (CameraMediaWriteAuthorizationTest): a crash, then a gallery edit, then recovery keeps the edit and the backup and signs nothing; a queue read or parse failure during `add` and during `remove` leaves the store untouched.
- Limit: the set-aside backup is not yet shown to the user.

## Step 36: code review round 7 fixes

- An interrupted restore is a rollback state, not a gallery edit. A granted write that fails, then a restore the process dies in, leaves the backup's bytes up to where the restore stopped, then what the write left. The journal records the restore phase (`GrantedWriteJournal.restoring`, synced before the restore writes a byte), and one check (`GrantedWriteJournal.explains`) accepts every layout the write and the restore can leave: in the write phase, the written bytes then the backup's; once the restore has begun, the backup's bytes first. Every restore goes through `restore`, which marks the phase first; recovery then finishes the restore, keeps the record until it is verified, and the queued request stays.
- Tests (CameraMediaWriteAuthorizationTest): a restore killed after part of the backup is back is finished by the next recovery and the request stays queued; a retry finishes it and signs; a gallery edit after an interrupted restore keeps the edit and the backup. MediaPublisherTest: the layouts of each phase are accepted and an edit is refused.

## Step 37: code review round 8 fixes

- A queued capture leaves the queue only once it is published or permanently refused. `publishGranted` keeps the request on any read, staging or embedding failure (a full disk is an `IOException` before `writeGranted`); only a capture that changed since it was signed (`SourceChangedException`), is gone (`FileNotFoundException`) or cannot be hashed (`MediaTooFragmentedException`) is dropped. The auto-signer has already marked the capture processed, so the queue is its only retry.
- Captures waiting for write access are reachable without the notification. `MediaWriteAuthorizations.settingsEntry` is the one intent to `MediaWriteRequestActivity`, used by the notification and by a "pending captures" button in the media-signing settings. Turning auto-signing on asks for POST_NOTIFICATIONS on Android 13+ (`notificationPermissionToRequest`); a refusal changes nothing else, and settings still opens the request.
- Tests: CameraMediaWriteAuthorizationTest (one test: a staging failure keeps the request and a retry signs, while a gone capture leaves the queue) and MediaWriteEntryPointTest (settings entry with notifications off and permission denied; the permission is asked for on Android 13+ until it is granted, and never before Android 13, sdk 32).
- Limit: a `FileNotFoundException` while staging is taken as the capture being gone.

## Step 38: code review round 9 fix

## Step 46: code review round 17 fixes (process death, as a class)

- (a) State a screen needs after a restore is never process-local. ## Step 47: code review round 18 fixes (resource bounds, as a class)

- Signing memory stays bounded across captures. Every capture is hashed by streaming with constant-size buffers (`MediaHasher.hashStreamed`); nothing below the embed bound is buffered whole, and only a size probe precedes the hash. `MediaJobGate` is the one way a signing job starts: one job per URI in flight, and no more jobs holding memory at once than its bound allows (the signer runs one at a time, as a JPEG embed holds the image in memory).

## Step 49: code review round 20 fix (one read per hash, as a class)

- A hash reads its media once. `MediaHasher.hashStreamed(open, mimeType, workDir)` is the choke point: it reads `open()` one time into a private snapshot under `workDir` (a `MediaSaveRuns.work` file, so a killed run's snapshot is reclaimed by the start sweep), hashing the whole bytes on the same pass, and every canonical pass (the strip plan over `FileByteSource` and the digest over `Pieces.write`) reads that snapshot. The snapshot is deleted when the hash returns or throws. `MediaHasher.withSnapshot` is the shared read; `MediaHasher.hashStreamedFile(file, mimeType)` hashes a file xKey already owns without a second copy.
- A check made before a hash reads the same bytes as the hash. `AutoSignHash.contentHashOf` takes one snapshot and runs the size bound, the carried-signature check and the hash on it (`contentHashOfFile`); media hashed whole is read in one pass. `MediaHasher.checkInBandUri` reads the embedded signature (`XmpMetadataHelper.readSignatureFromSnapshot`) and checks its hash from one snapshot of the original; a type that carries no in-band signature reads as unsigned before any read, so its verify still goes to the sidecar picker without location access.
- Sweep of paths that read a mutable source more than once for one decision: `MediaHasher.hashStreamedUri` and `AutoSignHash.contentHashUri`/`contentHashOriginal` (fixed; snapshot in the recovery directory); `AutoSignHash.contentHashFile` (file overload); the co-sign copy check in `CoSignActivity.copyInPlace` (carried signature and hash from one snapshot of the target) and its append (`hashStreamedFile` on the staged copy); `XmpMetadataHelper.writeSignedCopy` (`hashStreamedFile`); `VerifiedMediaViewerActivity.verifyMedia` and `FileOperationActivity.performVerify` (signature and hash were two reads; now `checkInBandUri`, the sidecar path reads the media once and the sidecar is its own file); `MediaWriteAuthorizations` (passes the recovery directory). Left as is: `XmpMetadataHelper`'s strip plan and piece write over the same file run on files xKey owns or works on under the path lock, with no other writer; the signing-mode probe in `FileOperationActivity` is one read and decides no verification.
- Tests: MediaHasherSnapshotTest (a JPEG that gains trailing bytes or a changed scan byte after the first read is hashed from the one read, and a hash stored for it does not match the changed bytes; the signer's size check and hash, and its carried-signature check and hash, read the same bytes, each with one open). Failing on the test commit, passing with the fix; the full unit suite passes.
