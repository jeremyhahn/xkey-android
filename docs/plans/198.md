# #198: report the generated key's own security level

## Objective

`generateKey` and `local.generateKey` report `securityLevel` (`software`,
`tee`, `strongbox`) from the generated key's `KeyInfo`, not from whether the
device has StrongBox. Today `preferStrongBox=false`, a StrongBox refusal that
falls back to the TEE (P-384/P-521, RSA-4096) and every AES/HMAC key report
`strongbox` on a StrongBox device, and HMAC-SHA512 reports 256 bits.

## KeyInfo mapping

`KeystoreManager.keySecurityLevel(keyId)` resolves the alias, reads the
key's `KeyInfo` (`KeyFactory` for private keys, `SecretKeyFactory` for AES
and HMAC keys) and maps it with `KeystoreManager.securityLevelOf`:

| API   | KeyInfo                                   | level       |
|-------|-------------------------------------------|-------------|
| 31+   | `securityLevel == SECURITY_LEVEL_STRONGBOX` | `strongbox` |
| 31+   | `TRUSTED_ENVIRONMENT` or `UNKNOWN_SECURE` | `tee`       |
| 31+   | `SOFTWARE`                                | `software`  |
| 31+   | `UNKNOWN`                                 | as API 28-30 |
| 28-30 | `isInsideSecureHardware` and the StrongBox spec succeeded | `strongbox` |
| 28-30 | `isInsideSecureHardware` only             | `tee`       |
| 28-30 | not inside secure hardware                | `software`  |

API 28-30 cannot tell StrongBox from the TEE in `KeyInfo`, so the generators
record (in memory) each alias whose StrongBox spec succeeded; after a process
restart such a key reads `tee`, an under-claim, never an over-claim. A key with
no Keystore entry (Ed25519 lives in EncryptedSharedPreferences) is `software`.

## Call sites changed

- `KeystoreManager.isKeyStrongBoxBacked`: the per-key level, not the device.
- `KeystoreManager.generateKeyForAlgorithm`: the audit line's `strongBox`.
- `KeystoreManager.generateKeyWithAuthDuration`, `generateECKeyPair`,
  `generateRSAKeyPair`: record which spec succeeded.
- `Handler.handleGenerateKey`: the credential's own level (r2).
- `Handler.handleLocalGenerateKey`: asymmetric and symmetric paths store the
  per-key value in `KeyEntity.strongBoxBacked` and the result; HMAC-SHA512
  reports 512 bits. Exportable keys stay `software` (generateSoftwareKey).
- `LocalGenerateKeyResult.withLevel` builds the result from a
  `KeySecurityLevel`; the wire values are unchanged.

## r2: exact alias, three-way level in generateKey, KeyInfo failures propagated

- `KeystoreManager.credentialSecurityLevel` / `generalKeySecurityLevel` read
  one exact alias (`xkey_credential_<id>`, `xkey_key_<id>` or its Ed25519
  entry); `local.generateKey` uses the general one, so a StrongBox credential
  `k` never lends its level to a general key `k`.
- `GenerateKeyResult.withLevel` serializes `securityLevel` and keeps
  `strongBoxBacked`; `handleGenerateKey` passes the credential's level.
- `aliasSecurityLevel` throws `KeyInfoUnavailableException` when an existing
  entry's KeyInfo cannot be read; `software` only for an Ed25519 entry or a
  software KeyInfo. The handlers discard the key and return an error.
- Tests: `LocalMessagesTest` (base result per level),
  `KeystoreManagerGeneralKeysTest` and `RequestHandlerLocalKeyFamilyTest`
  (namespace collision; failing KeyInfo read via `keyInfoReader`).

## Out of scope

Attestation-certificate parsing (`parseAttestationSecurityLevel`), the SPEC
row (stays shipped, unchanged), PIV, key sharing, biometric and PIN code.
