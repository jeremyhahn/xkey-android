# #298: deterministic USB slot reattach tests (usb-transport)

## Objective

Make `a slow teardown of the detached session keeps the new peer identity`
in `UsbAccessoryServerSlotTest` deterministic. It failed once in a full
unit-test run on a loaded machine with `the reattach was ignored`.

## Slices

1. Test first: the reattach case drives the slot's teardown wait itself.
   It learns through a signal (not a sleep) that the reattach waits on the
   old session's teardown, releases the teardown, and joins the reattach
   with no bound, so no wall clock decides the outcome.
2. Fix at one choke point: `UsbAccessoryServerSlot.open`'s wait for the
   retiring session becomes an injectable `awaitTeardown`; production keeps
   the bounded join with the same timeout. Both reattach cases use it.

## Cause

- Test side (`UsbAccessoryServerSlotTest.kt`, the reattach case as on
  main): the reattach ran on a thread joined with `reattach.join(5_000)`,
  which returns after 5 s whether or not the attach finished, and its
  result came back through a plain captured var. On a loaded machine the
  attach (session launch, mocked `NoiseSession`, temp file) was still
  running, so `assertNotNull("the reattach was ignored", second)` saw null.
  Reproduced by delaying the reattach thread 6 s: the case fails at that
  assertion. The clear-while-waiting case had the same shape
  (`reattach.join(10_000)`, thread-state polling).
- Production side (`UsbAccessoryServerSlot.open`): the wait for the
  retiring session was `withTimeoutOrNull(TEARDOWN_WAIT_MS) { join() }`, a
  real-time bound a test could not drive.
- Ruled out: open() returning null because the new server left the slot
  before connect() returned. The second session waits in its key load until
  cancelled, so nothing closes it during the case.

## Fix

- `UsbAccessoryServerSlot` takes `awaitTeardown: suspend (Job) -> Unit`.
  The default (`awaitTeardownWithin`) is the old bounded join with the same
  timeout and warning.
- Both reattach cases build the slot with a wait that signals the retiring
  job through a `CompletableDeferred` and joins it with no bound. The test
  releases the old teardown only after that signal, joins the reattach
  thread with no bound, and reads its result from an `AtomicReference`.
  Session starts and the new peer identity are signalled, not polled.
- Checked: the rewritten case passes with the reattach delayed 6 s and the
  old teardown held 6 s, past the production bound.

## Out of scope

Other USB behaviour, other flaky tests, the teardown timeout's value.
