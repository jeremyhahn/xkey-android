# 199: advertise ECDH only where the Keystore can do it

## Objective

minSdk is 28, but Android Keystore supports key agreement
(`KeyProperties.PURPOSE_AGREE_KEY`, `KeyAgreement` on a Keystore key) only
from API 31. `local.getCapabilities` answers `supportsECDH = true` on every
device, so a caller on API 28-30 that trusts it gets an opaque
`ECDH_FAILED` from `local.ecdh`. This row makes the capability true only where
ECDH works and makes `local.ecdh` refuse plainly elsewhere.

## API table

| Capability | API floor | Why |
|------------|-----------|-----|
| ECDH (`supportsECDH`, `local.ecdh`) | 31 | `PURPOSE_AGREE_KEY` is API 31 |
| ES256/384/512, RS256/384/512, AES128/256, HMAC-SHA256/512 | 28 (minSdk) | Keystore since API 23 |
| Ed25519 | not advertised | `local.generateKey` cannot parse it (round 2) |

## Refusal

Below API 31, `local.ecdh` answers `ECDH_FAILED` before touching the
Keystore, with the message
`ECDH key agreement failed: local.ecdh requires Android 12 (API 31); this device runs API <n>`.

An EC key generated before an OS upgrade to 31 has no agree purpose; Keystore
throws `InvalidKeyException` from `KeyAgreement.init`. `performECDH` maps that
to an `ECDHException` saying the key was not generated with
`PURPOSE_AGREE_KEY`.

## Slices

1. This plan.
2. Failing tests: `KeystoreCapabilitiesTest` (JVM) — `supportsEcdh` false
   for 28, 29, 30, true for 31+; `supportedAlgorithms` leaves out Ed25519
   below 33 and lists it from 33; `ecdhUnsupportedReason` names API 31.
   `RequestHandlerLocalKeyFamilyTest.getCapabilitiesAdvertisesEcdhOnlyFromApi31`
   (device) — `supportsECDH == SDK_INT >= 31`, and below 31 `local.ecdh`
   answers `ECDH_FAILED` naming API 31.
3. Fix: `crypto/KeystoreCapabilities` (SDK level injectable), Handler reads
   it for the capability, the algorithm list and the early refusal;
   `performECDH` names the missing agree purpose. Docs: architecture.md
   states the ECDH API floor.

## Out of scope

- Wire keys of `LocalGetCapabilitiesResult` stay as they are.
- The SPEC row stays shipped and unchanged.
- Regenerating pre-31 EC keys with the agree purpose after an OS upgrade.

## Round 2: review findings

1. Ed25519 is not advertised on any release: `local.generateKey` parses
   names through `CoseAlgorithms.fromName`, which has no Ed25519, so a
   client that picked it could not create a key. It returns when parsing,
   generation and signing agree (a later row).
   Tests: `KeystoreCapabilitiesTest` "Ed25519 is never advertised";
   `RequestHandlerLocalKeyFamilyTest.everyAdvertisedAlgorithmCanBeGeneratedAndUsed`
   (device) generates every advertised algorithm through the handler and
   signs with each asymmetric one.
2. `RequestHandlerErrorPathTest` expects `ECDH_FAILED` for `local.ecdh`
   below API 31 (`expectedCode`) in the missing-params, missing-field,
   unknown-key and attestation-gate tests, and the old codes from API 31.
3. `KeystoreManagerGeneralKeysTest.ecdhWithALegacyKeyWithoutTheAgreePurposeNamesThePurpose`
   (device, API 31+) makes an EC key with only `PURPOSE_SIGN` under the
   general alias and asserts the `PURPOSE_AGREE_KEY` message.
