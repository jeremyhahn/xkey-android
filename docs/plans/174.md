# #174: unpairing a desktop drops its per-key sharing grants

## Objective

`PairedDeviceRepository` tells its removal listeners about every key that
stops being paired (`removeDevice`, the eviction in `addDevice`, `clear()`),
but nothing deletes that peer's `key_sharing_policies` rows:
`KeySharingPolicyDao.clearPoliciesForPeer` has no caller. A desktop that
re-pairs with the same static key gets its old `SELECTED_PEERS` grants back,
because `RequestHandler.canShareKeyWithPeer` reads `isKeySharedWithPeer`.

## Design

A `PairedDeviceGrantCleanup` removal listener, defined next to
`PairedDeviceRemovalListener` in `PairedDeviceRepository.kt` and registered
once in `XKeyApplication.onCreate`. For each removed key it launches
`clearPoliciesForPeer` on an IO coroutine and logs the dropped count through
`AuditLogger.logPeerGrantsDropped`.

Why a listener and not the repository: the repository holds no database
handle. It is built from a `Context` or a `SharedPreferences` in many places
(Activities, services, tests), and its listeners already run outside its lock
and must not block. A listener keeps the repository free of Room, keeps the
`suspend` DAO call off the caller's thread, and covers all three removal paths
through the one `notifyRemoved` funnel. The DAO is resolved lazily on the IO
coroutine, so app start does not open the database.

Only policy rows are deleted. Keys and their `sharing_policy`
(`ALL_PEERS`, `PRIVATE`, `SELECTED_PEERS`) are untouched; other peers' rows
stay.

Audit: a new `AuditLogger.logPeerGrantsDropped(deviceId, droppedGrants)`
event (operation `KEY_SHARING_CHANGED`, details `reason=peer_unpaired`,
`droppedGrants`), logged only when rows were dropped. `logDeviceUnpaired` is
not extended: it fires synchronously inside `removeDevice` before the count
exists, and not at all for evictions or `clear()`.

## Slices

1. This plan.
2. Failing test: `PairedDeviceGrantCleanupTest` grants two keys to peer A and
   one to peer B, removes A, asserts A's rows are gone and B's remain; the
   same for eviction by re-pairing under a new key and for `clear()`; checks
   the audit count.
3. Fix: `PairedDeviceGrantCleanup`, `AuditLogger.logPeerGrantsDropped`,
   registration in `XKeyApplication`.
4. Docs: `docs/key-sharing/architecture.md` states the policy rows' lifetime.

## Deviation from the brief

The unit-test classpath has no Robolectric (`libs.bundles.testing` is json,
junit, mockk, coroutines-test) and adding it is outside this row's files, so
the test backs `KeySharingPolicyDao` with an in-memory table (MockK answers)
instead of an in-memory `XKeyDatabase`. The DELETE query itself is plain
SQL on `peer_public_key_hex`.

## Out of scope

No Room schema change. No change to `RequestHandler` or to the DAO.
