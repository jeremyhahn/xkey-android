# #174: unpairing a desktop drops its per-key sharing grants

## Objective

`PairedDeviceRepository` tells its removal listeners about every key that
stops being paired (`removeDevice`, the eviction in `addDevice`, `clear()`),
but nothing deletes that peer's `key_sharing_policies` rows:
`KeySharingPolicyDao.clearPoliciesForPeer` has no caller. A desktop that
re-pairs with the same static key gets its old `SELECTED_PEERS` grants back,
because `RequestHandler.canShareKeyWithPeer` reads `isKeySharedWithPeer`.

## Design

A `PairedDeviceGrantCleanup` removal listener, defined next to
`PairedDeviceRemovalListener` in `PairedDeviceRepository.kt` and registered
once in `XKeyApplication.onCreate`. For each removed key it launches
`clearPoliciesForPeer` on an IO coroutine and logs the dropped count through
`AuditLogger.logPeerGrantsDropped`.

Why a listener and not the repository: the repository holds no database
handle. It is built from a `Context` or a `SharedPreferences` in many places
(Activities, services, tests), and its listeners already run outside its lock
and must not block. A listener keeps the repository free of Room, keeps the
`suspend` DAO call off the caller's thread, and covers all three removal paths
through the one `notifyRemoved` funnel. The DAO is resolved lazily on the IO
coroutine, so app start does not open the database.

Only policy rows are deleted. Keys and their `sharing_policy`
(`ALL_PEERS`, `PRIVATE`, `SELECTED_PEERS`) are untouched; other peers' rows
stay.

Audit: a new `AuditLogger.logPeerGrantsDropped(deviceId, droppedGrants)`
event (operation `KEY_SHARING_CHANGED`, details `reason=peer_unpaired`,
`droppedGrants`), logged only when rows were dropped. `logDeviceUnpaired` is
not extended: it fires synchronously inside `removeDevice` before the count
exists, and not at all for evictions or `clear()`.

## Durable revocation

Pairings live in `SharedPreferences` and grants in Room, so no one transaction
covers both. A one-shot coroutine could lose the delete (process death, or a
throw) and a same-key re-pairing would then get the old grants back. So:

- Where: `removeDevice`, the eviction in `addDevice` and `clear()` add the
  removed keys to a `pending_grant_revocations` string set in the same prefs
  edit that removes the pairing, so both persist or vanish together.
  `PairedDeviceGrantCleanup` clears a key only after `clearPoliciesForPeer`
  returns; on failure the key stays.
- When it replays: at every app start (`XKeyApplication`, on the IO scope),
  and when `addDevice` re-pairs a key that is still pending.
- Why fail closed: until the delete commits, `canShareKeyWithPeer` refuses
  `SELECTED_PEERS` for a pending key, so surviving rows never authorize a
  re-paired peer, even before the replay finishes. `ALL_PEERS` keys are not
  affected. A grant made to that peer while its revocation is still pending is
  dropped by the retry.

No Room change: a pairing-generation column would need a migration.

## r3: shared lock and cleanup generations

- Shared lock: every read-modify-write of the device list and the pending
  set takes one lock in `PairedDeviceRepository`'s companion. The Activity,
  the services and the cleanup each build their own repository over the same
  prefs, so `@Synchronized` (per instance) let one write back a pending set
  another had changed since its read, losing that peer's entry.
- Generations: a removal records `key@generation` from a counter in the same
  prefs edit. `completeRevocation(key, generation)` clears the entry only
  when that generation is still the pending one.
- Coalesced cleanup: `PairedDeviceGrantCleanup` keeps at most one job per
  peer. The job reads the pending generation, deletes, acknowledges it, and
  reads again until nothing is pending; the final read and the release of the
  job are one step under the job map's lock, so a removal after it starts a
  new job. With nothing pending a job is a no-op, so a duplicate (from
  re-pairing, a replay, or a second removal notice) never deletes grants
  approved after the revocation completed.
- The fail-closed check in `canShareKeyWithPeer` is now covered by a test
  that calls it while the re-paired peer's old rows still exist.

## r4: durable acknowledgment and in-flight retry

- Durable acknowledgment: `completeRevocation` clears the pending entry with
  `commit()`, not `apply()`, while holding the store lock that every reader
  of the pending set takes. No grant writer sees the revocation as done
  before it is on disk, so a crash cannot leave an entry that the next
  start's replay would use to delete a grant approved after completion. A
  write that fails puts the entry back and counts as a failed attempt.
- In-flight retry: a request that arrives while a peer's job runs (a
  re-pairing, a replay) is recorded on that job instead of dropped. A failed
  delete retries after a backoff that doubles from 1 s up to 60 s, or right
  away if such a request arrived. After eight failures in a row the job
  ends and the entry waits for the next start or re-pairing.

## r5: audit count across acknowledgment retries and atomic worker exit

- Audit count: `logPeerGrantsDropped` runs as soon as `clearPoliciesForPeer`
  returns, before the acknowledgment. If the acknowledgment's commit fails,
  the retry deletes nothing, and the event with the real count is already
  recorded, exactly once.
- Atomic exit: each way a worker ends (nothing pending, a failed read, or
  the last failure in a row) decides and removes the worker from the job map
  in one step, under the lock `revoke()` takes. A re-pairing that arrives
  while the worker exits either is seen before the decision, or finds no
  worker and starts a new one.

## r6: no grants while revocation is pending, failure budget reset on wake

- No grants while pending: the key-sharing sheet's peer list now comes from
  `KeySharingPeers`, which follows the key's policy rows through Room and a
  `PairedDeviceRepository.revocationChanges` signal. A peer whose revocation
  is pending is shown unselected and not selectable (checkbox disabled, card
  dimmed), whatever rows it still has, and `setAllowed` refuses a grant for
  it, so the cleanup never erases a grant the user just made. When the
  revocation completes, the list updates on its own and the peer can be
  granted again. The sheet no longer keeps its own copy of the grants, so a
  deletion made elsewhere shows up at once.
- Failure budget reset on wake: the worker resets its failure count when
  any request has arrived since its last attempt, including one that woke
  it from its backoff, before it clears that request. A re-pairing during
  the last backoff therefore gets a full set of retries.

## r7: grants bound to the pairing, peer list observes pairings

- Grants bound to the pairing: each pairing of a key now gets a pairing
  generation, saved in the same prefs edit as the device list. A key paired
  again while still paired keeps its generation, and devices paired before
  this change have 0. A grant goes through
  `PairedDeviceRepository.writeGrant`, which refuses it unless the key is
  paired and not revoking. Before the insert it commits a `key@generation`
  marker, and it clears the marker afterwards. While a marker names a
  pairing that has ended, the key counts as revoking, so a row it left
  authorizes nothing. A write that crossed a pairing change records a fresh
  revocation in the same commit that clears its marker, and the cleanup
  deletes the row. That fresh generation also makes any acknowledgment
  still in flight a no-op. A grant written for an older pairing therefore
  never authorizes a newer one, with no Room schema change and no change to
  the handler's query. At start, `replayPending` first settles markers left
  by an ended process.
- Peer list observes pairings: the signal is now
  `PairedDeviceRepository.storeChanges`, which is bumped by every write of
  the device list as well as by revocations. A device paired while the sheet
  is open appears without any change to policy rows or revocations.
- Sweep of peer-grant writers. In `app/src/main`, the only writer of a
  granting row is `KeySharingPeers.setAllowed(peer, true)`, through
  `writeGrant`. Every other DAO write only removes rows:
  - `removePolicy` (withdrawal)
  - `clearPoliciesForKey` (leaving SELECTED_PEERS)
  - `clearPoliciesForPeer` (the cleanup)

  The handler and `remote/` read the table and never write to it. The
  `setPolicy`/`setPolicies` calls left are all in tests.

## r8: legacy pairing generation and grant-write recovery tests

- Legacy pairing generation: `pendingRevocations` now compares a grant-write
  marker against `currentPairing`, the rule `writeGrant` used when it wrote
  the marker. A key paired before #174 is paired at generation 0. Before,
  the raw `pairing_generations` map gave null for it, so the key counted as
  revoking during its own grant write. An unpaired key is still null and
  never matches a marker.
- Recovery tests: restart cases seed a persisted `grant_writes` marker that
  no write in the new process holds. A marker for an ended pairing makes the
  replay remove the stale grant. A marker for the current pairing leaves its
  grant in place. A marker whose commit failed means no grant is written and
  nothing is left for a restart.

## r9: the grant protocol off the main thread

- `writeGrant` commits its marker, and `finishGrantWrite` commits again,
  both synchronously. The sheet calls `setAllowed` from `lifecycleScope` on
  Main. `KeySharingPeers.setAllowed` now runs the grant under `withContext`
  on an injected dispatcher, `Dispatchers.IO` by default, so neither commit
  blocks the UI. The commits are still durable.
- Test: `aGrantFromTheMainThreadCommitsOnTheIoDispatcher` calls
  `setAllowed` from a single-thread "main" context and checks that both
  commits ran on the injected IO thread. The other tests in the class inject
  `UnconfinedTestDispatcher`, so their pauses stay deterministic.

## r10: grants and withdrawals in user-action order

- Since r9 a grant switches to IO and commits its marker before the
  insert, but a withdrawal called `removePolicy` directly. If the user
  checked and then unchecked a peer, the delete could finish first, and the
  older grant would then insert `allowed=true` and stand.
- `KeySharingPeers` now runs every grant, every withdrawal and the new
  `clearAll` under one `Mutex`, shared by all instances. That Mutex is FIFO
  and is taken before the switch to IO, so the edits land in the order the
  user made them.
- Test: `aWithdrawalAfterAHeldGrantLeavesThePeerWithoutAccess`.
- Not done: `KeySharingBottomSheet` still calls
  `clearPoliciesForKey` directly when the key leaves SELECTED_PEERS. The
  sheet is outside this row's file map, so routing that call through
  `clearAll` is left as a follow-up.

## r11: key-wide clears ordered, generation captured at the user action

- Key-wide clears ordered: `persistSharingPolicy` stored the key's policy
  and then called `clearPoliciesForKey` directly, so a clear on leaving
  SELECTED_PEERS could finish before an earlier, queued grant inserted its
  row. It now calls `KeySharingPeers.setKeyPolicy`, which stores the policy
  and clears the rows under the same FIFO lock as grants and withdrawals.
  The unused `clearAll` is gone.
- Generation at the user action: `setAllowed` reads the pairing generation
  with `PairedDeviceRepository.pairingOf` before it waits on the lock, and
  passes it to `writeGrant(peer, pairing, write)`. That call refuses the
  grant unless the key's current pairing is still that one. A grant queued
  while its peer was unpaired, cleaned up and paired again is therefore
  refused. It never reaches the new pairing. The two-argument `writeGrant`
  reads the generation itself, for a caller whose call is the user action.
- Tests: `aKeyWideClearAfterAHeldGrantLeavesThePeerWithoutAccess` (PRIVATE
  and ALL_PEERS) and `aQueuedGrantForAPeerRePairedMeanwhileIsRefused`.
- Sweep of policy-row writers in `app/src/main`:
  - `setPolicy` (grant): `KeySharingPeers.setAllowed`, under the lock,
    through `writeGrant` with the user-action generation.
  - `removePolicy` (withdrawal): `setAllowed`, under the lock.
  - `clearPoliciesForKey` (leaving SELECTED_PEERS): `setKeyPolicy`, under
    the lock.
  - `clearPoliciesForPeer`: the grant cleanup, keyed to the revocation
    generation. It only removes rows.

  `setPolicies`, `grantPolicy`, `revokePolicy` and the DAO's `deleteAll`
  have no caller in `app/src/main`. The handler's `local.setKeyPolicy`
  writes only the key's policy column, through `keyDao.updateSharingPolicy`.
  It writes no policy rows, and it does not clear them either (follow-up:
  `Handler.kt` is outside this row's file map).

## r14: accepted withdrawals survive sheet dismissal

- Since r10 a withdrawal or a Private policy change waits on the shared
  edits lock, but it waited in the sheet's `lifecycleScope`. Dismissing
  the sheet while another grant held the lock cancelled the waiter, so
  `removePolicy` and the policy write never ran, and the peer kept access.
- `KeySharingPeers` now runs every grant, withdrawal and `setKeyPolicy`
  under the lock in `editScope`: by default one shared
  `SupervisorJob + Dispatchers.IO` scope that lives as long as the
  process; tests pass their own. Each edit starts undispatched, so it
  joins the FIFO lock queue before its call suspends, still in
  user-action order. A cancelled caller only stops waiting for the answer.
- The sheet's launches at ~296 and ~531 are unchanged: they reach the
  queue synchronously (`lifecycleScope` is `Main.immediate`), and the
  sheet's lazy `keyDao` is set before a policy change can run, so the
  queued `persist` never touches the detached fragment's context.
- Tests: `aWithdrawalQueuedBehindAGrantSurvivesTheSheetsDismissal` and
  `aPrivatePolicyQueuedBehindAGrantSurvivesTheSheetsDismissal`.

## r15: failures in a detached withdrawal

(The brief named this "r9"; r9 is taken above, so it is numbered in order.)

- Since r14 a withdrawal or Private policy can run with nobody awaiting
  it. A failed `removePolicy` or policy write was kept only in that
  abandoned Deferred: not reported, not retried, peer still authorized.
- `KeySharingPeers.withdraw` now catches the failure inside the edit:
  it logs it, records a pending withdrawal (key, peer), or (key, any
  peer) for Private, and retries the write under the edits lock with a
  1 s to 60 s backoff until it lands.
- A pending withdrawal denies: `Handler.canShareKeyWithPeer` checks
  `KeySharingPeers.isWithdrawalPending` before the policy (the one line
  outside the File map, needed for the denial to reach requests), and
  the sheet shows the peer unselected.
- A later grant of the peer, or a later policy, settles the pending
  entry, so a retry never undoes the user's later choice.
- The pending set lives in the process, like the retries; after a
  process death the stored rows apply again (out of scope: a durable
  replay would need the policy write outside the sheet's closure).
- Tests: `aDetachedWithdrawalThatFailsDeniesThePeerAndIsRetried`,
  `aDetachedPrivatePolicyThatFailsDeniesEveryPeerAndIsRetried`,
  `aGrantAfterAFailedWithdrawalIsNotUndoneByItsRetry`.

## r16: fail-closed detached policy edits

(The brief named this "r9: fail-closed detached policy edits"; r9 is taken.)

- r15 recorded a failed Private change as a pending (key, any peer)
  withdrawal, and treated every other policy change as safe. Three holes:
  Selected Peers narrows All Peers too but was never recorded; a later
  Selected Peers lifted a failed Private's denial without clearing its old
  grant rows; a grant accepted under a pending Private was then deleted by
  the older retry.
- Intent model: `KeySharingPeers` keeps one pending key-wide intent per
  key: the policy the user chose, its `persist`, whether the key's rows
  still need clearing, and a token. Every `setKeyPolicy` records it under
  the edits lock before writing, replacing any older intent (whose retry
  then stops on the token). It inherits the older intent's outstanding row
  clear when it is Selected Peers (Private and All Peers clear anyway), so
  an obligation is superseded, never dropped. Landing it clears the rows
  first (then settles the key's per-peer withdrawals), then persists; the
  intent is removed only after both. A failure is logged and retried
  (1 s to 60 s) under the lock until it lands or a newer intent replaces it.
- While an intent is pending the handler enforces it instead of the stored
  policy (`KeySharingPeers.enforcedPolicy`): Private, or Selected Peers
  with rows still to clear, denies every peer; Selected Peers with its rows
  cleared checks the rows; All Peers enforces what the intent it replaced
  enforced (nothing if none). Per-peer pending withdrawals still deny.
- Grants: refused (false, peer not selectable) while the key's intent
  enforces Private or still owes a row clear, so no retry can delete an
  accepted grant. Under a pending Selected Peers with rows cleared a grant
  is written and the retry only persists the policy.

- Enforcing Selected Peers, stored or pending, reads the explicit grant row

## #193: user-action order

r7 bound a grant to the pairing read when the write ran, and the sheet wrote
each edit from its own coroutine, so edits could land out of order: a grant
still waiting could land after a later withdrawal, a grant in flight after
the key-wide clear on leaving SELECTED_PEERS, and a grant queued across an
unpair and re-pair attached to the new pairing. The grant ran on the main
thread.

- One writer per key: `KeySharingPeers` runs every edit through a fair
  `Mutex` per key id, shared by all its instances (a recreated sheet keeps
  the order), then on an injected IO dispatcher (`Dispatchers.IO`). A call
  joins the queue before its first suspension, and once queued runs under
  `NonCancellable`: a withdrawal is never dropped behind a grant because the
  sheet closed.
- The sheet starts both edits with `CoroutineStart.UNDISPATCHED` from the
  click listeners, so the queue order is the tap order. The policy radio
  calls `setSharingPolicy(selectedPeers, store)`: the key's policy column
  write and, unless SELECTED_PEERS, `clearPoliciesForKey`, in one queue slot.
- The checkbox listener reads `pairingGeneration(peer)` at the tap and passes
  it to `setAllowed(peer, allowed, pairing)`. `writeGrant(peer,
  expectedPairing, write)` refuses, under the store lock and before the
  marker is committed, when the current pairing is not `expectedPairing`; a
  null capture (not paired at the tap) is refused without a call.
- No DAO change: the clear and the grant are ordered by the queue, so no
  transactional clear is needed.

Writers of `key_sharing_policies` rows in `app/src/main`
(`git grep -n -E 'setPolicy|removePolicy|clearPoliciesFor'`):

| Writer | Call | Ordered by |
|---|---|---|
| `KeySharingPeers.setAllowed` (grant) | `setPolicy` inside `writeGrant` | key queue + pairing check |
| `KeySharingPeers.setAllowed` (withdrawal) | `removePolicy` | key queue |
| `KeySharingPeers.setSharingPolicy` | `clearPoliciesForKey` | key queue |
| `PairedDeviceGrantCleanup.drain` | `clearPoliciesForPeer` | revocation markers (r3-r8), not the queue |

The DAO declarations and the `KeySharingPolicy` KDoc example are not
callers. androidTest fixtures write rows directly; they are test setup only.

Tests: `KeySharingPeersTest.aWithdrawalAfterAGrantStillWaitingEndsWithdrawn`,
`leavingSelectedPeersForPrivateDuringAGrantLeavesNoPeerRow`,
`leavingSelectedPeersForAllPeersDuringAGrantLeavesNoPeerRow`,
`aGrantTappedBeforeAnUnpairAndRepairIsRefused`,
`theGrantWriteDoesNotRunOnTheCallingDispatcher`;
`PairedDeviceGrantCleanupTest.writeGrantRefusesAnotherPairing`.

Combined with r12-r16 (#193 r4): the per-key queue and `NonCancellable`
give way to r14's single edits lock, run in `editScope` (`accepted`), which
orders local.setKeyPolicy too; `setSharingPolicy` is `setKeyPolicy(policy,
persist)` with its pending intent and retry. `setAllowed` keeps the pairing
its caller captured at the tap; the queue rows of the table above read
"edits lock".
