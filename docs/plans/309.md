# 309: FIDO2 phone-backend byte fields as standard base64

## Objective

The desktop decodes `local.listFido2Credentials` and
`local.signFido2Assertion` with plain `encoding/json`, which reads a byte
field only from standard-alphabet, padded base64. The phone sends stored
credential and user ids as they are stored (URL-safe, unpadded), and looks
the request's `credentialId` up as a raw stored string. Every passkey the
phone makes has a URL-safe id, so `xkey fido2 --backend phone` fails to
decode the list and the assertion answers KEY_NOT_FOUND.

## Slices, in order

1. Test first: `Fido2WireEncodingTest` drives both RPCs through
   `RequestHandler` with a passkey whose stored keyId and userId are
   URL-safe unpadded base64. It asserts that listed `credentialId` and
   `userId` decode with the strict standard decoder to the original
   bytes, that a sign with the listed id signs and returns a standard
   `userHandle`, that a non-standard id answers INVALID_PARAMS, an unknown
   one KEY_NOT_FOUND, that a non-base64 stored id round-trips as its
   UTF-8 bytes, and that the raw stored URL-safe id does not sign.
2. One choke point, `protocol/Fido2WireIds`: `encode` (stored id to
   standard padded base64 of the bytes the BLE path uses for the same
   passkey) and `resolve` (strict standard decode, then the single FIDO2
   entity for the rpId with those bytes). Both handlers take every byte
   field through it; the sign handler resolves once and uses the stored
   id for alias, counter, audit and log. Existing tests that send raw ids
   move to the wire form.
3. Docs: the wire encoding of every byte field and the
   `userVerificationRequired` default in
   `docs/fido2-phone-backend/architecture.md`.

## Round 1 review

| Change | Where |
|--------|-------|
| P1: listing assertions compare wire ids through two helpers, `listsCredential(storedId, forRpId)` and `listedEntry(storedId, forRpId)`, which encode the stored id; every listing site moved onto them, so the PRIVATE check can no longer pass vacuously; the `userHandle` expectation comes from the encoder | `RequestHandlerFido2AndCosignTest` |
| Mismatched-rpId and non-FIDO2 refusals expect KEY_NOT_FOUND ("Credential not found") from the rpId-scoped lookup | `RequestHandlerFido2AndCosignTest` |
| Two JVM cases for those refusals, and a source scan that keeps listing reads inside the helpers | `Fido2WireEncodingTest` |
| The errors table row for those refusals says KEY_NOT_FOUND | `architecture.md` |

The review raised no P2 or P3. The device tests were compiled, not run (no
device). The `keyType`/`rpId` guards after `resolve` in `Handler.kt` stay as
defence in depth: this lookup cannot reach them, and removing them is a
production change outside this test-only round.

## Out of scope

The CTAP2 BLE path (unchanged), the database schema, the SPEC row status
(the device check stays open).
