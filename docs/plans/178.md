# #178: local.setKeyPolicy widens sharing only after owner approval

## Objective

`local.setKeyPolicy` with `shareable: true` sets a key's sharing policy to
`ALL_PEERS` with no prompt, no confirmed-peer check and no audit entry, so any
paired peer can open a key to every peer and then pass the sharing check in
`local.shareSymmetric`. Widening must need a confirmed peer and the owner's
approval on the phone; every policy change from the wire is audited.

Rule:

- Widening = `shareable: true` on a key whose policy is not already
  `ALL_PEERS`. It needs a confirmed peer (`OPERATION_DENIED` otherwise) and an
  approved biometric prompt naming the key (label, else id). No launcher, a
  cancel or a failure answers `BIOMETRIC_FAILED`; the stored policy is
  unchanged.
- Narrowing (`shareable: false`), an absent `shareable` and a key already
  `ALL_PEERS` behave as today, with no prompt.
- Every stored policy change calls `AuditLogger.logKeySharingChanged`.
- Wire shape, params and the `updated` result stay the same.

## Slices, in order

1. This plan.
2. Failing tests: `SetKeyPolicyHandlerTest` (JVM unit, through
   `RequestHandler.handleRequest`): widen approved -> `ALL_PEERS` stored and
   audited; widen cancelled and with no launcher -> `BIOMETRIC_FAILED`,
   `updateSharingPolicy` never called; widen with no confirmed peer ->
   `OPERATION_DENIED`; narrow -> `PRIVATE`, no prompt, audited; already
   `ALL_PEERS` -> no prompt; unknown key -> `KEY_NOT_FOUND`.
3. Fix: `handleLocalSetKeyPolicy` in `protocol/Handler.kt` only.
4. Docs: a `local.setKeyPolicy` section at the end of
   `docs/hardware-backed-keys/architecture.md`.

## Consistent write and caller peer (review round 1)

- The policy write is a compare-and-set against the policy the request read
  (`KeyDao.compareAndSetSharingPolicy`, row count). A key already at the
  target is not written. A widening whose starting policy moved during the
  prompt is refused (`OPERATION_DENIED`); a narrowing re-reads and retries
  (3 tries). Only a write that changed a row is audited, with the policy it
  replaced.
- One helper, `currentPeerPublicKeyHex()`, resolves the peer from the
  request's `CallerSession`, falling back to the handler-wide peer only when
  there is none. `requireConfirmedPeer` (setKeyPolicy, sharePublicKey,
  shareSymmetric, importSharedKey), the FIDO2 sharing checks and the
  sign/decrypt/encrypt audit device ids use it.
- Tests: a stateful fake store in `SetKeyPolicyHandlerTest` pins the races
  and the caller-peer cases, no sleeps.

## r3: row-bound write and one approval request

- The compare-and-set also matches the row's immutable id
  (`KeyEntity.id`, AUTOINCREMENT, never reused). A key deleted and
  re-created under the same key id while the prompt is up, or after the
  read, gets no policy change; the request answers `OPERATION_DENIED`.
- Every launcher prompt is one launcher-owned request. `requestAuthentication`
  and `requestCryptoSignature` hand their request id and prompt intent to
  an `onLaunch` hook; the handler's `lockScreenPrompt` shows the lock-screen
  notification for that id and intent, so approving or cancelling there
  completes the waiting request (a cancel answers `BIOMETRIC_FAILED`).
  `PendingAuthentications` issues process-wide ids and answers only an id
  it issued. setKeyPolicy, local sign, FIDO2 assertion, sign and the
  generic user-verification prompt use it.
- Prompts no launcher request waits on (the activity-bound `BiometricHelper`
  fallbacks, verifyUser's user-verification key) keep the old wake-only
  notification.
- `RequestHandlerLocalKeyFamilyTest`: headless widening is refused with the
  key left private; narrowing runs from a key generated shareable.

## r4: policy revision and single launch

- ABA: `keys.policy_revision` (schema 13, `MIGRATION_12_13`, 13.json) moves
  forward on every policy write; an `AFTER UPDATE` trigger bumps it when a
  write would keep or lower it. The setKeyPolicy compare-and-set matches row
  id, revision and policy, so a policy changed away and back is refused.
- Double launch: `CryptoSigningCancellations` gives a request id one owner;
  a later delivery (full-screen intent, tap) finishes unseen, and only the
  owner's release fails or dequeues the request. The prompt intent no longer
  sets `FLAG_ACTIVITY_CLEAR_TOP`.
- Sweep, policy writers: `KeyDao.updateSharingPolicy`
  (`KeySharingBottomSheet.persistSharingPolicy`),
  `KeyDao.compareAndSetSharingPolicy` (`Handler` setKeyPolicy), `KeyDao.update`
  (no callers on main; covered by the trigger), and inserts, which write
  fresh rows at revision 0 (`CreateCredentialHandler`, `Handler` x3,
  `KeyStoreSyncManager` x2, `CertificateManagementActivity`,
  `KeyManagementActivity`).
- Sweep, launcher callers posting a full-screen notification
  (`lockScreenPrompt`): setKeyPolicy, local sign, `signWithBiometric` (crypto
  and generic), the generic user-verification prompt and the FIDO2 assertion.
  Only the crypto path starts `CryptoSigningActivity` (standard launch mode),
  now single-owner; the others start the singleTop
  `TransparentBiometricActivity`, which is on top while it prompts.
  verifyUser and the `BiometricHelper` fallbacks keep the wake-only
  notification.

## r5: serialized approval prompts

- Finding: every generic approval launched at once, and a second one reached
  the singleTop `TransparentBiometricActivity` still showing the first, which
  read its request only in `onCreate`; the second never prompted or settled.
- `PendingAuthentications` launches a request only when the one before it has
  settled, in the process-wide `SigningPromptQueue` the crypto signing
  prompts already use (one screen, one biometric prompt). A request still
  queued after `QUEUE_DEADLINE_MILLIS` (2 min) settles with `ERROR_TIMEOUT`
  unseen, which the handlers answer as BIOMETRIC_FAILED; a caller cancelled
  while queued never prompts; `unregister` cancels queued requests too.
- `TransparentBiometricActivity`: a start reaching the instance on screen is
  ignored when it repeats that request or names an older one (ids grow), and
  a newer launcher id makes it answer cancelled and hand the request to a
  fresh instance. Answered prompts report nothing more, and an activity that
  goes away unanswered answers cancelled, so no request holds the screen
  forever.
- Sweep, callers of the generic prompt path (`requestAuthentication`), all in
  `Handler.kt` and all through the one queue: `handleGenerateKey`,
  `handleLocalGenerateKey`, `signWithBiometric` (generic signing),
  `handleLocalSign`, setKeyPolicy, `requireUserPresenceForAttestation` and
  `handleLocalSignFido2Assertion`. Crypto-bound signing
  (`requestCryptoSignature`) takes turns in the same line. Notification route:
  `lockScreenPrompt` runs in `onLaunch`, so a request's lock-screen
  notification is posted only when its turn comes; the wake-only
  notifications (`sign-…`, `verifyUser-…`, attestation ids) carry
  non-numeric ids that never displace a launcher prompt. Co-sign
  (`handleCosignRequest`) shows no prompt, so it has nothing to serialize.
- Known limit: the handlers' `cancelBiometricNotification()` clears the one
  shared notification, so a queued request that times out also clears the
  notification of the prompt on screen; that prompt itself stays up.

## r6: notification ownership and real-flow tests

- Finding: an approval withdrawn (its connection closed) or timed out while
  it waited for its turn ran the setKeyPolicy `finally` that cleared the one
  app-wide notification 2001, which belonged to the approval on screen; when
  Android blocks the direct start, that notification is the owner's only
  route to the prompt. Second finding: the lock-screen tests mocked the
  launcher, the helper and the prompt intent, so they could not catch a
  broken notification-to-prompt handoff.
- `BiometricNotificationHelper` posts each notification under its request
  id as the tag, keeps a timeout per request, and `cancelNotification(id)`
  takes down only that request's. The no-argument form cancels only what
  that helper posted. setKeyPolicy records the id its `onLaunch` saw and
  cancels by it; a request that never came up cancels nothing.
- Tests: `SetKeyPolicyHandlerTest` covers withdrawing and timing out a queued
  approval with another on screen. `ApprovalPromptFlowTest` (Robolectric,
  new as a test dependency) runs the real `RequestHandler`,
  `BiometricActivityLauncher`, helper and `TransparentBiometricActivity`
  lifecycle on a locked phone:
  - the tap opens the request's own prompt with no `CLEAR_TOP`;
  - a repeat or older delivery is ignored;
  - a newer request is handed to a fresh prompt;
  - a prompt destroyed unanswered fails its request;
  - each result reaches only the request it names.

  Disabling the `onNewIntent` handoff or the helper's use of the prompt
  intent fails a case. The activity exposes its prompt callback
  (`@VisibleForTesting`) so a test can approve.
- Known limit: the other handlers still call the no-argument cancel, which
  clears every notification their helper posted. A queued signing or
  key-generation request on the same connection can still take down the
  notification of the prompt on screen; moving them to cancel by id is a
  follow-up outside this row's file map.

## r7: notification keys across prompt families and the active deadline

- Findings: (1) a launched approval whose start Android blocked, with its
  notification left to expire, never settled, so it held the shared prompt
  queue for as long as its connection stayed open; (2) sign, local.sign,
  FIDO2 assertion, attestation and verifyUser still cleared every
  notification of their helper, including an approval's on the same
  handler; (3) generic approvals and crypto signatures are numbered apart,
  each from 1, so their notification tags collided app-wide, and an
  approval leaving the screen took down the crypto signature's notification
  it had just handed the screen to.
- Keys: `NotificationKeys` gives every notification a key unique across the
  app: `approval-<id>`, `signature-<id>`, or a fresh `wake-<op>-<n>` for a
  wake-only notification. The launcher passes the key to `onLaunch`. The
  helper's no-argument `cancelNotification()` is gone, so no caller can
  clear all notifications.
- Ownership: each handler operation holds an `OwnNotifications` that records
  the keys it posted and cancels exactly those in its `finally`.
- Deadline: when an approval's notification expires and its prompt never
  came up, `BiometricActivityLauncher.expireUnshown` settles it with
  `ERROR_TIMEOUT` (`BIOMETRIC_FAILED` on the wire), and the next request gets
  the screen. A late start of that prompt finishes without prompting.
  `TransparentBiometricActivity` tracks which prompts are up so a prompt the
  owner is answering is never expired.
- Sweep, every `cancelNotification` caller in `Handler.kt` and the auth
  package (6, all through `OwnNotifications.close`, each cancelling only the
  keys its own operation posted):
  - `signWithBiometric`: `approval-<id>` or `signature-<id>`, or its `wake-sign-<n>`;
  - `handleLocalSign`: `approval-<id>`;
  - `local.setKeyPolicy` (share with all peers): `approval-<id>`;
  - `requireUserPresenceForAttestation`: `approval-<id>`, or its `wake-<op>-<n>`;
  - `signVerifyUser`: its `wake-verifyUser-<n>`;
  - `handleLocalSignFido2Assertion`: `approval-<id>`.

  The auth package has no other caller; the helper's own expiry cancels only
  the key it posted.
- Tests (`ApprovalPromptFlowTest`):
  - an approval whose notification expires unanswered fails, and the next
    request gets its prompt;
  - withdrawing a queued `local.sign` leaves the notification of the
    approval on screen;
  - an approval handing the screen to a crypto signature leaves the
    signature's notification up.
- Known limit: a crypto signature whose notification expires unanswered
  still waits on its prompt. Settling it needs to know whether
  `CryptoSigningActivity` is up, which is outside this row's file map.

## r8: an active deadline for every launched request

- Findings: (1) after its turn came, a launched request waited with no
  deadline of its own; it settled early only through its notification's
  expiry. Both key-generation handlers (`handleGenerateKey`,
  `handleLocalGenerateKey`) launched with no `onLaunch`, so when Android
  blocked their start silently there was neither a notification nor an
  expiry, and the request held `SigningPromptQueue.process` across
  connections until its own connection closed. (2) The instrumented
  `aSecondRequestReplacesThePendingTimeout` still expected one request's
  timer to replace another's, which the r7 per-request timers no longer do.
- Deadline: `PendingAuthentications.await` starts a clock with every launch,
  `ACTIVE_DEADLINE_MILLIS` (60 s: past the notification's 30 s, inside the
  2 min queue deadline). If the prompt is still not up when it passes,
  `expireUnshown` settles the request with `ERROR_TIMEOUT`
  (`BIOMETRIC_FAILED` on the wire), and the next request gets the screen.
  It needs no notification or other callback. A prompt the owner is
  answering keeps waiting, since it answers when it goes away. The
  notification expiry stays as the earlier of the two routes.
- Key generation: both handlers post through `OwnNotifications.onLaunch`
  and close it in `finally`, as setKeyPolicy does, so on a locked phone the
  notification opens their own prompt and they take down only their own
  key (`approval-<id>`). This adds two callers to the r7 sweep, for 8.
- Tests:
  - `PendingAuthenticationsTest`: a launched request whose prompt never
    comes up times out and hands the screen on; one whose prompt is up
    keeps waiting; the deadline's bounds.
  - `ApprovalPromptFlowTest`: a key generation whose start is blocked fails
    at its deadline, and a sharing approval then gets its prompt. Only
    coroutine time passes, so no notification timer can settle it. The
    queued-approval timeout case now opens the prompt on screen first.
  - `SetKeyPolicyHandlerTest`: the fake prompts count as up.
  - `BiometricNotificationHelperTest` (instrumented, compiled only):
    different keys expire and cancel independently; reposting a key
    replaces its own timer.
- Known limit, unchanged: crypto signatures (`PendingCryptoSignatures`)
  have no active deadline yet.

## r10: one owner per queue entry

- Finding: nine rounds of point fixes each took or released the one prompt
  queue's turn in a new place, and each opened a path where an approval
  held a turn or leaked one. r9 gave crypto signatures the active deadline.
- `PromptOwnership` is a pure state machine per approval key
  (`approval-<id>` or `signature-<id>`, unique across both families). It
  owns the queue: an approval holds exactly one entry from `enqueue` to
  settle, one approval is ACTIVE at a time whatever its connection, and the
  entry is released exactly once, when it settles, which activates the next.

  | From | Event | To |
  |---|---|---|
  | (none) | `enqueue` | QUEUED, or ACTIVE when nothing is |
  | QUEUED | its turn | ACTIVE (prompt or notification launched) |
  | QUEUED | owner: queue deadline, withdrawal | SETTLED (expired, withdrawn) |
  | ACTIVE | activity result | SETTLED (approved, denied, failed) |
  | ACTIVE | deadline / notification expiry | SETTLED (failed / expired) |
  | ACTIVE | owner: launch failure, withdrawal | SETTLED (failed, withdrawn) |
  | SETTLED or unknown | anything | refused and reported, nothing changes |

  A notification tap, or any other start of the prompt activity, is
  accepted only for the ACTIVE key; r11 has the activity enforce this
  before it prompts or hands on (see below). `end` is the
  owner's own exit: it settles an open approval as withdrawn and is silent
  for one already settled.
- Sweep, every place that took or released a queue turn before, and its
  replacement:
  - `PendingAuthentications.await`: `prompts.join(turn)` becomes `enqueue`;
    the `finally` `prompts.leave(turn)` becomes `end`; the queue deadline
    and a launch failure settle by the owner (expired, failed).
  - `PendingAuthentications.complete`: resumed only; now settles by the
    activity result, refused unless ACTIVE.
  - `PendingAuthentications.expireUnshown`: now settles by its event
    (deadline or notification expiry), refused unless ACTIVE.
  - `PendingCryptoSignatures.await`: `prompts.join(request)` becomes
    `enqueue`; the cancellation's `prompts.leave(request) { cancelPrompt }`
    becomes `end` with the same `beforeNext`.
  - `PendingCryptoSignatures.Request.show`: its two `prompts.leave` (withdrawn
    before its turn, launch failure) go: a withdrawn request is settled and
    never activated, and a launch failure settles by the owner.
  - `PendingCryptoSignatures.complete` and `expireUnshown`: `prompts.leave`
    becomes a settle by the activity result or by the expiry's event.
  - `SigningPromptQueue` is gone; `PromptOwnership.process` is the one queue.
- Tap: a request withdrawn while ACTIVE has its prompt ended unshown in
  `end`'s `beforeNext`, so a late tap on its notification finishes without
  prompting, and its result, if any, is refused.
- Tests (`PromptOwnershipTest`, the machine alone): every kind holds one
  entry while QUEUED or ACTIVE and none after SETTLED; a second settle and a
  late result, tap, expiry and deadline are each refused and change
  nothing; a deadline settles the ACTIVE approval as failed and activates
  the next; two connections are never ACTIVE at once. The r5-r9 tests run
  on the routed launcher unchanged but for the queue they construct.
  `PendingAuthenticationsTest` adds a settled request's late result, expiry
  and deadline, each refused; `ApprovalPromptFlowTest` checks after every
  flow that the process owner holds no entry, and its fresh-process helper
  also forgets the settled keys (`forgetSettled`), since ids start over.

## r11: ownership checked before settle and before display

- Findings: with two launchers on `PromptOwnership.process`, a result that
  reached the launcher that did not issue it settled the owner's ACTIVE
  entry before `pending.remove` found nothing, so the owner's caller never
  resumed. `PendingCryptoSignatures.complete` had the same order. And the
  prompt activity's `claim` checked only its expired set, so a settled
  request's launch or tap intent reaching a fresh activity prompted again.
- Both queues, `complete` and `expireUnshown`: `accept` the key, then find
  the launcher's own pending request, and only then settle or expire the
  entry and remove the request. Another launcher's request is left
  untouched, its prompt included.
- `TransparentBiometricActivity`: `claim` and `onNewIntent` take a numeric
  request id only while `PromptOwnership.process.accept(approval-<id>,
  NOTIFICATION_TAP)` holds; a refused intent finishes the fresh activity
  and leaves a prompt on screen alone. Wake-only ids (`wake-<op>-<n>`)
  are not launcher requests and stay exempt.
- Tests: `PendingAuthenticationsTest`
  `aResultReachingTheLauncherThatDidNotIssueItFirstStillCompletesItsOwnersCaller`
  and `aSignatureReachingTheLauncherThatDidNotIssueItFirstStillCompletesItsOwnersCaller`;
  `ApprovalPromptFlowTest` `a settled approval's launch or tap reaching a
  fresh activity shows no prompt` and `a settled approval's intent arriving
  while another prompts leaves that prompt alone`. The notification-expiry
  flow test no longer advances 90 s, which passed the next request's 60 s
  active deadline; it had passed only on an id an earlier test left on
  screen.
