# #178: local.setKeyPolicy widens sharing only after owner approval

## Objective

`local.setKeyPolicy` with `shareable: true` sets a key's sharing policy to
`ALL_PEERS` with no prompt, no confirmed-peer check and no audit entry, so any
paired peer can open a key to every peer and then pass the sharing check in
`local.shareSymmetric`. Widening must need a confirmed peer and the owner's
approval on the phone; every policy change from the wire is audited.

Rule:

- Widening = `shareable: true` on a key whose policy is not already
  `ALL_PEERS`. It needs a confirmed peer (`OPERATION_DENIED` otherwise) and an
  approved biometric prompt naming the key (label, else id). No launcher, a
  cancel or a failure answers `BIOMETRIC_FAILED`; the stored policy is
  unchanged.
- Narrowing (`shareable: false`), an absent `shareable` and a key already
  `ALL_PEERS` behave as today, with no prompt.
- Every stored policy change calls `AuditLogger.logKeySharingChanged`.
- Wire shape, params and the `updated` result stay the same.

## Slices, in order

1. This plan.
2. Failing tests: `SetKeyPolicyHandlerTest` (JVM unit, through
   `RequestHandler.handleRequest`): widen approved -> `ALL_PEERS` stored and
   audited; widen cancelled and with no launcher -> `BIOMETRIC_FAILED`,
   `updateSharingPolicy` never called; widen with no confirmed peer ->
   `OPERATION_DENIED`; narrow -> `PRIVATE`, no prompt, audited; already
   `ALL_PEERS` -> no prompt; unknown key -> `KEY_NOT_FOUND`.
3. Fix: `handleLocalSetKeyPolicy` in `protocol/Handler.kt` only.
4. Docs: a `local.setKeyPolicy` section at the end of
   `docs/hardware-backed-keys/architecture.md`.

## Consistent write and caller peer (review round 1)

- The policy write is a compare-and-set against the policy the request read
  (`KeyDao.compareAndSetSharingPolicy`, row count). A key already at the
  target is not written. A widening whose starting policy moved during the
  prompt is refused (`OPERATION_DENIED`); a narrowing re-reads and retries
  (3 tries). Only a write that changed a row is audited, with the policy it
  replaced.
- One helper, `currentPeerPublicKeyHex()`, resolves the peer from the
  request's `CallerSession`, falling back to the handler-wide peer only when
  there is none. `requireConfirmedPeer` (setKeyPolicy, sharePublicKey,
  shareSymmetric, importSharedKey), the FIDO2 sharing checks and the
  sign/decrypt/encrypt audit device ids use it.
- Tests: a stateful fake store in `SetKeyPolicyHandlerTest` pins the races
  and the caller-peer cases, no sleeps.

## r3: row-bound write and one approval request

- The compare-and-set also matches the row's immutable id
  (`KeyEntity.id`, AUTOINCREMENT, never reused). A key deleted and
  re-created under the same key id while the prompt is up, or after the
  read, gets no policy change; the request answers `OPERATION_DENIED`.
- Every launcher prompt is one launcher-owned request. `requestAuthentication`
  and `requestCryptoSignature` hand their request id and prompt intent to
  an `onLaunch` hook; the handler's `lockScreenPrompt` shows the lock-screen
  notification for that id and intent, so approving or cancelling there
  completes the waiting request (a cancel answers `BIOMETRIC_FAILED`).
  `PendingAuthentications` issues process-wide ids and answers only an id
  it issued. setKeyPolicy, local sign, FIDO2 assertion, sign and the
  generic user-verification prompt use it.
- Prompts no launcher request waits on (the activity-bound `BiometricHelper`
  fallbacks, verifyUser's user-verification key) keep the old wake-only
  notification.
- `RequestHandlerLocalKeyFamilyTest`: headless widening is refused with the
  key left private; narrowing runs from a key generated shareable.

## r4: policy revision and single launch

- ABA: `keys.policy_revision` (schema 13, `MIGRATION_12_13`, 13.json) moves
  forward on every policy write; an `AFTER UPDATE` trigger bumps it when a
  write would keep or lower it. The setKeyPolicy compare-and-set matches row
  id, revision and policy, so a policy changed away and back is refused.
- Double launch: `CryptoSigningCancellations` gives a request id one owner;
  a later delivery (full-screen intent, tap) finishes unseen, and only the
  owner's release fails or dequeues the request. The prompt intent no longer
  sets `FLAG_ACTIVITY_CLEAR_TOP`.
- Sweep, policy writers: `KeyDao.updateSharingPolicy`
  (`KeySharingBottomSheet.persistSharingPolicy`),
  `KeyDao.compareAndSetSharingPolicy` (`Handler` setKeyPolicy), `KeyDao.update`
  (no callers on main; covered by the trigger), and inserts, which write
  fresh rows at revision 0 (`CreateCredentialHandler`, `Handler` x3,
  `KeyStoreSyncManager` x2, `CertificateManagementActivity`,
  `KeyManagementActivity`).
- Sweep, launcher callers posting a full-screen notification
  (`lockScreenPrompt`): setKeyPolicy, local sign, `signWithBiometric` (crypto
  and generic), the generic user-verification prompt and the FIDO2 assertion.
  Only the crypto path starts `CryptoSigningActivity` (standard launch mode),
  now single-owner; the others start the singleTop
  `TransparentBiometricActivity`, which is on top while it prompts.
  verifyUser and the `BiometricHelper` fallbacks keep the wake-only
  notification.

## Out of scope

- `AuditLogger` and the wire types (unchanged); `KeyDao` gains only the
  compare-and-set and the policy revision.
- verifyUser's prompt, which is not a launcher request.
- Per-peer (`SPECIFIC_PEERS`) policies from the wire.
- Other handlers in `Handler.kt` beyond the peer reads listed above.
