# #173: local.pivImportCert refuses a certificate for another key

## Objective

`PivKeyManager.importCertificate` stored `certificate_der` unparsed once the
slot row existed. It now parses the bytes as one X.509 DER certificate and
stores it only when the certificate's SubjectPublicKeyInfo equals the slot
key's public key. `local.pivImportCert` maps the refusals onto existing
codes; the success result is unchanged.

| Request | Result |
|---------|--------|
| Certificate for the slot's key | stored, `success: true` |
| Certificate for another key | `INVALID_PARAMS`, earlier certificate kept |
| Bytes that are not one DER certificate | `INVALID_PARAMS`, nothing stored |
| `certificate_der` not base64 | `INVALID_PARAMS`, nothing stored |
| Slot with no key | `PIV_SLOT_NOT_FOUND` (-32026) |

## Slot lock

An import checks the certificate against the key it read from the slot
row, then writes the row. If `generateKey` or `deleteKey` ran in between,
the upsert would bring back the old key's row with the certificate. The
GATT service and each PIV screen build their own `PivKeyManager`, and GATT
requests run concurrently, so the lock is process-wide: `PivSlotLocks`
holds one `Mutex` per slot. `generateKey`, `deleteKey` and
`importCertificate` hold their slot's lock from the first read to the last
write; `listSlots` reads each slot under its lock (r6); other slots, `sign`
and the getters take no lock.
`PivKeyManagerTest` holds an import mid-way and checks that a delete on a
second manager waits for it.

## Live key check

The Android Keystore entry `xkey_piv_<slot>` is the proof that a slot
holds a key and which key it is; the `piv_slots` row is a cache. The row
can disagree with the Keystore: a key deleted outside `PivKeyManager`
leaves `hasKey` and the old public key behind, and a `generateKey` that
fails or is cancelled after replacing the Keystore key leaves the
replaced key's public key in the row. So:

- `importCertificate` compares the certificate with the public key the
  Keystore holds, read under the slot lock. A missing alias is
  `PivSlotEmptyException` (`PIV_SLOT_NOT_FOUND`); on success the row's
  public key is refreshed from the Keystore. `getPublicKey` and
  `listSlots` (`hasKey`, `publicKeyDer`) read the Keystore too.
- `generateKey` writes its row under `NonCancellable`. If the write
  fails, it deletes the new Keystore key and the row, then rethrows, so
  the slot is empty rather than holding a key its row does not describe.
- PIV slot aliases are not general keys. `KeyStoreSyncManager` does not
  list them in the `keys` table and removes any an earlier sync listed,
  and `KeystoreManager` does not resolve or delete them by raw alias.
  Otherwise the key management screen or `local.deleteKey` could delete
  a slot key behind `piv_slots`, outside the slot lock.

The PIV screens still read `piv_slots` directly for display; they decide
nothing on it.

## r4: classify by alias

The sync no longer treats a logical key id starting with `xkey_piv_` as a PIV
slot: a general key `xkey_piv_example` lives at `xkey_key_xkey_piv_example` and
keeps its row. Sweep result: sync discovery tests the raw Keystore alias,
stale-row removal now relies on `resolveKeystoreAlias` (which tries the general
alias first and refuses only a raw PIV alias), `deleteByAlias` receives real
aliases from every caller, and import and key-list paths go through
`PivSlot.keystoreAlias`; no other logical-id prefix check remains.

## r5: guard coverage

`KeystoreManagerPivAliasTest` drives a real `KeystoreManager` over the
`FakePivKeystore` double: a raw PIV slot alias is not resolved, found or
deleted by `resolveKeystoreAlias`, `keyExists`, `deleteKey` or `deleteByAlias`,
and a general key `xkey_piv_example` still resolves and deletes. With the
`resolveKeystoreAlias` raw-alias guard removed, 2 of its 5 tests fail (resolve
and `deleteKey`); with the `deleteByAlias` guard removed, 1 fails. Both guards
were restored unchanged.

## r6: Ed25519 fallback exclusion and slot listing generation

- On API 33+ a general Ed25519 key with id `xkey_piv_9A` is stored in the
  Ed25519 preferences under `xkey_key_xkey_piv_9A`. The fallback returned
  `keyId`, the raw alias of slot 9A, so `deleteKey` removed the slot key. It
  now returns the general alias for a key stored there and skips the raw
  Ed25519 check for a PIV alias. The check sits behind
  `hasSoftwareEd25519Key` so `KeystoreManagerPivAliasTest` drives it on the
  JVM (2 tests).
- `listSlots` re-reads each slot's row under its `PivSlotLocks` lock before
  reading the live key. `PivKeyManagerTest` holds an ES256-to-RS2048
  regenerate at its upsert while a listing runs, and checks that the listing
  shows one generation.
