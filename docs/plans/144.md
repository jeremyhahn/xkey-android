# Plan: #144 remote key sharing to the paired desktop

## Objective

Send keys from the phone to the paired desktop with `remote.sharePublicKey`,
`remote.shareSymmetric` and `remote.importSharedKey`. The params and results
use the shapes in go-xkms xkey/v0.64.2-alpha `pkg/pairingproto`. Nothing
reaches the wire unless the `local.*` sharing rules allow it.

## Slices

1. **Wire shapes (test first).** `RemoteShareClientTest` pins param keys,
   base64/PEM fields, omitempty, result parsing, malformed replies, error and
   timeout mapping, zeroing, and shared request IDs (base 6_000_000).
2. **Client.** `remote/RemoteShareClient.kt` holds strict types and throws
   `ProtocolException` on a malformed reply.
3. **Policy gate.** `DesktopKeyShareTest`: a denied, unconfirmed-peer or
   non-exportable key never reaches the wire; a hardware key sends only its
   public half; software material is zeroed. `DesktopShareGate` mirrors the
   Handler rules for `local.importSharedKey`.
4. **Sheet.** `KeySharingBottomSheet` gets a "Paired desktop" section. It is
   hidden with no desktop, and the strings are in `strings_sharing.xml`.
   `KeySharingDesktopStatusTest` gives each gate decision its own status line.
5. **Docs.** docs/key-sharing/architecture.md and
   docs/remote-key-access/architecture.md list the methods. The key-sharing
   page says why symmetric keys are not sent.

## Findings

- No wrap path matches. The desktop bridge hands `wrapped_key` to xkmsd's
  BYOK `ImportKey`, which needs the wrapping key and import token from
  `GetImportParameters`; the pairing protocol cannot fetch them, so
  `SYMMETRIC_WRAP_PATH_MATCHES` is false and only the public key is offered.
- `XKeyGattService.shareSession()` returns one `ShareSession` snapshot:
  sender, router and confirmed peer together. The send checks the policy
  against that snapshot's peer and refuses (`SessionChanged`) if the session
  is replaced before the transport encrypts the bytes.
- The session is bound to one connection. Each transport reports the peer
  confirmed on its own live connection (`MessageSender.confirmedConnection`);
  a share goes out via `sendEncryptedMessageOn`, which every transport
  refuses at encryption admission unless that connection still confirms it.
  Out of the file map for this: ble/GattServer, ble/XKeyGattService,
  transport/StreamPairingSession, tcp/TcpHsmServer, usb/UsbAccessoryServer.
- `loadZeroedOnCancel` zeroes decrypted share inputs a cancellation drops.
- A key that fails to load in the desktop refresh is reported (send hidden,
  error shown, policy controls kept), never thrown out of the sheet's scope.
- BLE admission checks the scoped connection before liveness, so a reconnect
  at encryption fails as a changed connection on every transport.
- A reply with `accepted=false` is `Outcome.Declined`, shown as
  `sharing_desktop_declined` (`strings_sharing.xml`, outside the r3 map).
- The service has no confirm event, so the sheet polls `shareSessionChanges`
  (500 ms, while started). `DesktopSectionRefresh` lets only the latest
  refresh apply, and only on the session it decided on: a disconnect or a
  new session that overtakes a pending decision always wins.
- Handler's sharing checks are private, so `DesktopShareGate` repeats them.
  Follow-up: Handler should call the gate.
- Revocation while pending: `DesktopKeyShare` runs the gate again in the
  guarded sender, immediately before the bytes go to the transport, on the
  key as the store holds it then (`currentEntity`) and the peer grants as
  they stand then. A policy narrowed, a grant removed or the key deleted
  while the share waited refuses it (`POLICY_DENIED`) and nothing is sent.
  A revoke that commits after that check and during encryption is ordered
  after the send. `shareSymmetric` and `importSharedKey` have no snapshot
  check of their own (no caller sends symmetric material; import is
  desktop to phone); a caller passes its check as `client(beforeSend)`.

## Out of scope

- SPEC.md, the other remote clients, PivActivity and OathActivity.
- Sending the certificate from the sheet (`certificatePem` is null).
- A UI for `remote.importSharedKey` (client method only).
- A symmetric wrap path (needs a go-xkms pairing method for the parameters).
