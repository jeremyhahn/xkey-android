# Plan: #144 remote key sharing to the paired desktop

## Objective

Send keys from the phone to the paired desktop with `remote.sharePublicKey`,
`remote.shareSymmetric` and `remote.importSharedKey`. The params and results
use the shapes in go-xkms xkey/v0.64.2-alpha `pkg/pairingproto`. Nothing
reaches the wire unless the `local.*` sharing rules allow it.

## Slices

1. **Wire shapes (test first).** `RemoteShareClientTest` pins param keys,
   base64/PEM fields, omitempty, result parsing, malformed replies, error and
   timeout mapping, zeroing, and shared request IDs (base 6_000_000).
2. **Client.** `remote/RemoteShareClient.kt` holds strict types and throws
   `ProtocolException` on a malformed reply.
3. **Policy gate.** `DesktopKeyShareTest`: a denied, unconfirmed-peer or
   non-exportable key never reaches the wire; a hardware key sends only its
   public half; software material is zeroed. `DesktopShareGate` mirrors the
   Handler rules for `local.importSharedKey`.
4. **Sheet.** `KeySharingBottomSheet` gets a "Paired desktop" section. It is
   hidden with no desktop, and the strings are in `strings_sharing.xml`.
   `KeySharingDesktopStatusTest` gives each gate decision its own status line.
5. **Docs.** docs/key-sharing/architecture.md and
   docs/remote-key-access/architecture.md list the methods. The key-sharing
   page says why symmetric keys are not sent.

## Findings

- No wrap path matches. The desktop bridge hands `wrapped_key` to xkmsd's
  BYOK `ImportKey`, which needs the wrapping key and import token from
  `GetImportParameters`; the pairing protocol cannot fetch them, so
  `SYMMETRIC_WRAP_PATH_MATCHES` is false and only the public key is offered.
- `XKeyGattService.shareSession()` returns one `ShareSession` snapshot:
  sender, router and confirmed peer together. The send checks the policy
  against that snapshot's peer and refuses (`SessionChanged`) if the session
  is replaced before the transport encrypts the bytes.
- The session is bound to one connection. Each transport reports the peer
  confirmed on its own live connection (`MessageSender.confirmedConnection`);
  a share goes out via `sendEncryptedMessageOn`, which every transport
  refuses at encryption admission unless that connection still confirms it.
  Out of the file map for this: ble/GattServer, ble/XKeyGattService,
  transport/StreamPairingSession, tcp/TcpHsmServer, usb/UsbAccessoryServer.
- `loadZeroedOnCancel` zeroes decrypted share inputs a cancellation drops.
- A key that fails to load in the desktop refresh is reported (send hidden,
  error shown, policy controls kept), never thrown out of the sheet's scope.
- BLE admission checks the scoped connection before liveness, so a reconnect
  at encryption fails as a changed connection on every transport.
- A reply with `accepted=false` is `Outcome.Declined`, shown as
  `sharing_desktop_declined` (`strings_sharing.xml`, outside the r3 map).
- The service has no confirm event, so the sheet polls `shareSessionChanges`
  (500 ms, while started). `DesktopSectionRefresh` lets only the latest
  refresh apply, and only on the session it decided on: a disconnect or a
  new session that overtakes a pending decision always wins.
- Handler's sharing checks are private, so `DesktopShareGate` repeats them.
  Follow-up: Handler should call the gate.
- Revocation while pending: the permission check runs at transport
  admission, the step that consumes the nonce, after every wait (BLE: the
  notification channel and `sendMutex`; TCP/USB: the send lock and the IO
  dispatcher). `DesktopKeyShare` takes the key's `SharePermissionLedger`
  revision, then runs the gate again on the key as the store holds it
  (`currentEntity`) and the peer grants as they stand. The transport then
  runs the check `sendEncryptedMessageOn(admit)` hands it inside its
  admission critical section (`GattServer.revocationLock`, the stream
  connection's `state` lock): it refuses the send if a revoke of that key is
  in flight or has committed since the revision. Every revoke writer (policy
  change, grant removal, key delete) commits through
  `SharePermissionLedger.revoking`, which takes the ledger's lock before the
  write and again after it; admission takes the same lock, so a revoke
  started before admission always wins. A policy narrowed, a grant removed or
  the key deleted while the share waited refuses it (`POLICY_DENIED`): nothing
  is encrypted or written. A revoke that starts after admission is ordered
  after the send. The check applies to every send of `ShareSession.client`
  (`sharePublicKey`, `shareSymmetric`, `importSharedKey`); only the
  public-key share passes one today, as no caller sends symmetric material
  and import is desktop to phone.
- Key-delete sweep (r11): every path that deletes a key or its metadata row
  commits through `SharePermissionLedger.revoking`: `local.deleteKey`, the
  legacy `deleteKey` RPC (it now also removes the metadata row), the
  KeyDetail, KeyManagement, Passkey, Passkeys and CertificateManagement
  deletes, and the `KeyStoreSyncManager` prune; `KeyDao.delete`,
  `deleteFido2ByRpId` and `deleteAll` have no app caller, key generation
  refuses an existing key ID (`KEY_EXISTS`) so no insert replaces a shared
  key, and PIV slot deletes touch no key metadata row.
- Key-row choke point (r12): `KeyDao` itself commits every write that
  replaces, re-permissions or deletes a key row as a revoke of that key ID
  (`SharePermissionLedger.revoking`), so no caller can bypass it.
  The raw Room writes are marked `@RawKeyRowWrite` (an opt-in at ERROR level)
  and only `KeyDao`'s own wrappers opt in. Callers that already wrapped a write
  in `revoking` now nest it; the ledger counts in-flight revokes, so nesting is
  harmless. `local.generateKey` also refuses an ID that any key store holds
  (`KEY_EXISTS`): the general or credential Keystore namespace, the software
  store, or the metadata table. A row that appears after that check, during
  the generation's prompt, is still replaced only as a revoke.

  | KeyDao write | App callers | Why it cannot bypass the ledger |
  |---|---|---|
  | `insert` (REPLACE) | Handler `local.generateKey` (3 paths), CreateCredentialHandler, KeyStoreSyncManager (2), CertificateManagementActivity, KeyManagementActivity | the DAO method runs `insertRow` inside `revoking(key.keyId)` |
  | `insertRow` | none (`@RawKeyRowWrite`) | only `insert` opts in; any other call fails to compile |
  | `update` | none | runs `updateRow` inside `revoking(key.keyId)` |
  | `updateRow` | none (`@RawKeyRowWrite`) | only `update` opts in |
  | `delete` | none | runs `deleteRow` inside `revoking(key.keyId)` |
  | `deleteRow` | none (`@RawKeyRowWrite`) | only `delete` opts in |
  | `updateSharingPolicy` | Handler `local.setKeyPolicy`, KeySharingBottomSheet | runs `updateSharingPolicyRow` inside `revoking(keyId)` |
  | `updateSharingPolicyRow` | none (`@RawKeyRowWrite`) | only `updateSharingPolicy` opts in |
  | `deleteByKeyId` | Handler `deleteKey` and `local.deleteKey`, KeyStoreSyncManager prune, CertificateManagement, KeyDetail, KeyManagement, PasskeyDetail and Passkeys activities | runs `deleteRowByKeyId` inside `revoking(keyId)` |
  | `deleteRowByKeyId` | none (`@RawKeyRowWrite`) | only `deleteByKeyId` opts in |
  | `deleteFido2ByRpId` | none | deletes each matching row through `deleteByKeyId` |
  | `deleteAll` | none (instrumented tests only) | deletes each row through `deleteByKeyId` |
  | `recordUsage` | Handler sign/encrypt paths, GetCredentialHandler, FileOperationActivity | changes `use_count` and `last_used_at` only, not who may receive the key: not a revoke |
  | `updateSignCount` | Handler FIDO2 assertion, GetCredentialHandler | changes `sign_count` and `last_used_at` only: not a revoke |

- Key material inside the revoke (r13): a delete that removed the Keystore
  entry before opening its revoke left a window where a waiting share passed
  admission with an unchanged revision and sent the cached PEM.
  `KeyDao.deleteKeyAndMaterial(keyId) { ... }` opens the revoke, removes the
  material, then the row; every key delete that removes material uses it or,
  for the legacy RPC, its own `revoking` block. Every path that removes key
  material:

  | Removal | Store | Inside `revoking` from its first removal |
  |---|---|---|
  | Handler `local.deleteKey` | Keystore general entry (`deleteGeneralKey`), `SoftwareKeyStore.delete`, row | yes: `deleteKeyAndMaterial` |
  | Handler `deleteKey` (legacy) | Keystore entry (`KeystoreManager.deleteKey`), row | yes: its own `revoking` block (r11) |
  | KeyDetailActivity delete | Keystore entry (`deleteByAlias`), row | yes: `deleteKeyAndMaterial` |
  | KeyManagementActivity delete | Keystore entry (`deleteByAlias`), row | yes: `deleteKeyAndMaterial` |
  | CertificateManagementActivity issuance rollback | Keystore entry (`deleteByAlias`), row | yes: `deleteKeyAndMaterial` |
  | CreateCredentialHandler metadata-failure rollback | Keystore credential entry | no key row has been written yet, so no share of it can exist |
  | FileEncryptor ephemeral key | Keystore entry | never a key row, never shared |
  | PivSlotDetailActivity delete | PIV slot (`PivKeyManager.deleteKey`) | yes since r15: the slot alias is a discovered key row's ID |
  | OathRepository `deleteCredential` | OATH credential store | no key row; not shared through `DesktopKeyShare` |

## Invariant (r14)

Rounds 10 to 13 each closed one path; this is the rule they all serve, and
every share and every key-material change is held to it:

1. A share sends only if the key revision it captured before reading any
   key input (record, public half, software material) is unchanged at the
   transport's admission. `SharePermissionLedger.baseline(keyId)` captures
   it; `DesktopKeyShare.send` takes that baseline and nothing else as its
   admission check, and refuses a baseline for another key.
2. Every operation that removes or replaces key material resolves the
   key's canonical ID first (an alias form such as `xkey_key_<id>` resolves
   to `<id>`) and opens `SharePermissionLedger.revoking` on that ID before it
   touches the Keystore, the software store or the metadata row.
3. `local.generateKey` reserves its canonical ID for its whole run, across
   the biometric prompt (a second generation of the same ID meanwhile is
   refused with `KEY_EXISTS`), checks existence again after approval, and
   generates inside the revoke.

Sweep (line numbers at the r14 fix). Paths that read key inputs for a share:

## r15: PIV deletion and replacement enter the share ledger

`KeyStoreSyncManager.discoverKeystoreEntries()` gives every Keystore alias
outside the xKey prefixes a plain key row whose ID is the alias, so a PIV
slot (`xkey_piv_9A`) is shareable from the sheet. PIV keys stay shareable.
`PivKeyManager.deleteKey` and `generateKey` now run their Keystore and
`piv_slots` writes inside `SharePermissionLedger.revoking(slot.keystoreAlias)`,
as every other key delete and replacement does (invariant 2). The ledger is
the existing singleton; its contract is unchanged, and no construction site
changes: `PivKeyManager` gains only a defaulted key-pair generator parameter
so tests run the real writer. Tests (`StreamPairingSessionRevocationTest`):
a share paused at admission while the real `deleteKey`, or `generateKey`
replacing the slot, runs sends nothing; a share started after `generateKey`
completes sends the new key.

## r16: merged with unpair-drops-grants

Main (#182) moved the sheet's peer list onto `KeySharingPeers`, whose grants
go through `PairedDeviceRepository.writeGrant` (bound to the pairing
generation, docs/plans/174.md r7-r8). One file conflicted,
`ui/KeySharingBottomSheet.kt`, in three hunks:

- Imports: this branch's remote-share imports kept; `PairedDeviceData`
  dropped, as main did (the sheet no longer names it).
- `persistSharingPolicy`: the clear of per-peer rows stays inside the
  `SharePermissionLedger.revoking(keyId)` block after the policy update (the
  same order main uses); main's second clear and this branch's
  `allowedPeersFlow` reset are gone, since the list now follows the rows.
- `updatePeerPolicy`: main's `sharingPeers.setAllowed` path, with its
  redraw on a refused grant. A withdrawal runs inside
  `SharePermissionLedger.revoking(keyId)`, as this branch's removal did; a
  grant runs unwrapped through `writeGrant`.

Not changed: the unpair cleanup (`clearPoliciesForPeer`) drops a peer's rows
without a ledger revoke. Whether a share already waiting for that desktop
must also be refused is left to a follow-up row; this merge does not decide it.

## r17: exact key IDs, pending revocations and untracked writers

- `local.deleteKey`: an ID with a key row or a software key of its own is
  that key; only an ID with neither is read as a raw Keystore alias
  (`canonicalKeyId`). Software key `xkey_key_a` and hardware key `a` (alias
  `xkey_key_a`) can both exist; deleting the first no longer deletes the
  second (`LocalDeleteKeyExactIdTest`).
- Desktop share: `DesktopShareGate.peerGrant` is the SELECTED_PEERS check the
  sheet passes to both gate checks (the early decision and the recheck at
  admission). Like `RequestHandler.canShareKeyWithPeer`, it refuses a peer
  whose unpair revocation is pending (#174), so an old grant left by
  unpair-then-re-pair never authorizes the re-paired desktop
  (`PairedDeviceGrantCleanupTest.aRePairedPeerIsRefusedADesktopShareWhileItsRevocationIsPending`).
- `DeviceIdentity` (`createEnrollmentRequest`, `storeCredential`, `reset`)
  and `KeystoreUserVerificationKey` (`regenerate` and its repairs) replace
  their keys outside the ledger, synchronously and from many paths, while
  `KeyStoreSyncManager` gives their aliases plain key rows. Rather than
  enroll every one of those writers, `DesktopShareGate` refuses their aliases
  (`xkey_device_identity_*`, `xkey_user_verification_key`) outright, at both
  checks: they are the phone's own identity keys, not keys to hand a desktop
  (`DesktopKeyShareTest`, a share paused before admission while the key is
  replaced sends nothing).

## r18: UI deletes revoke the key actually removed; ephemeral keys never shared

- KeyDetailActivity and KeyManagementActivity delete through one storage
  helper, `KeyDao.deleteKeyRow` (`storage/KeyStoreSyncManager.kt`), never
  through `resolveKeystoreAlias`. A row's key ID names exactly one key: a
  software key of that ID if `SoftwareKeyStore` holds one, else the Keystore
  entry discovery maps to that ID (`xkey_credential_<id>`, `xkey_key_<id>`,
  or the ID itself only when it carries neither prefix). The revoke is that
  row's ID, the one removed. Deleting software key `xkey_key_a` no longer
  removes hardware key `a` (alias `xkey_key_a`), so a share of `a` waiting
  for admission still sends a live key.
- Correction to the invariant table: FileEncryptor's ephemeral key
  (`xkey_key_ephemeral_<UUID>`) could get a row. `discoverKeystoreEntries`
  saw every alias, so key management opened during a long encryption gave it
  a plain, shareable row. Now discovery skips `xkey_key_ephemeral_` aliases,
  `DesktopShareGate` refuses `ephemeral_` IDs at both checks (a row left by an
  earlier build), and FileEncryptor deletes the key inside
  `SharePermissionLedger.revoking` of its canonical ID.
- Tests (`KeyMaterialRemovalShareTest`): both UI paths delete the
  `xkey_key_a` row while a share of `a` waits; an ephemeral row's share waits
  while the encryption completes and is refused. `KeyStoreSyncManagerTest`:
  an ephemeral alias gets no row.

## r19: delete the resolved alias, legacy generation in the share ledger

- `local.deleteKey` removes only the material of the key its ID resolved
  to, inside the canonical ID's revoke. A raw alias (`xkey_credential_k`,
  `xkey_key_k`) deletes that Keystore entry itself; a canonical ID deletes
  its software key, else the first entry discovery maps to it
  (`KeyStoreSyncManager.keystoreAliasesOf`, the rules `KeyDao.deleteKeyRow`
  uses). Before, `xkey_credential_k` dropped `k`'s row and policies but
  deleted `xkey_key_k`, leaving the credential able to sign. The answer is
  `deleted=true` only when material or a row went.
- Legacy `generateKey` was a material writer outside the ledger: it checked
  existence only before its prompt, and writes no key row. It now holds
  invariant 3 like `local.generateKey`: `KeyGenerationReservations` on the
  credential ID across the prompt (a second request on any transport is
  refused), the existence check again after approval, and
  `generateKeyWithAuthDuration` inside `SharePermissionLedger.revoking`.
- Tests: `LocalDeleteKeyExactIdTest` (a raw credential alias deletes the
  credential, the general key survives, a second delete reports nothing);
  `LegacyGenerateKeyShareLedgerTest` (a delayed request reserves the ID, the
  other transport's is refused, one generation, a share baselined before is
  refused; a credential created during the prompt is not replaced).
