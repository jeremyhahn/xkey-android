# #135: wire error for missing user verification

## Objective

`UserVerificationCompliance.enforce` throws `UserVerificationRequiredException`
when a peer requires user verification that did not happen and strict UV is
on. On the wire (`local.signFido2Assertion`) nothing caught that type, so
`RequestHandler.dispatch` answered with the generic `INTERNAL_ERROR`
(-32603), which reads as "the phone is broken". Map it through one explicit
`ErrorCodes` constant, documented at the mapping, and pin it with a test.

## Choice of code

`ErrorCodes.BIOMETRIC_FAILED` (-32003). Neither SPEC.md nor the docs name a
code for this case. It is the code dispatch already sends for
`BiometricRequiredException` and `BiometricUnavailableException`, the two
other "verification was required and did not happen" cases, and the
exception's message tells the user to enrol a biometric, which is what a peer
seeing -32003 already tells its user. `OPERATION_DENIED` was the other
candidate; it means a policy refusal (sharing policy) the user cannot fix by
verifying, so it fits less. No new code is added.

## Slices

1. `test(protocol)`: `UserVerificationWireErrorTest` sends a request for
   each wire FIDO2 method (`local.listFido2Credentials`,
   `local.signFido2Assertion`) through `RequestHandler.handleRequest`, with a
   mocked `KeyDao` throwing the real `enforce` refusal (REQUIRED, not
   verified, strict); asserts code -32003, the request id, and the
   exception's message. Fails without the dispatch catch (-32603). A first
   version called the mapping directly; review asked for dispatch.
2. `fix(protocol)`: `UserVerificationWireError` in `protocol/` holds the
   constant and builds the response; `dispatch` catches
   `UserVerificationRequiredException` before the generic `Exception`.
   The mapping file landed first in a `wip:` commit (the first session could
   not edit `Handler.kt`); the `fix` commit wires it into `dispatch`.

3. `docs`: after merging main, `docs/fido2-phone-backend/architecture.md`
   names `BIOMETRIC_FAILED` for both methods in its errors table and links
   `UserVerificationWireError.kt`.

## Out of scope

- The Credential Manager create/get handlers: they report through Android's
  credential exceptions, not `ErrorCodes`.
- Any SPEC wording, method name, or go-xkms change.
