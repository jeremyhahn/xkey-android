# Plan 189: audit trust store imports and deletes

## Objective

`AuditLogger.logTrustStoreImport` and `logTrustStoreDelete` have no caller, so
adding or removing a trusted CA never reaches the audit log. Record both from
`TrustStoreRepository`, which every trust store write goes through (manual
import, URL import, bootstrap, trust store sync, internal CA).

## Slices

1. Failing tests (`TrustStoreRepositoryTest`), capturing entries through
   `AuditLogger`'s `daoRef`/`scopeRef` holders (relaxed DAO mock,
   `Dispatchers.Unconfined`, both reset in `@After`):
   - importCertificate records one TRUST_STORE_IMPORT with subject,
     fingerprint and source `manual`;
   - a duplicate import and a self-signed certificate record nothing;
   - importFromURL records one import per stored certificate with source
     `url:<url>`;
   - importInternalCACertificate records source `internal-ca`;
   - deleteCertificate of a stored certificate records one
     TRUST_STORE_DELETE; of an unknown fingerprint, nothing;
   - clearAll over two certificates records two deletes.
2. Fix in `TrustStoreRepository`:
   - `storeCertificate` logs the import after the DER and metadata are
     written, with the subject, the repository's fingerprint and `source`;
   - `deleteCertificate` logs only when it returns true, with the subject from
     the metadata row (empty when only the file existed);
   - `clearAll` reads the metadata first and logs one delete per entry.
   - The repository logs only when `AuditLogger.isInitialized()`: the
     uninitialized drop path calls `android.util.Log.w`, which throws in JVM
     unit tests (no `returnDefaultValues`), so callers that never initialize
     the logger (e.g. `TrustStorePersistenceTest`, sync) would break.
3. `docs/audit-log/architecture.md` names the trust store events.

## Out of scope

## r4: deletion events only for real removals

Review finding: clearAll ignored a null `listFiles()` and every
`File.delete()` result, yet logged every metadata row as a successful
delete, so a CA that stayed trusted could be audited as removed.

- `TrustStoreRepository` takes an injectable `fileDeleter` (default
  `File.delete`); a file counts as removed only if it no longer exists.
- `clearAll` removes each metadata row's file, rewrites the metadata with
  the rows it could not remove (deletes it when none remain), then clears
  stray files. It returns `ClearResult(removed, failed, unlisted)`.
  Removed certificates record a successful TRUST_STORE_DELETE; the others
  record one with success=false and an error message.
- `deleteCertificate` keeps the metadata row, records a failure and
  returns false when the file cannot be deleted or the metadata cannot
  be rewritten.
- `AuditLogger.logTrustStoreDelete` gains `success` and `errorMessage`
  parameters with defaults (callers unchanged).
- Tests: `clearAll records a failed delete for a certificate it cannot
  remove`, `clearAll reports a complete clear when every certificate is
  removed`, `deleteCertificate records a failure and keeps the entry when
  the file cannot be removed`.
- Left for a follow-up: `TrustStoreActivity` ignores the `ClearResult` and
  still shows "cleared" (UI is out of this row's file map). Done in r5.

## r5: atomic metadata, callers honour failures, stray files audited

Review findings on r4: a partial clear rewrote metadata.json in place, so a
write that failed after truncating lost the rows of certificates still on
disk; the screens deleted the database row and showed success whatever the
repository returned; and clearAll removed DER files no metadata row named
without auditing them.

- `TrustStoreRepository` takes an injectable `fileWriter`; `saveMetadataSync`
  writes `metadata.json.tmp` and renames it over `metadata.json`, so a failed
  write leaves the previous document (and the temp file is removed).
- `clearAll` puts each removed stray `.der` file's fingerprint in `removed`
  and records a successful TRUST_STORE_DELETE with an empty subject.
- `TrustStoreDeletion.kt`: `removeTrustedCertificate` deletes the database
  row only once the certificate is neither on disk nor in the metadata;
  `clearTrustStore` clears first and deletes the rows of `removed` only.
  `CertificateManagementActivity`, `CertificateDetailActivity` and
  `TrustStoreActivity.confirmClearAll` call them and report a failure or a
  partial clear instead of success.
- Tests: `a metadata write that fails part-way keeps the previous metadata`,
  `clearAll removes and audits a certificate file without metadata`, and
  `TrustStoreDeletionTest` (row kept on failure, deleted on success or when
  the certificate was never in the store, partial clear).

## r6: one writer at a time across repository instances

Review finding on r5: SyncEngine and the screens each create their own
repository, and every writer shared `metadata.json.tmp`, so one writer could
rename another's snapshot and report success while the other's rename failed,
losing certificate rows (an empty store skips EK chain verification).

- A process-wide lock per store directory (canonical path) serializes every
  metadata read/modify/write and deletion: imports (the presence check and
  the store together), `deleteCertificate`, `clearAll`,
  `updateSystemInstalled` and `refreshSystemInstallStatus`. Readers take no
  lock: the rename gives them the old or the new document.
- `saveMetadataSync` writes its own `File.createTempFile` (exclusive, unique
  name), renames it and removes it if the rename failed.
- Tests hold the first repository's write on a latch while a second instance
  imports or deletes: `two repositories importing at once both keep their
  certificate`, `a delete on another repository during an import keeps the
  imported certificate`, `an import on another repository during a delete is
  kept`. Each checks the metadata parses to the expected set, both results,
  and that no `.tmp` file remains.
- Out of scope: writers in other processes (the app has one).

## r7: URL import sources redacted before audit logging

Review finding on r6: importFromURL recorded the whole URL as the source, so
userinfo and signed-URL query tokens reached Room audit details and the
AuditLogActivity JSON/CSV export, and outlived the certificate's deletion.

- `importFromURL` records `url:` plus `redactedUrl(url)`: scheme, host, port
  and decoded path only; userinfo, query and fragment are dropped.
  Characters no URI allows (quotes, spaces, braces) are percent-encoded
  before parsing, so `TrustStorePersistenceTest`'s quoted path still
  round-trips. A URL that then does not parse, is opaque or has a registry-based authority is recorded
  as `url:[unparseable url]`. The metadata row gets the same source.
- Tests: `importFromURL keeps url credentials, query and fragment out of the
  audit log`, `importFromURL logs a malformed url without its raw text`.
- Out of scope: secrets in the URL path; audit rows written before r7.

## r8: hostless URIs never logged verbatim

Review finding on r7: for `https:///user:secret@example.com/ca.pem`
java.net.URI finds no authority and puts the userinfo in the path, so the
redactor returned it verbatim, while OkHttp (CABundleFetcher) skips the
redundant slashes and fetches from example.com: a successful import stored
the credentials in the metadata and the audit details.

- `redactedUrl` returns `[unparseable url]` whenever the parsed host is
  null (hostless paths as well as registry-based authorities).
- Test: `importFromURL through okhttp logs a hostless url without its
  credentials`, a real OkHttp client whose interceptor serves the bundle
  (no network); audit details and metadata hold neither `user` nor `secret`.
- Out of scope: redacting with OkHttp's HttpUrl parser instead of
  java.net.URI.

## r9: deletion failure state

Review findings on r8: when the metadata rewrite failed after the DER file
was deleted, deleteCertificate and clearAll reported the CA as kept (row and
screens say trusted) while verifyIDevIDChain, which loads anchors from the
DER files, had lost it; and TrustStoreActivity.confirmDelete ignored false.

- Decision: restore, not partial removal. Both paths read each DER before
  deleting it; when the metadata rewrite throws they write the bytes back,
  so the CA stays trusted everywhere: reported failed, row kept, audit
  failure, chain verification still anchored on it. Only if the restore
  also fails is the CA gone from verification: then it is reported removed
  (database row dropped, audit success carrying the metadata error) and its
  stale metadata row is left for a later delete or clear.
- clearAll restores before its stray pass, so restored files are not strays.
- TrustStoreActivity: confirmDelete goes through removeTrustedCertificate
  (top-level `deleteFromTrustStoreScreen`), shows a failure message on
  false and refreshes the list either way.
- Tests: `removeTrustedCertificate keeps a CA whose metadata rewrite fails
  trusted for chain verification`, `clearTrustStore keeps CAs whose metadata
  rewrite fails trusted for chain verification`, and
  `TrustStoreScreenDeleteTest` (failure message and refresh on false).
- Out of scope: a unit test of the double failure (restore write failing).
