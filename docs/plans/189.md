# Plan 189: audit trust store imports and deletes

## Objective

`AuditLogger.logTrustStoreImport` and `logTrustStoreDelete` have no caller, so
adding or removing a trusted CA never reaches the audit log. Record both from
`TrustStoreRepository`, which every trust store write goes through (manual
import, URL import, bootstrap, trust store sync, internal CA).

## Slices

1. Failing tests (`TrustStoreRepositoryTest`), capturing entries through
   `AuditLogger`'s `daoRef`/`scopeRef` holders (relaxed DAO mock,
   `Dispatchers.Unconfined`, both reset in `@After`):
   - importCertificate records one TRUST_STORE_IMPORT with subject,
     fingerprint and source `manual`;
   - a duplicate import and a self-signed certificate record nothing;
   - importFromURL records one import per stored certificate with source
     `url:<url>`;
   - importInternalCACertificate records source `internal-ca`;
   - deleteCertificate of a stored certificate records one
     TRUST_STORE_DELETE; of an unknown fingerprint, nothing;
   - clearAll over two certificates records two deletes.
2. Fix in `TrustStoreRepository`:
   - `storeCertificate` logs the import after the DER and metadata are
     written, with the subject, the repository's fingerprint and `source`;
   - `deleteCertificate` logs only when it returns true, with the subject from
     the metadata row (empty when only the file existed);
   - `clearAll` reads the metadata first and logs one delete per entry.
   - The repository logs only when `AuditLogger.isInitialized()`: the
     uninitialized drop path calls `android.util.Log.w`, which throws in JVM
     unit tests (no `returnDefaultValues`), so callers that never initialize
     the logger (e.g. `TrustStorePersistenceTest`, sync) would break.
3. `docs/audit-log/architecture.md` names the trust store events.

## Out of scope

- Any change to `AuditLogger` or its signatures.
- `AuditLoggerDispatchTest`, the UI activities and `sync/`.
- Auditing refused or failed imports.

## r4: deletion events only for real removals

Review finding: clearAll ignored a null `listFiles()` and every
`File.delete()` result, yet logged every metadata row as a successful
delete, so a CA that stayed trusted could be audited as removed.

- `TrustStoreRepository` takes an injectable `fileDeleter` (default
  `File.delete`); a file counts as removed only if it no longer exists.
- `clearAll` removes each metadata row's file, rewrites the metadata with
  the rows it could not remove (deletes it when none remain), then clears
  stray files. It returns `ClearResult(removed, failed, unlisted)`.
  Removed certificates record a successful TRUST_STORE_DELETE; the others
  record one with success=false and an error message.
- `deleteCertificate` keeps the metadata row, records a failure and
  returns false when the file cannot be deleted or the metadata cannot
  be rewritten.
- `AuditLogger.logTrustStoreDelete` gains `success` and `errorMessage`
  parameters with defaults (callers unchanged).
- Tests: `clearAll records a failed delete for a certificate it cannot
  remove`, `clearAll reports a complete clear when every certificate is
  removed`, `deleteCertificate records a failure and keeps the entry when
  the file cannot be removed`.
- Left for a follow-up: `TrustStoreActivity` ignores the `ClearResult` and
  still shows "cleared" (UI is out of this row's file map). Done in r5.

## r5: atomic metadata, callers honour failures, stray files audited

Review findings on r4: a partial clear rewrote metadata.json in place, so a
write that failed after truncating lost the rows of certificates still on
disk; the screens deleted the database row and showed success whatever the
repository returned; and clearAll removed DER files no metadata row named
without auditing them.

- `TrustStoreRepository` takes an injectable `fileWriter`; `saveMetadataSync`
  writes `metadata.json.tmp` and renames it over `metadata.json`, so a failed
  write leaves the previous document (and the temp file is removed).
- `clearAll` puts each removed stray `.der` file's fingerprint in `removed`
  and records a successful TRUST_STORE_DELETE with an empty subject.
- `TrustStoreDeletion.kt`: `removeTrustedCertificate` deletes the database
  row only once the certificate is neither on disk nor in the metadata;
  `clearTrustStore` clears first and deletes the rows of `removed` only.
  `CertificateManagementActivity`, `CertificateDetailActivity` and
  `TrustStoreActivity.confirmClearAll` call them and report a failure or a
  partial clear instead of success.
- Tests: `a metadata write that fails part-way keeps the previous metadata`,
  `clearAll removes and audits a certificate file without metadata`, and
  `TrustStoreDeletionTest` (row kept on failure, deleted on success or when
  the certificate was never in the store, partial clear).
