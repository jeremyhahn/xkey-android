# #180: a signature never shows as verified without a real check

## Objective

Two bugs share one rule: a signer is verified only when the stored content
hash matches the file *and* the signature checks against a public key we
hold.

1. Trust by association. `VerifiedMediaViewerActivity.verifyEntry` and
   `FileOperationActivity.verifySignatures` match a local key row with no
   public key (`publicKeyDer == null`) when its `keyId` equals the entry's
   `keyFingerprint`, then report the signer verified with no signature
   check. Both values come from the file under test. Such a key must never
   match: the signer is unknown.
2. Copied signature block. `FileOperationActivity.performVerify` hashes the
   file but `verifySignatures` checks the signature over the stored
   `contentHash` alone, so an in-band block copied onto another file
   verifies. The in-band path must check
   `MediaHasher.contentHashMatchesUri(..., SignatureSource.IN_BAND)` first,
   as the viewer and the sidecar path do; on a mismatch every entry fails.

## Slices (commits, in order)

1. This plan.
2. Refactor, behaviour unchanged: `media/SignerVerification.kt` holds the
   per-entry decision (today's rule, trust-by-association included); both
   activities call it and keep their own result types and UI text.
3. Failing tests: `media/SignerVerificationTest.kt` with real EC P-256
   keys. Null-key row whose keyId equals the fingerprint gives UNKNOWN
   (fails on slice 2); valid key + signature + hash match gives VERIFIED;
   hash mismatch, corrupted signature, invalid contact signature give
   FAILED; valid contact signature gives VERIFIED; no match gives UNKNOWN.
4. Fix: drop the null-key match; `performVerify` checks the in-band content
   hash and passes the result in.
5. Docs: both features' `architecture.md` state the rule.

## Out of scope

- strings.xml, Handler.kt, AuditLogger.kt, ble/ and remote/ (open PRs).
- Desktop-side signing and the sidecar format.
