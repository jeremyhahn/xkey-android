# Plan #177: cosign.request signs only after the owner approves

## Objective

`RequestHandler.handleCosignRequest` signed whatever hex `hash` a peer sent,
at once: no prompt, no confirmed-peer check, no digest-length check, and the
fallback key could be a FIDO2 credential. It is in the shared dispatch map,
so every transport reaches it. After this change it:

1. refuses a session with no confirmed peer (`OPERATION_DENIED`);
2. checks `hashAlgorithm` is known and `hash` decodes to exactly its digest
   length (SHA-256: 32 bytes); otherwise `INVALID_PARAMS`;
3. signs only with a `signing` key: a named key of any other type (FIDO2
   included) is `OPERATION_DENIED`, and the fallback never picks a FIDO2 key;
4. asks the owner on the phone through `BiometricActivityLauncher`, naming the
   first 8 hex characters of the hash; no launcher, a cancel or a failure is
   `BIOMETRIC_FAILED` and nothing is signed;
5. keeps the success result shape (`signature`, `keyFingerprint`,
   `algorithm`, `signerName`).

## Slices, in order

1. This plan.
2. Failing tests: `CosignRequestHandlerTest` (JVM, mocked database, keystore
   and launcher): approved prompt signs; cancelled prompt and null launcher
   answer `BIOMETRIC_FAILED` and never sign; no confirmed peer and a named
   FIDO2 key answer `OPERATION_DENIED`; the fallback skips a FIDO2 key; a
   31-byte hash and an unknown algorithm answer `INVALID_PARAMS`.
3. Fix: `handleCosignRequest` only. The instrumented
   `RequestHandlerFido2AndCosignTest` cosign cases move to the new behaviour
   (its handler has no launcher, so a valid request now answers
   `BIOMETRIC_FAILED`); compiled with `compileDebugAndroidTestKotlin`.
4. Docs: `docs/co-signing/architecture.md` states the approval step, the key
   rule and an errors table for `cosign.request`.

## r2: co-sign peer from the caller session

Review P1: `requireConfirmedPeer` read the handler-wide
`connectedDevicePublicKeyHex`, which BLE, TCP and USB share and each clears
on its own teardown. Dropping USB or TCP made a still-confirmed BLE peer's
next co-sign answer `OPERATION_DENIED`, and one connection's confirmed
identity stood in for another's.

5. Failing tests in `CosignRequestHandlerTest`: a BLE and a USB connection
   confirmed on different peers, the USB one torn down, the BLE request
   still signs for its own peer; a request whose caller-session peer is not
   paired is denied though the global identity is confirmed.
6. Fix: when the request carries a `CallerSession`, its peer is the peer, and
   it counts as confirmed only when the paired-device store knows it; no
   fallback to the global field. Requests with no caller session keep the
   global field. The share and import methods use the same check.

## r3: one co-sign prompt at a time, settled by its own id

Review P1s: every co-sign launched its prompt at once through the shared
launcher; the single-top prompt activity reads its request only in
`onCreate`, so a second co-sign over a visible prompt was dropped and its
caller waited with no timeout. On a locked phone the notification opened
its own prompt (`cosign-<RPC id>`), which the launcher's numeric-id
receiver ignores, so answering it settled nothing.

7. Failing tests in `CosignRequestHandlerTest`: two overlapping co-signs
   (the second waits, then gets its own prompt and result; a late answer
   to the first settles nothing); a prompt never answered fails at its
   timeout and releases the next; a cancelled caller takes its prompt
   down; on a locked phone the notification carries the prompt's own
   intent and id, and approving or cancelling it settles the request.
8. Fix: `CosignApprovalPrompts` (protocol package) serializes co-sign
   prompts with a mutex, gives each a `cosign-<n>` id, fails at 60 s and
   dismisses on cancellation. `ActivityCosignPromptSurface` builds one
   prompt intent, starts it and, when locked, passes the same intent to
   `BiometricNotificationHelper` (new optional `promptIntent`); its own
   result receiver settles only that id. The launcher and the prompt
   activity are unchanged (row 178 rewrites the prompt queue there).

Left for row 178: a co-sign prompt and a launcher prompt (FIDO2, sign) can
still overlap, and a timed-out prompt stays on screen until dismissed (its
late answer is ignored).

## Out of scope

- Session-cached approval (every co-sign prompts).
- The initiator side (`CoSignActivity`) and `cosign.response`.
- Hash algorithms other than SHA-256, SHA-384 and SHA-512.
