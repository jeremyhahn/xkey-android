# Plan #177: cosign.request signs only after the owner approves

## Objective

`RequestHandler.handleCosignRequest` signed whatever hex `hash` a peer sent,
at once: no prompt, no confirmed-peer check, no digest-length check, and the
fallback key could be a FIDO2 credential. It is in the shared dispatch map,
so every transport reaches it. After this change it:

1. refuses a session with no confirmed peer (`OPERATION_DENIED`);
2. checks `hashAlgorithm` is known and `hash` decodes to exactly its digest
   length (SHA-256: 32 bytes); otherwise `INVALID_PARAMS`;
3. signs only with a `signing` key: a named key of any other type (FIDO2
   included) is `OPERATION_DENIED`, and the fallback never picks a FIDO2 key;
4. asks the owner on the phone through `BiometricActivityLauncher`, naming the
   first 8 hex characters of the hash; no launcher, a cancel or a failure is
   `BIOMETRIC_FAILED` and nothing is signed;
5. keeps the success result shape (`signature`, `keyFingerprint`,
   `algorithm`, `signerName`).

## Slices, in order

1. This plan.
2. Failing tests: `CosignRequestHandlerTest` (JVM, mocked database, keystore
   and launcher): approved prompt signs; cancelled prompt and null launcher
   answer `BIOMETRIC_FAILED` and never sign; no confirmed peer and a named
   FIDO2 key answer `OPERATION_DENIED`; the fallback skips a FIDO2 key; a
   31-byte hash and an unknown algorithm answer `INVALID_PARAMS`.
3. Fix: `handleCosignRequest` only. The instrumented
   `RequestHandlerFido2AndCosignTest` cosign cases move to the new behaviour
   (its handler has no launcher, so a valid request now answers
   `BIOMETRIC_FAILED`); compiled with `compileDebugAndroidTestKotlin`.
4. Docs: `docs/co-signing/architecture.md` states the approval step, the key
   rule and an errors table for `cosign.request`.

## Out of scope

- Session-cached approval (every co-sign prompts).
- The initiator side (`CoSignActivity`) and `cosign.response`.
- Hash algorithms other than SHA-256, SHA-384 and SHA-512.
