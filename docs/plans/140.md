# Plan: the phone sends remote.piv* (#140)

## Objective

SPEC remote-key-access covers PIV, but the phone never sends
`remote.pivListSlots`, `remote.pivGetCert` or `remote.pivSign`. This row
adds them to `RemoteKeyClient` using the wire shapes of go-xkms tag
`xkey/v0.64.2-alpha` (`pkg/pairingproto/protocol_piv.go`, served by
`xkey/pkg/pairing/bridge_piv.go`). It also shows the paired desktop's slots
on the PIV screen.

Wire (Go `[]byte` travels as standard base64):

| Method | Params | Result |
|---|---|---|
| `remote.pivListSlots` | `{backend?}` (no params when unset) | `{slots: [PIVSlotInfo]}` |
| `remote.pivGetCert` | `{slot, backend?}` | `{certificate_der, subject?, issuer?, expiry?}` |
| `remote.pivSign` | `{slot, data, algorithm?, backend?}` | `{signature, algorithm}` |

`PIVSlotInfo` is `{slot, label?, algorithm?, has_key, has_certificate,
cert_subject?, cert_expiry?}`. If the phone leaves `backend` out, the
desktop uses `software`.

## Slices, in order

1. **Client.** `RemoteKeyClient.pivListSlots()`, `pivGetCert(slot)` and
   `pivSign(slot, data)` go through `sendRequest`, so they use its shared
   request-id counter. Parsing is strict: a wrong type, a missing required
   field, or bad base64 or DER raises `ProtocolException`.
   Tests (`RemoteKeyClientPivTest`): method names and exact param key sets,
   omitempty behaviour, result parsing, one rejection per malformed shape,
   and a peer error code passing through.
2. **Desktop PIV source.** `DesktopPivSlots` (in `PivActivity.kt`) loads the
   desktop's slots. When no desktop is connected, or the desktop fails, it
   returns an empty list and never throws. `DesktopPivSlotActions` (in
   `PivSlotDetailActivity.kt`) fetches a slot's certificate and runs a test
   sign through `remote.pivSign`.
   Tests (`DesktopPivSlotsTest`): no client gives an empty list; a remote
   error gives an empty list; slots parse; a sign sends `remote.pivSign`.
3. **UI.** `PivActivity` binds `XKeyGattService` and shows a read-only
   "Desktop slots" section only when the desktop answers. A desktop slot
   card opens `PivSlotDetailActivity` in remote mode, which shows the
   certificate detail and a test-sign button. Remote mode has no generate,
   delete or import. The service gains `remoteKeyClient()`: one client per
   active transport, built the same way as the attestation path.
4. **Docs.** `docs/remote-key-access/architecture.md` lists the PIV methods.

## Round 2: verifier and review fixes

1. **Slot ids verbatim.** go-xkms slot ids are lowercase and case-sensitive.
   A desktop slot keeps the desktop's own id string from the list through
   `PivSlotDetailActivity` to `remote.pivGetCert` and `remote.pivSign`; it is
   never mapped onto the phone's `PivSlot`, so a slot outside that set still
   opens.
2. **Transport failures.** A missing session (`IOException`) while fetching
   the certificate or signing shows as a failure, like a desktop error.
   Cancellation still propagates.
3. **Request ids.** `RemoteKeyClient` takes its request-id counter from its
   router, shared by every client on that router. Device attestation uses the
   service's shared client.
4. **Session ready/lost.** `XKeyGattService.desktopSession` is the shared
   client while a desktop session is ready on any transport, and null once it
   is lost (the cached client is dropped too). The PIV list and the detail
   screen follow it: they load on connect and clear on disconnect.

The project has no Robolectric, so the screen logic sits in plain functions
(`desktopPivSlots`, `desktopPivSlotDetail`, `DesktopPivSlotActions.trySignTest`),
which `DesktopPivSessionTest` drives with a scripted desktop.

Result: `make test` (`./gradlew testDebugUnitTest`) passed on 2026-11-12 (BUILD SUCCESSFUL) at the round-2 fix commit.

## Round 3: pre-push review fixes

1. **Blank slot ids.** `pivListSlots` rejects a blank or whitespace-only slot
   id with `PARSE_ERROR`; valid ids stay verbatim. The detail screen and the
   test sign treat the client refusing a slot id (`IllegalArgumentException`)
   as a failure, not a crash. Cancellation still propagates.
2. **USB session state.** The USB transport counts as a desktop only while
   `UsbAccessoryServer.state` is `Connected`. The service follows that state,
   so the client is published on Connected and dropped when the session ends,
   detached or not, and the PIV screens reload or clear with it. The cache
   and publication live in `DesktopSessionTracker` (in `XKeyGattService.kt`),
   which `DesktopSessionTrackerTest` drives without a service.

Result: `make test` (`./gradlew testDebugUnitTest`) passed on 2026-11-12
(BUILD SUCCESSFUL, 2184 tests, 0 failures) at the round-3 fix commit.

## Out of scope
