# Plan: the phone sends remote.piv* (#140)

## Objective

SPEC remote-key-access covers PIV, but the phone never sends
`remote.pivListSlots`, `remote.pivGetCert` or `remote.pivSign`. This row
adds them to `RemoteKeyClient` using the wire shapes of go-xkms tag
`xkey/v0.64.2-alpha` (`pkg/pairingproto/protocol_piv.go`, served by
`xkey/pkg/pairing/bridge_piv.go`). It also shows the paired desktop's slots
on the PIV screen.

Wire (Go `[]byte` travels as standard base64):

| Method | Params | Result |
|---|---|---|
| `remote.pivListSlots` | `{backend?}` (no params when unset) | `{slots: [PIVSlotInfo]}` |
| `remote.pivGetCert` | `{slot, backend?}` | `{certificate_der, subject?, issuer?, expiry?}` |
| `remote.pivSign` | `{slot, data, algorithm?, backend?}` | `{signature, algorithm}` |

`PIVSlotInfo` is `{slot, label?, algorithm?, has_key, has_certificate,
cert_subject?, cert_expiry?}`. If the phone leaves `backend` out, the
desktop uses `software`.

## Slices, in order

1. **Client.** `RemoteKeyClient.pivListSlots()`, `pivGetCert(slot)` and
   `pivSign(slot, data)` go through `sendRequest`, so they use its shared
   request-id counter. Parsing is strict: a wrong type, a missing required
   field, or bad base64 or DER raises `ProtocolException`.
   Tests (`RemoteKeyClientPivTest`): method names and exact param key sets,
   omitempty behaviour, result parsing, one rejection per malformed shape,
   and a peer error code passing through.
2. **Desktop PIV source.** `DesktopPivSlots` (in `PivActivity.kt`) loads the
   desktop's slots. When no desktop is connected, or the desktop fails, it
   returns an empty list and never throws. `DesktopPivSlotActions` (in
   `PivSlotDetailActivity.kt`) fetches a slot's certificate and runs a test
   sign through `remote.pivSign`.
   Tests (`DesktopPivSlotsTest`): no client gives an empty list; a remote
   error gives an empty list; slots parse; a sign sends `remote.pivSign`.
3. **UI.** `PivActivity` binds `XKeyGattService` and shows a read-only
   "Desktop slots" section only when the desktop answers. A desktop slot
   card opens `PivSlotDetailActivity` in remote mode, which shows the
   certificate detail and a test-sign button. Remote mode has no generate,
   delete or import. The service gains `remoteKeyClient()`: one client per
   active transport, built the same way as the attestation path.
4. **Docs.** `docs/remote-key-access/architecture.md` lists the PIV methods.

## Out of scope

- SPEC.md, the go-xkms side, `RemoteSyncClient`, `RemoteBackupClient`.
- Wire changes beyond the three methods above.
- Choosing a desktop backend in the UI (the desktop default is used).
- Generating keys or importing certificates in desktop slots.
