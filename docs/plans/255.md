# Plan 255: SPEC row key-sharing

## Objective

Row `key-sharing` of docs/SPEC.md: `local.sharePublicKey`,
`local.shareSymmetric`, `local.importSharedKey`; per-key, per-peer sharing
policies managed from the key detail screen. One branch, one PR that closes
#255 and leaves the row `shipped` in docs/SPEC.md.

The row already reads `shipped` on main. The open work is the folded items:

- #193 (PR #211, branch `row/193-grant-order`): grants, withdrawals and
  key-wide clears apply in user-action order, through one KeyPolicyStore.
- PR #215 (branch `row/174-unpair-drops-grants`): follow-up to the unpair
  grant cleanup, held for #211.

5. Merge main (#239, #206, #165, #263) and fit its new tests to the store:
   HmacEcdhAuditTest and PerSessionApprovalReattachTest stub KeyPolicyDao,
   and HmacEcdhAuditTest passes a per-peer connection id.
6. `make test` (testDebugUnitTest) passes on the tip.
7. Lane-verify review fixes, each a class fix with a bypass test:
   - A crypto call made after an approval prompt rechecks the key under the
     delete lock (`KeyPolicyStore.withUsableKey`): SignAfterDeleteTest.
   - An unreadable Ed25519 store refuses the delete, and a failed prefs
     commit keeps the tombstone owed: KeyDeletionMaterialTypesTest.
   - The per-key material locks are reference counted, so ids chosen by a
     peer leave nothing behind: KeyMaterialLockTest.
   - The app's own Keystore aliases are listed as system keys, and every UI
     delete goes through `deleteUserKey`, which refuses an internal key
     instead of crashing: UserKeyDeleteTest.
   - docs/SPEC.md is back to main's text (slice 4).
8. Lane-verify round 2 fixes:
   - A credential and a general key sharing an id: a delete names one of
     them (`UserKeyKind`); its generation and tombstone hold only that
     key's aliases, and a delete of the key without the row keeps the other
     key's row (`deleteMaterial(besideRow)`), replayed, never dropped:
     KeyDeletionMaterialTypesTest, KeyPolicyStoreTest, UserKeyDeleteTest.
   - An Ed25519 delete counts only a commit() that returns true, even when
     the prefs cache already shows the entry gone: repeated failed replays
     and a restart keep the tombstone owed (KeyDeletionMaterialTypesTest).
   - The Credential Provider assertion, file signing, co-signing and media
     auto-signing sign inside `withUsableKey`: AssertionSignCountTest, with
     a sweep of every user key signature.
9. Lane-verify round 3 fixes. PR #211's head (88ba5bb) was already merged:
   - local.setKeyPolicy decides "already at that policy" in its own turn
     in the edits queue (`KeyPolicyStore.setPolicy`), not before it, so a
     sheet edit queued ahead of it never lands over it:
     SetKeyPolicyHandlerTest.
   - A user delete's kind is resolved against the material under the id
     (`KeystoreManager.presentKind`, inside `keyMaterialGeneration`): a
     fido2-typed key that `local.generateKey` put under the general alias is
     deleted: KeyDeletionMaterialTypesTest.
   - No delete replaces a tombstone that still owes material
     (`noTombstoneOwed`, used by `deleteKey` and `deleteMaterial`): it is
     settled first, and while it stays owed the new delete is refused:
     KeyPolicyStoreTest.
10. Lane-verify round 4 fix: a delete that follows a settled earlier
    delete of its id is a retry (`noTombstoneOwed`), and a retry deletes
    only the key it names (`keyMaterialGeneration(retry)`, the one place a
    delete's namespace is chosen): a credential's retry beside a general
    key's row never falls through to that general key:
    KeyDeletionMaterialTypesTest.
