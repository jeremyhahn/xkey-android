# Plan 255: SPEC row key-sharing

## Objective

Row `key-sharing` of docs/SPEC.md: `local.sharePublicKey`,
`local.shareSymmetric`, `local.importSharedKey`; per-key, per-peer sharing
policies managed from the key detail screen. One branch, one PR that closes
#255 and leaves the row `shipped` in docs/SPEC.md.

The row already reads `shipped` on main. The open work is the folded items:

- #193 (PR #211, branch `row/193-grant-order`): grants, withdrawals and
  key-wide clears apply in user-action order, through one KeyPolicyStore.
- PR #215 (branch `row/174-unpair-drops-grants`): follow-up to the unpair
  grant cleanup, held for #211.

    - ui/CoSignActivity.kt `generateInitiatorQR` and `signAsWitness`: the

      The `else keyId` fallback for the owner fingerprint is removed from

    - ui/KeyDetailActivity.kt `exportPublicKey`: `orRefuse`

13. Verify r4: a key record that cannot be attributed is unreadable, and a
    refused co-sign QR leaves no QR on screen.
    - crypto/SoftwareKeyStore.kt: one reading of a record's id (`recordId`):
      a non-empty string keyId, or none. It is used by the presence probe,
      the key read (`get`) and the migration. Material beside metadata that
      is missing, `{}`, has no keyId, an empty or non-string keyId, or
      cannot be parsed is `UNREADABLE` for every id. Under the id's own file
      name, metadata naming another id is `UNREADABLE` too (`recordOf`).
      Before, a legacy `{}` read as no key, so `exportKind` picked a
      credential of the same id and shared it under the software key's
      grants. `get` refuses when only such a legacy record is there. A
      well-formed legacy record naming another id is that id's record (the
      migration moves it there), so it stays absent for this id.
    - ui/CoSignActivity.kt: `clearInitiatorQR` runs before every Generate QR
      attempt and on every key-spinner change.
    - Tests: LegacyRecordInvariantTest covers every shape at both file names,
      through the presence probe, `exportKind`, `readShareable` (the read
      that `local.importSharedKey` uses) and `get`.
      CoSignInitiatorQrRefusalTest `aRefusalAfterASuccessLeavesNoQrVisible`
      covers a successful QR followed by a refused one, and a key change.
    - This brings back the fail-closed brick the plan accepts: once one
      unattributable legacy record exists, every software key read refuses.
      If that is refused in turn, the fallback is to drop legacy migration.

14. Verify r5: a legacy record named like a digest, and a delete whose
    material unlink fails.
    - crypto/SoftwareKeyStore.kt: whether a record has been migrated now
      depends on the id its metadata names, not on what its file name
      looks like. A record has been migrated when its name is the digest of
      that id. An older build kept a 64-hex id as its own file name; that
      record now migrates and reads. A hex name that is neither the id nor
      its digest contradicts its metadata. It is not moved (`migratable`),
      and it stays unreadable for the id whose digest it is. The migration
      moves the metadata only once the material has moved.
    - `delete` unlinks the material first and removes the metadata only
      once the material is gone. A failed unlink leaves the record whole.
    - Departure from item 13: material with no metadata under an id's own
      digest name is now `PRESENT` for that id, not `UNREADABLE`. That
      record holds the id, so no credential stands in for it. `get` refuses
      to read it. The delete's replay can now finish it. Before, the
      replay's presence checks threw before the unlink was retried.
    - Tests: LegacyRecordInvariantTest
      `aLegacyRecordNamedLikeADigestIsMigratedAndRead`, plus a source guard
      that there is one record-id read and no shape-based skip.
      SoftwareKeyDeleteReplayTest covers a failed material unlink, and
      material-only and metadata-only leftovers, each replayed to a
      complete delete.
