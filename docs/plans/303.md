# 303: retry the toolchain image's Gradle dependency download

## Objective

The toolchain image's `warm` stage runs one Gradle build to fill the
dependency cache. A single transient repository failure (an artifact that
cannot be resolved from Google Maven, Maven Central or the plugin portal)
failed that build, the image build, and so main. Retry the download at one
place, bounded, and keep the build failing closed when the failure persists
or is not a download failure.

## Slices, in order

1. Test first: `scripts/gradle-retry-test.sh`, wired as `make gradle-retry-test`
   and a `lint-gates` prerequisite.
   - static: the warm stage's Gradle run goes through `gradle-retry`; no bare
     `gradle ... assembleDebug` run remains; copies of the Dockerfile without
     the retry (the RUN or the script) fail the check.
   - behaviour: the `gradle-retry` script, extracted from the Dockerfile's
     heredoc, against a stubbed `gradle` and `gradle-quiesce` on PATH:
     a resolution failure then success passes; every attempt failing fails
     after exactly the bound and prints the log tail; no attempt after a
     success; a non-resolution failure (a failing test) is not retried.
     Mutants of the script (bound removed, fail-open on the last attempt,
     every failure retried) are caught.
   - it fails on the Dockerfile before the fix.
2. Fix: a `/usr/local/bin/gradle-retry` heredoc in the warm stage (3 attempts,
   15 s then 30 s backoff, `gradle-quiesce` between attempts, retrying only
   on a log that says `Could not resolve` / `Could not GET` / `Could not HEAD`
   / `Could not download`); the warm RUN calls it; the stage comment says
   what is retried.

## Out of scope

- Gradle's internal repository retry properties.
- Any workflow change; CI already runs `make lint-gates`.
- The apt retries, index sums and image tag logic (unchanged; the tag moves
  with the Dockerfile as it always does).
