# Plan 195: a cut-short backup record is a failure, not an absent backup

## Objective

`BackupStore` promises that an unreadable backup is never treated as absent
(docs/SPEC.md: desktop backups round-trip). A record whose header is whole but
whose body is cut short breaks that today: `latestId()` skips it and returns an
older backup, `load()` returns null ("Backup not found"), and `store()` writes
the record in place, so a crash mid-write leaves exactly such a record.

## Design

- `decodeRecord` keeps returning null for a file that is not a record (shorter
  than a magic, unknown magic) and throws `IOException` for a record with a
  known magic that is cut short: header shorter than its fixed size, a negative
  id length, or an id length past the end of the file.
- `latestId()` still filters by `readHeader`, so a record whose `XKB2` header
  (sequence and created-at) is cut short is skipped as today; a record whose
  header reads but whose id does not decode makes it throw.
- `load(id)` throws on such a record instead of returning null.
- `store()` (and the legacy migration) write the record to a temp file in the
  same directory (`.<sha256>.backup.tmp`), sync it, and rename it over the
  record. A failed write deletes the temp file and leaves the earlier record.
  The temp name never matches the record pattern, and migration deletes stray
  temp files left by a crash instead of migrating them as legacy blobs.
- A test seam: an internal `writeFile` property that writes bytes to a file.
