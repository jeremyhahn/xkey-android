# 161: BLE client tests wait on signals, not settle sleeps

## Objective

The BleClient test classes stop sleeping. Every `Thread.sleep` (settle
windows and poll loops alike) becomes a bounded wait on something the fake
stack or the client signals, with a timeout that fails the test. Each test
keeps its assertions. No production code changes.

## The signals

- **The harness monitor.** `BleClientHarness` notifies one monitor whenever
  the fake stack takes a write, closes a GATT object, or the client's inbound
  consumer takes an event. `awaitUntil(what) { ... }` re-checks its condition
  on each notification and fails at its timeout. It replaces every poll loop
  in the harness and in the test classes.
- **Inbound events taken.** The harness counts the events the client's
  single inbound consumer takes, through the existing `inboundFragmentHook`
  seam. Tests that paused the consumer chain onto it (`onInboundEvent`).
- **Inbound handled.** `awaitInboundHandled(n)` notifies one fragment too
  short to carry a header, which the consumer drops without touching any
  state, and waits for the consumer to take event n + 1: the consumer is
  single, so the first n are then fully handled. A test reads the count
  before it queues its events. This is the idle check that replaces the
  settle windows. Where the connection has ended and nothing can be
  notified, the test waits for the disconnect event queued behind its
  fragments instead.
- **Connection state.** `awaitConnectionState` collects `connectionState`
  instead of polling it.
- **Synchronous paths.** Where the event under test is handled on the test
  thread (`handleCompleteMessage`, the stack's disconnect callback), the
  outcome is checked directly once the call returns, on the waiter the bug
  would have taken (`pendingResponse`).

## Slices, one commit per class

1. Harness: the monitor, the counters and the helpers; its own four poll
   loops (`awaitResponses`, `holdWriteOpen`, `awaitWritesAcked`, fragment
   pacing in `deliver`) wait on the monitor.
2. BleClientCallbackTest: three 50 ms settles become a drain or a direct
   check.
3. BleClientEventOrderTest: both `SETTLE_MS` windows go.
4. BleClientInboundConnectionTest: the 50 ms settle becomes a direct check.
5. BleClientPhoneInitiatedAttestTest, BleClientStaleCallbackTest,
   BleClientTeardownTest: the poll helpers go.

Each class runs 20 times in a row before its commit.

## Out of scope

- BleClientPhoneInitiatedSasTest (row 158) and every GattServer* test
  (row 160).
- Production code under `app/src/main/`.
- The one wait with no signal: a thread blocking on a lock
  (`aDisconnectWaitsForAWriteAlreadyAdmittedToTheConnection`) has no event
  to wait on, so it spins on the thread's state with `Thread.yield`, bounded
  by a deadline, instead of sleeping.
