# #152: local.oathAdd encodes its otpauth URI and returns the stored id

Row branch `row/152-oath-add-encoding`, a follow-up of #133.

## Objective

`RequestHandler.handleOathAdd` (local.oathAdd) has two defects:

1. It builds `otpauth://<type>/<issuer>:<account>?secret=...&issuer=<issuer>`
   by string concatenation with no encoding. An issuer or account holding a
   space, `:`, `&`, `?`, `#` or `/` makes `OathRepository.importFromUri`
   parse the wrong account, truncate the issuer or drop the secret.
2. It returns the caller's `name` as `credential_id`, but `importFromUri`
   stores the credential under the id it returns. That id is the `name`
   local.oathList reports and the `credential_id` local.oathGenerate and
   local.oathRemove accept, so a caller using the returned id misses it.

## Slices, in order

1. Test commit: `OathAddHandlerTest` (JVM + MockK, `OathRepository` mocked
   by constructor) pins the URI handed to `importFromUri` and the reply's
   `credential_id`. Before the fix the three encoding cases and the
   `credential_id` case fail; the counter and INVALID_PARAMS cases pin
   behaviour that was already right.
   - `issuer and account with reserved characters are percent-encoded`
   - `non-ASCII issuer and account are percent-encoded as UTF-8`
   - `a missing issuer leaves the label prefix and issuer parameter out`
   - `a TOTP add passes no counter`
   - `a HOTP add passes the request counter`
   - `a HOTP add without a counter passes counter 0`
   - `credential_id is the id importFromUri returned`
   - `missing credential fields still return INVALID_PARAMS`
2. Fix commit: `handleOathAdd` calls the internal
   `com.automatethethings.xkey.sync.otpauthUri` (the builder
   `SyncEngine.mergeOath` uses; counter non-null only for HOTP) and returns
   the id `importFromUri` returned.
3. Docs commit: docs/oath/architecture.md describes the encoded URI and the
   stored id as `credential_id`.

## Review round 1: one choke point for app-built URIs

The fix above built the URI with `otpauthUri` but imported it with the
external-label parser (`structuredLabel = false`), so an issuerless
account `host:user` (label `host%3Auser`) was stored as issuer `host`,
account `user`.

4. Test commit: `OathAddHandlerTest` runs the real `OathRepository`
   (recording DAO, `Uri.parse` backed by `java.net.URI`) and asserts what is
   stored: `an issuerless account with a colon is stored whole` fails before
   the fix; `an issuer and account with colons are stored whole` and the
   stored-id case pin the rest.
5. Fix commit: `OathRepository.importStructured` takes the issuer, account
   and parameters, builds the URI with `otpauthUri` and reads its label on
   the structured path; `importFromUri` takes no `structuredLabel` and is the
   external-import path only (QR scan). local.oathAdd, `SyncEngine.mergeOath`
   and manual entry (OathActivity) call `importStructured`. `otpauthUri`
   also percent-encodes the secret and algorithm, as manual entry's builder
   did. A JVM `OathRepository` test pins both paths.
6. Docs: docs/oath/architecture.md names the two import paths.

## Out of scope

- `manualOtpauthUri` (OathLabel.kt) and its test stay; manual entry no
  longer calls it.
