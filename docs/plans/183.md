# 183: the devcontainer proof step races a surviving JVM

## Objective

Main went red at e8469ae: the devcontainer image build failed in the warm
stage's last step (the offline proof build) with

    rm: cannot remove '/tmp/proof-home/caches/modules-2': Directory not empty

The proof build finished, then `rm -rf /tmp/proof-home` raced a process that
was still writing under that Gradle user home.

## Cause

`gradle --no-daemon` does not mean "no background JVM":

- `org.gradle.jvmargs` in gradle.properties differs from the client JVM's, so
  the client forks a single-use build daemon. The client returns when the
  build result arrives; the daemon then closes its caches (lock release,
  cache cleanup under `caches/modules-2`) and only then exits.
- The Kotlin Gradle plugin's default execution strategy starts a separate
  Kotlin compile daemon, which outlives Gradle by its idle timeout.

Either one can still be writing into `caches/` while `rm -rf` walks it; rm
deletes a directory's entries, a new entry appears, and rmdir fails with
ENOTEMPTY. The warm step has the same shape: it copies `caches/modules-2`
right after its gradle run, so it can copy a cache mid-cleanup.

## Fix (one slice: build/docker/devcontainer/Dockerfile)

1. Both warm-stage gradle runs (warm and proof) pass
   `-Pkotlin.compiler.execution.strategy=in-process`: Kotlin compiles in the
   build daemon and no Kotlin daemon is started.
2. A `gradle-quiesce` helper (a COPY heredoc in the warm stage, so the
   toolchain tag hashes it with the Dockerfile) runs after each gradle run and
   before its cache is copied or deleted: `gradle --stop`, then it waits for
   every `java` process in the step to exit, sends TERM at 10 s and KILL at
   20 s, and fails the image build if one survives 30 s.
3. No other Dockerfile under build/docker runs gradle (only the devcontainer
   Dockerfile has a gradle step), so nothing else changes.

## Tests

The image build is the test: `make docker-build-toolchain` (the target the
CI Devcontainer job calls; `docker-build-it` builds the integration stage on
the same base) twice, the warm and proof steps passing both times.

## Results

- This lane's container has no Docker daemon or CLI, so neither image build
  could run here; CI's Devcontainer job builds the image on the pull request.

## Out of scope

- gradle.properties (the daemon jvmargs the gates use at run time).
- The run-time gates in the image, which run with the ro cache and
  `GRADLEW="gradle --no-daemon"` and delete no Gradle home.
