# #320: pairing prompt host

## Objective

A desktop that completes the Noise handshake while the app is in front must
get the pairing confirmation dialog, not a silent "pairing rejected by user".
The same lookup guards every biometric prompt in the request handler, so the
fix covers those too. With no visible activity the request is still refused:
no dialog from a background context, no auto-accept.

## Root cause

Only MainActivity registered itself with the service (`setActivity`), and
every MainActivity instance cleared the service's reference in its own
onPause/onDestroy, whichever instance was held. A second MainActivity
instance (for example from the foreground notification, whose intent starts
MainActivity over another screen) is destroyed after the first instance's
onResume, so its onDestroy clears the reference the first one just set: the
first instance is resumed and focused, the service has its one binding, and
the reference is null. Any other screen in front (OATH, PIV, Settings, ...)
never registered at all.

## Slices

1. Failing unit tests (Robolectric), `PromptActivityTrackerTest`:
   - the recreate order (new.onResume, then old.onPause/onDestroy) leaves the
     new activity as the host, and the service's pairing confirmation shows
     the dialog on it;
   - a non-Main FragmentActivity in front hosts the dialog;
   - no resumed activity: the pairing confirmation is refused;
   - a source guard: no main code calls `setActivity(`, and every
     "No activity available" lookup goes through the prompt host.
2. Fix: `ui/PromptActivityTracker`, one app-wide tracker of the resumed
   FragmentActivity, registered by XKeyApplication. It clears on pause or
   destroy only when the activity going away is the one it holds.
   XKeyGattService.showPairingDialog and the five RequestHandler biometric
   lookups ask it. MainActivity no longer calls `setActivity`; the service
   and handler keep `setActivity` only as a test hook that pins a host.
3. Device test: the pairing confirmation through the service, with the
   activity in front and nothing registered, shows the dialog; a secondary
   screen in front does too.

## Out of scope

- Raising the prompt from the background (a notification or full-screen
  intent) when no activity is visible: still refused.
- Any change to the pairing protocol itself.
