# Plan: remote OATH client (#141)

## Objective

Let the phone store an OATH credential on the paired desktop
(`remote.oathAdd`) and show the current code of a desktop-stored credential
(`remote.oathGenerate`), using the go-xkms wire shapes in
`pkg/pairing/protocol_oath.go` at tag `xkey/v0.64.2-alpha`. No SPEC.md change
and no other wire change.

## Slices

1. `RemoteOathClientTest`: params shape (`credential` object; `credential_id`),
   go `omitempty` handling, escaping, secret zeroing (caller chars and body),
   validation before send, strict result parsing (wrong types, missing fields,
   `success: false`, non-digit code, string/negative/fractional `expires_in`),
   desktop error and timeout, shared request-ID counter, Base32 vectors.
2. `remote/RemoteOathClient.kt` until slice 1 passes. IDs from a companion
   counter above 5,000,000 (no cross-client counter exists; the others use
   1M-4M).
3. `OathDesktopActionsTest`: copy sends `remote.oathAdd` and stores the
   desktop ID; desktop code sends `remote.oathGenerate` and returns code plus
   expiry; no desktop: no menu entries, nothing sent.
4. `OathDesktopActions` (in `ui/OathActivity.kt`), context-menu entries,
   code dialog, strings in `strings_oath.xml`. The activity binds
   `XKeyGattService` without auto-create; a small
   `XKeyGattService.remoteOathClient()` accessor (outside the file map) hands
   out a client on the active transport.
5. `docs/remote-key-access/architecture.md` lists both methods; `make test`.
6. Review fixes. Desktop links are keyed by the desktop's Noise-authenticated
   static key plus the phone oathId, so a link made on desktop A is neither
   offered nor queried on desktop B, and a copy to B keeps A's link
   (`OathDesktopActionsTest`). Each server hands out a `ConnectedDesktop`
   (peer key, sender, router) only for an established session; USB requires
   `UsbAccessoryState.Connected`, so a handshaking, refused or ended accessory
   offers no desktop action and Copy never decrypts the secret
   (`UsbConnectedDesktopTest`).
7. Session binding (ruling 554). A `ConnectedDesktop` sender is bound to the
   connection that authenticated its key: it sends on that connection's
   session and fails with `IOException` once that connection ends or another
   peer replaces it, never re-resolving the transport's current session.
   All four `remote.*` clients take only a `ConnectedDesktop`;
   `XKeyGattService.activeTransport()` is gone. Tests, committed failing
   first: a peer swap between capture and send on TCP
   (`TcpConnectedDesktopBindingTest`, with copy and desktop code), USB
   (`UsbConnectedDesktopTest`) and BLE (`GattServerBoundSenderTest`); the
   oathAdd secret and body zero while the reply is pending
   (`RemoteOathClientTest`); a reflective sweep over the clients, the
   transports and the service (`ConnectedDesktopBindingTest`). The
   instrumented selection tests use a real USB session over a socket pair.
8. Code expiry (ruling 554). `Outcome.Code` carries only a
   `DesktopCodeDeadline` started from `expires_in` on an injectable monotonic
   clock when the reply arrives; `view()` is the one way to read the code and
   returns `Expired` (code dropped) at zero. The dialog re-renders on each
   second change and shows the code expired while still open. Tests, failing
   first, on a fake clock (`DesktopCodeDeadlineTest`): expires_in 2 shows no
   code after 2 s; a reflective check that neither type hands out the code.

## Out of scope

- Listing or deleting desktop credentials (`remote.oathList` etc.).
- Marking synced credentials as desktop-stored: the desktop ID is known only
  from an oathAdd reply made on this phone.
- Any change to RemoteKeyClient, RemoteSyncClient, RemoteBackupClient or SPEC.md.
