# Plan: key algorithm parity with the desktop (#333)

## Objective

The desktop can ask for keys the phone cannot make, and a `local.generateKey`
RSA request with `keySizeBits` is answered with the size the hash implies.
Close those gaps. Post-quantum algorithms are out of scope.

## Slices (each: test commit, then fix commit)

1. PIV RSA 3072/4096 and desktop spellings
   - `PivAlgorithm` gains `RS3072` and `RS4096`, and every value carries its
     PIV algorithm id (ECC P-256 0x11, ECC P-384 0x14, RSA 2048 0x07,
     RSA 3072 0x05, RSA 4096 0x16; Yubico PIV algorithm table).
   - PIV keys are generated in the Keystore TEE at the enum's size; PIV never
     requests StrongBox, so nothing changes for 3072/4096 there.
   - `PivAlgorithm.fromWireName` (moved out of the handler so it can be
     tested) accepts ECCP256, ECCP384, RSA3072, RSA4096, RSA-3072, RSA-4096
     next to the existing names. An unknown name is already
     `INVALID_ALGORITHM`; that stays.
   - The PIV generate dialog lists `PivAlgorithm.entries`, so it shows them.
   - Tests: `PivSlotTest` (ids, sizes), `PivAlgorithmsTest` (spellings map to
     the same values, unknown is null), `PivKeyManagerTest` (an RS4096
     generate asks the Keystore for 4096 bits and never StrongBox).
2. `local.generateKey` honours `keySizeBits`
   - `LocalGenerateKeyParams` reads `keySizeBits` (0 or absent = not given).
   - RSA: the modulus comes from `keySizeBits` (2048, 3072, 4096), from the
     hash only when absent; any other size is `INVALID_PARAMS`. Other
     algorithms: a `keySizeBits` that differs from the algorithm's size is
     `INVALID_PARAMS`, never a key of another size.
   - `KeystoreManager.generateKeyForAlgorithm` takes the size; StrongBox is
     requested only for RSA 2048 and EC P-256 (the sizes StrongBox
     guarantees); the TEE fallback rules are unchanged.
   - Tests: `LocalGenerateKeySizeTest` (RS256 + 4096 parses to 4096; bad sizes
     refused), `KeystoreCapabilitiesTest` (size resolution).
3. Key Management screen: P-521 (TEE), RSA 3072, RSA-OAEP 3072, AES-192,
   HMAC-SHA384, in a pure `KeyCreationAlgorithms` list; Keystore gains
   AES-192 and HMAC-SHA384 generation and HMAC-SHA384 compute.
   - Tests: `KeyCreationAlgorithmsTest`.
4. `local.getCapabilities` lists AES192 and HMAC-SHA384 (ES512 and
   RS256/384/512 are listed already; RSA sizes are reached through
   `keySizeBits`, which has no list entry in the existing format).
   - Tests: `KeystoreCapabilitiesTest`.
5. Docs: PIV algorithm table and wire names in `docs/piv/architecture.md`,
   a SPEC.md row and a ROADMAP.md entry for key-algorithm-parity.
6. Device tests follow the new support (review finding)
   - Rejection fixtures move to inputs the code still refuses: AES-512 in
     `KeystoreManagerGeneralKeysTest` (message "128, 192 or 256"), EdDSA
     through `local.generateKey` in `RequestHandlerErrorPathTest`
     (`INVALID_ALGORITHM`).
   - `KeystoreManagerGeneralKeysTest` gains an AES-192 encrypt/decrypt round
     trip and an HMAC-SHA384 MAC (48 bytes, deterministic). Both are plain
     Keystore features since API 23, so no capability skip is needed.
7. RSA size through the RPC, size read off the key made (review finding)
   - `LocalGenerateKeyRsaSizeHandlerTest` drives the real handler: RS256 at
     3072/4096 forwards the size, returns and stores it, and the public key
     has that modulus; a keystore that ignores the size gives
     INTERNAL_ERROR, the key is deleted and no row is written. Device tests
     in `RequestHandlerLocalKeyFamilyTest` make RS256 3072/4096 keys.
   - One reader, `crypto/PublicKeySize.kt` (`publicKeySizeBits`, tested by
     `PublicKeySizeTest`), used by the handler and Key Management.
   - The RS256 tests read the key from `publicKeyDer`, the field the
     `local.generateKey` result carries (SPEC hardware-backed-keys row);
     reading `publicKey` threw JSONException. The device test
     `assertRsaKeyOfSize` in `RequestHandlerLocalKeyFamilyTest` now reads
     `publicKeyDer` too. A sweep of every test that reads `publicKey` or
     `publicKeyDer` from a result found no other mismatch: the other readers
     take `publicKey` from `generateKey`, `loadKey`, `local.getPublicKey` and
     `local.pivGenerateKey`, which all emit that name.
   - The Key Management device tests pick algorithms by displayed name
     through one helper, `selectSpinnerItemByText`, and expect the lists
     `KeyCreationAlgorithms` builds; a sweep of every spinner pick by position
     in androidTest found none other from a list this row changed.

## Out of scope

Post-quantum algorithms; PIV security-level read-back (the PIV code reports
no level today); exportable asymmetric keys.
