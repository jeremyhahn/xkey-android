# #232 Audit the TCP pairing and native USB toggles

## Objective

Turning on the loopback TCP pairing server or native USB accessory mode
opens a path to the pairing responder, yet neither toggle leaves an audit
entry, unlike the biometric and media-signing settings. After this row,
every change of either toggle records one `SETTINGS_CHANGED` audit entry
(`setting` = `tcpPairing` / `nativeUsb`, with old and new values). Writing
the value already stored records nothing.

## Slices, in order

1. Plan (this file).
2. Failing JVM tests, `usb/UsbHsmSettingsAuditTest`, on a file-backed
   Preferences DataStore (`PreferenceDataStoreFactory` over a
   `TemporaryFolder` file), capturing entries from a mock `AuditLogDao`
   the way `AuditLoggerDispatchTest` does:
   - enable then disable TCP pairing: two entries, `tcpPairing`,
     false -> true then true -> false;
   - the same for `nativeUsb`;
   - writing the stored value records nothing (both settings).
   `UsbHsmSettingsRepository` has no DataStore constructor parameter yet,
   so this slice adds one the way `PinSettingsRepository` does: an
   internal primary constructor taking the DataStore and a public
   secondary constructor taking the `Context`. Callers are unchanged.
3. Fix: `setNativeUsbEnabled` and `setTcpHsmEnabled` read the old value
   and, only when it changes, call `AuditLogger.logSettingsChanged`.
   Setter signatures are unchanged.
4. Docs: `docs/tcp-pairing/architecture.md` and
   `docs/usb-transport/architecture.md` say the toggle is audited.

## Out of scope

- `ui/SettingsActivity.kt` switches (they keep calling the setters).
- androidTest helpers that call `setTcpHsmEnabled(true)`: AuditLogger
  drops entries when not initialized, so they keep working.
- Auditing other settings repositories.
