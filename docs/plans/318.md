# 318: PIN lockout and audit row, unit tests green

## Objective

The row branch moved the vault lockout onto an injected monotonic clock,
moved OATH audit rows into `OathRepository`, and records every policy
refusal once in the dispatcher. Five JVM unit tests fail at the branch
head; this slice makes them pass without weakening any assertion. A second
slice keeps secret dialogs off screen capture and closes three audit gaps.

## Slices, in order

1. Test: `PolicyDeniedAuditTest` gains a case where a refusal on a served
   connection that authenticated no peer writes no POLICY_DENIED row.
2. Fix: `RequestHandler.auditPolicyDenied` takes its peer as
   `val callerPeer = currentPeerPublicKeyHex()` and writes no row when the
   request carries a `CallerSession` but no peer.
3. Test setup: `SyncEngineMergeOathTest`, `PasswordStoreMethodsTest`,
   `UsbWireContractTest` and `PasswordSyncTest` stub what the branch reads.
4. Secret dialogs: every dialog in a UI file with a password-type input,
   and the OATH secret entry, is shown through `SecureScreens.show`.
   Tests: one FLAG_SECURE case per PIN dialog in
   `PinManagementActivitySecureTest`; `SecureDialogSourceGuardTest`
   counts builders against `SecureScreens.show` calls per guarded file.
5. Audit deletion: clear and delete-older run as one Room transaction with
   their AUDIT_LOG_CLEARED / AUDIT_LOG_PRUNED row
   (`AuditLogDao.deleteAllAndRecord` / `deleteOlderThanAndRecord` behind
   `AuditLogger.clearAuditLog` / `pruneAuditLog`). Tests: commit and
   rollback cases in `AuditLogDaoTest`; `AuditDeletionChokePointTest`
   source guard.
6. Returned denials: `dispatch` audits OPERATION_DENIED from the response
   it returns, so thrown and returned refusals write one POLICY_DENIED row
   each. The two returned refusals, co-sign with a key that is not a
   signing key and import of a key not shared with the peer, each write
   exactly one; the import refusal also keeps its failed KEY_EXPORTED row.
   Tests: the co-sign case in `PolicyDeniedAuditTest`; the import case in
   `KeyShareAuditTest` (`aPolicyRefusalRecordsOneFailedExport`,
   `aRefusedHardwareExportRecordsTheStoredKeyType`), whose `single(type)`
   now counts entries of that type.
7. Review fixes. A prompt that accepts the screen lock (the audit log's
   deletion confirmation) asks for BIOMETRIC_WEAK | DEVICE_CREDENTIAL on
   Android 9 and 10, which refuse BIOMETRIC_STRONG with it; one
   `BiometricHelper.promptAuthenticators` chooses every prompt's
   authenticators. A phone copy of an OATH code gets its code from
   `OathRepository.generateCode` by oathId, so it writes one
   OATH_CODE_GENERATED row. Tests: `BiometricPromptAuthenticatorsTest`
   (per API level, a PromptInfo built at API 28 and 29, a source guard);
   `OathPhoneCopyAuditTest` source guard; `OathActivityUiTest`
   `tapCopy_recordsOneOathCodeGeneratedRow`.
8. PIN screen lockout: the lockout card, its countdown and Reset Lockout
   come from one `PinLockoutDisplay` built from both PINs'
   `PinManager.getLockoutStatus`, never from the wall clock. The screen
   reads the status again only when `PinLockoutDisplay.refreshKey`
   (attempts, policy, set flags) changes, so the re-anchor write a read
   makes does not loop. Tests: `PinLockoutDisplayTest`.
9. Round 3. HOTP counter: `generateCode` claims the counter with the
   compare-and-set `OathCredentialDao.advanceCounter` and reads the row
   again when another generation moved it first, up to
   `MAX_COUNTER_ATTEMPTS`; usage and the audit row are written once.
   Tests: `OathHotpConcurrentCopyTest`. `KeyShareAuditTest` counts the
   dispatcher's POLICY_DENIED row next to a refused export. The one
   Devcontainer `GattServerBoundSenderTest` failure is a timing flake
   (no ble/ change here; the same suite passed in Integration).
10. Round 4. A committed OATH add, delete or HOTP counter advance is
    audited even when its caller (an activity's lifecycleScope) is
    cancelled before the call returns: one `auditedWrite` in
    `audit/AuditedWrite.kt` runs a write and its audit under
    NonCancellable, shared by `PasswordEdits` and `OathRepository`. A write
    that throws is not audited. Tests: cancel-after-commit cases for add,
    delete and HOTP generation in `OathRepositoryAuditTest`.
11. Round 5. `OathCredentialDao.deleteByOathId` returns the deleted row
    count; `deleteCredential` audits and returns true only when it removed
    a row, so two deletes that both read the credential write one entry.
    Tests: the two-deletes case in `OathRepositoryAuditTest`.
12. Round 5 sweep. A delete audits success only when it removed
    something. `KeystoreManager.deleteKey`, `deleteGeneralKey` and
    `deleteCredentialKey` check and remove the alias inside one alias
    gate (`removeAliasLocked`), which also removes a software Ed25519 key
    (`ED25519_PREFS_NAME`) that no delete removed before; `deleteByAlias`
    uses it too. `PivKeyManager.deleteKey` audits only when the Keystore
    entry or the `piv_slots` row went; the contact screen deletes through
    `deleteContactAudited` (count > 0). Tests: racing and missing-alias
    cases and Ed25519 removal in `KeystoreManagerCredentialDeleteTest`,
    empty and populated slots in `PivKeyManagerTest`,
    `ContactDeleteAuditTest`. Sweep of `AuditLogger.log*(Delet|Remov)`
    in app/src/main, every site gated:
    - KeystoreManager.kt deleteKey, deleteGeneralKey, deleteCredentialKey:
      existence checked and removed under the alias gate.
    - OathRepository.kt deleteCredential: row count > 0.
    - PasswordEdits.kt delete: `if (deleted)`.
    - PivKeyManager.kt deleteKeyLocked: Keystore entry or row count,
      under the slot lock.
    - TrustStoreRepository.kt deleteCertificateLocked: file and row
      checked under the store lock, early return when neither exists.
    - ui/ContactDeletion.kt deleteContactAudited: row count > 0.

Nothing in slices 4 to 12 was built or run where it was written (no Android
SDK); CI builds it and runs the tests.

Merge of main (OATH list row, tap to copy, long-press menu, store
hardening): the DAO keeps main's claimCounter and drops this branch's
advanceCounter (one HOTP compare-and-set); generateCode keeps main's
exhaustion and progress checks with the claim, usage and audit in
auditedWrite; copyCodeToClipboard is main's OathCodeClipboard path with a
CancellationException rethrow; strings.xml keeps oath_code_copy_failed and
oath_code_unavailable; deleteCredential merged cleanly (row count audit).

- The dispatcher's other catch blocks, docs.
