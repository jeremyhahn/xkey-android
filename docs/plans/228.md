# Plan: #228 — the biometric time window runs on a monotonic clock

## Objective

SPEC feature `user-verification` (shipped) promises a biometric time window of
the length chosen in Settings. `SessionAuthManager` measured that window on
`System.currentTimeMillis()`, so moving the wall clock back kept the window
open, and "never authenticated" was the timestamp `0L`, which a monotonic
clock reading just after boot falls inside. The window must run on
`SystemClock.elapsedRealtime()`, keep "never authenticated / invalidated" as
an explicit state, and treat a clock reading below the recorded one as
expired.

## Slices, in order

1. This plan.
2. Failing tests in `SessionAuthManagerTest`, driven by a fake clock passed
   to the constructor:
   - TIME_WINDOW needs no prompt one millisecond before `timeWindowSeconds`
     have passed, and needs one at and after the boundary;
   - a clock reading below the recorded authentication counts as expired;
   - before any `recordAuthentication`, and after `invalidateAuth`,
     TIME_WINDOW requires biometric even when the clock reads less than the
     window (just after boot);
   - `recordAuthentication` after `invalidateAuth` opens a fresh window.
3. The fix: `SessionAuthManager(clock: () -> Long = SystemClock::elapsedRealtime)`
   so production callers keep calling `SessionAuthManager()`; the last
   authentication is a nullable reading (null = never / invalidated); a
   reading below it is expired. Every existing test still passes, with
   `setUp` passing the fake clock (android.jar's `SystemClock` throws in
   plain JVM tests).
4. `docs/user-verification/architecture.md` names the clock the window uses.

## Out of scope

- `protocol/Handler.kt`, `ble/XKeyGattService.kt`, `settings/BiometricSettings.kt`,
  `ui/SettingsActivity.kt`, `auth/BiometricNotificationHelper.kt`: no
  signature they call changes.
- Persisting the window across process restarts (it is in-memory today and
  stays so).
- PER_OPERATION, PER_SESSION, UV disabled and `clearSession` behaviour.
