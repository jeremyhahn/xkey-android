# Plan: audit the key-sharing transfers (#222)

## Objective

SPEC `audit-log` records security events; `key-sharing` and
`exportable-symmetric-keys` move key material and public keys between the
phone and a paired desktop. Today `local.importSharedKey`,
`local.shareSymmetric` and `local.sharePublicKey` leave no audit record, and
`AuditLogger.logKeyExported` has no caller. Each transfer records one entry,
naming the caller device, with no key bytes in it.

## Slices

1. Failing tests, `protocol/KeyShareAuditTest` (real `RequestHandler`,
   `mockkObject(AuditLogger)`, `mockkObject(XKeyDatabase.Companion)`,
   `mockkConstructor(SoftwareKeyStore)`):
   - importSharedKey of an exportable, shareable software key: one
     KEY_EXPORTED, format `raw`, caller device id and name, no key bytes;
   - importSharedKey of a hardware key: one KEY_EXPORTED, format `public`;
   - a sharing-policy refusal: one failed KEY_EXPORTED; an unknown key: none;
   - shareSymmetric: one KEY_CREATED naming the peer; a duplicate id: none;
   - sharePublicKey: one CONTACT_IMPORTED, source `shared`; the same key
     again: none;
   - responses unchanged; with the logger not initialized all three still
     answer as before.
2. The fix:
   - `logKeyExported` gains defaulted `deviceId`, `deviceName`, `success`,
     `errorMessage`;
   - `logKeyCreated` and `logContactImported` gain defaulted `deviceId` and
     `deviceName`, `logKeyCreated` also `source` (departure from the brief's file map: the KEY_CREATED entry
     must name the peer and neither function could; both stay
     source-compatible);
   - the three handlers call them; the caller device is resolved as
     `logSigningRequest` does. A software key shared without its material
     records format `metadata`.
3. Fix round (verify P1): the peer a transfer is authorized for and
   recorded against is the request's own connection. Failing tests first:
   desktop A on BLE, desktop B paired last on USB, A's three transfers name
   A; a request with no connection never borrows the handler-wide peer.
   Then one choke point, `callerPeerPublicKeyHex()`, reads only the
   request's `CallerSession`; `requireConfirmedPeer` and every audit call
   (the signing/decrypt records too) go through it. A connection with no
   peer key names no device and never throws a protocol error.
   Second round: sign, RSA decrypt, AES encrypt and decrypt each get a
   two-transport test, and a source enumeration test fails if any audit
   path, the share gate or any other function but the field's setters,
   getter and the attestation fallback reads the handler-wide peer. It
   caught the FIDO2 list and assertion sharing checks, which move onto
   `callerPeerPublicKeyHex()` too. Third round: every audit name goes through `auditPeerName` (never throws), and `persistAudited` refuses an already-cancelled request; tests first.
4. Docs: `docs/audit-log/architecture.md` and
   `docs/key-sharing/architecture.md` list the events.

## Out of scope

`attestingPeerPublicKeyHex`'s no-session fallback, `authorizeShare`, `canShareKeyWithPeer`,
`setKeyPolicy` (in-flight policy work), `logKeySharingChanged`, the
`remote.share*` client, the audit log UI and the Room schema. No new
operation types: KEY_EXPORTED, KEY_CREATED and CONTACT_IMPORTED exist.
