# 200: embed the media signature as XMP in MP4/MOV, PNG and WebP

## Objective

SPEC media-signing says the signature is embedded in EXIF or XMP. Only JPEG
embeds it (EXIF `UserComment`); every other type gets a `<name>.xkeysig`
sidecar, and `readSignatureFromUri` reads JPEG only. This row embeds the same
`ContentAuthenticityData` JSON as an XMP packet in MP4/MOV, PNG and WebP, and
the canonical hash leaves out exactly that packet's box or chunk.

## Container layout per type (`XmpContainers`, pure bytes, no Android APIs)

The packet is one `rdf:Description` in the xkey namespace
(`xmlns:xkey="http://ns.automatethethings.com/xkey/media/1.0/"`) whose
`xkey:signature` element holds the XML-escaped JSON. "Ours" means an XMP
box/chunk whose packet declares that namespace.

- MP4/MOV (ISO BMFF): a top-level `uuid` box, usertype
  BE7ACFCB-97A9-42E8-9C71-999491E3AFAC, appended at the end of the file so no
  `stco`/`co64` chunk offset moves. A rewrite drops our old box and appends.
- PNG: an `iTXt` chunk, keyword `XML:com.adobe.xmp`, uncompressed, empty
  language and translated keyword, CRC-32 over type + data, inserted just
  before `IEND`.
- WebP: a RIFF `XMP ` chunk (padded to even length) after the image data, the
  VP8X XMP flag (0x04) set and the RIFF size updated. A simple-format file
  (no VP8X) gets a VP8X chunk with only the XMP flag and the canvas size read
  from the `VP8 ` / `VP8L` header.

## What the canonical hash leaves out

`canonicalContent` for these types removes our box/chunk and undoes exactly
what the writer changed: WebP also clears the XMP flag, drops a VP8X whose
flags are then 0, and restores the RIFF size. With no packet of ours the
bytes are returned unchanged, so an unsigned file's canonical hash is still
its whole-file hash (what `AutoSignHash` streams). JPEG is unchanged.

## Fallback and legacy rule

- The writer embeds only when the container parses and strip(embed(x)) == x
  is guaranteed: a foreign XMP packet, an MP4 whose last box runs to EOF
  (size 0), a VP8X with flags 0, or an unparseable file goes to the sidecar.
  HEIC, MKV and unknown types stay on the sidecar.
- Readers try the embedded packet first, then a legacy sidecar. An embedded
  write deletes no sidecar; the embedded packet wins on read.
  `appendSignature` writes back where it read from, so a legacy sidecar
  stays a sidecar.
- `readSignatureFromUri` streams the box/chunk headers and skips payloads.

## r2: trailing-only strip, unique staging, canonical URI hash, bounded large media

Review findings, one failing test each (committed first), then the fix:

1. `strip` leaves out MP4/MOV boxes of ours only as the trailing run `embed`
   allows; any other placement returns the file unchanged, so it never
   verifies (`MediaHasherCanonicalTest`: a uuid box inserted before mdat).
2. Each embedded write stages to its own `File.createTempFile` beside the
   media, and writes/appends to one path share a lock
   (`XmpMetadataHelperSidecarBranchTest`: overlapping writes).
3. `AutoSignHash.contentHashUri` hashes MP4/MOV, PNG and WebP canonically
   (`AutoSignHashTest`: signed PNG/MP4 re-signed through the URI path).
4. `XmpMetadataHelper.maxEmbedBytes` (128 MiB or heap/6): above it the
   signer streams the whole-file hash and the writer keeps a sidecar without
   reading the file; one already carrying an embedded signature is refused
   (`AutoSignHashTest`: the bound set below a fixture).

## r3: exact added VP8X, VP8L alpha, reader-sized packets

Review findings, one failing test each in `XmpContainersTest` (committed
first), then the fix in `XmpContainers`:

1. `strip` drops a VP8X only when the rest is one image chunk and the VP8X
   is byte for byte the one `embed` adds to it; any other VP8X stays (XMP
   flag cleared), so an edited canvas never verifies. `embed` refuses a
   file whose own VP8X would read as that added one. Test: a tampered
   canvas stays in the canonical bytes.
2. The added VP8X carries ALPHA (0x10) when the VP8L header's
   alpha_is_used bit is set. Test: a transparent simple lossless fixture
   gets flags 0x14 and strips back exactly. An instrumented decode of a
   real transparent VP8L is not in this round.
3. `embed` refuses (sidecar, or the helper's explicit error when a packet
   is already embedded) a packet whose payload exceeds the stream reader's
   1 MiB limit, per format. Test: sizes around the limit either embed and
   read back or are refused.

The plan's earlier "VP8X with flags 0" refusal is replaced by rule 1;
docs/media-signing/engineering.md still states the r1 wording.

r3 was written without a build; a later session compiled it and ran the
media unit tests, Android lint and the lint gates, all green with no code
change.

## fix round: parser bounds, re-sign path, read failures

Failing tests first (`XmpContainersTest`, `XmpMetadataHelperSidecarBranchTest`,
`XmpMetadataHelperInstrumentedTest`), then the fixes:

1. Parser bounds: `parse` stops at 65536 boxes/chunks (`MAX_PARTS`) and
   refuses the file (null) before allocating the next part, so `embed`
   refuses, `extract` finds nothing and `strip` hashes the file whole. Test:
   a WebP under `maxEmbedBytes` with 100 000 empty unknown chunks, and an MP4
   with 100 000 empty `free` boxes, are refused.
2. Re-sign path (choice: replace the embedded signature). The Share-sheet
   signer's non-JPEG branch calls the new
   `XmpMetadataHelper.replaceEmbeddedSignature` for MP4/MOV, PNG and WebP: it
   copies the shared stream into a unique working file (at most
   `maxEmbedBytes`; a larger one is probed for a carried packet, which
   refuses), embeds the new signature there, replacing the old one, and
   writes it back with `"wt"`. Only when the file cannot carry one (and so
   carries none) does the `.xkeysig` picker run as before. Tests: a JVM
   re-sign of an auto-signed PNG/WebP/MP4 with a second key reads back the
   second signer; the same through a file URI, instrumented (compiled).
3. Read failures: `XmpContainers.read` lets an `IOException` from the
   stream propagate (a short or unparseable stream is still null), and
   `writeEmbeddedSignature` no longer catches the probe or the
   `readBytes`, so a failed read fails `writeSignature` with no sidecar. On
   an `embed` refusal the existing-packet check uses the stream reader, the
   view readers have, so a refused file that still reads as signed throws.
   Tests: a media path that cannot be read, below and above
   `maxEmbedBytes`, throws and leaves no sidecar; `read` over a throwing
   stream throws. `MediaSigningService.contentHashUri`'s probe gains the
   same propagation through `read`.
