# 188: contact import reads the key's curve

## Objective

Contact import labels every EC key `ES256` and every RSA key `RS256`
without reading the curve, accepts EC keys on curves the app cannot verify
with, and lets a QR envelope's `algorithm` hint override the key. The
parsing is private to `ContactManagementActivity` and uses
`android.util.Base64`, so it has no JVM test.

## Slices (in order)

1. Tests first: `crypto/ContactKeyParserTest` against a stub
   `ContactKeyParser` (every parse returns null), so the suite compiles and
   fails:
   - P-256 DER and PEM give ES256 and the DER's SHA-256 fingerprint
     (lowercase hex);
   - P-384 gives ES384, P-521 gives ES512, RSA-2048 gives RS256;
   - a secp256k1 key is refused;
   - garbage, empty input and a non-Base64 PEM body are refused;
   - hint ES256 on a P-384 key gives ES384; a matching hint is kept.
2. The parser, turning them green: `crypto/ContactKeyParser`, no Android
   imports. DER first, then PEM (`java.util.Base64` MIME decoder for bodies
   with line breaks). The EC curve is identified by comparing the key's
   `ECParameterSpec` (order, generator, cofactor, field, coefficients) to
   P-256, P-384 and P-521, not by field size alone, so secp256k1 is refused.
   Returns the DER (`publicKey.encoded`), the detected algorithm and the
   fingerprint, or null. The detected algorithm wins over a disagreeing hint.
3. The activity calls the parser from `importPublicKeyBytes`,
   `importScannedPayload`, the paste dialog and the key detail dialog, and
   drops its private `parsePublicKey`, `parsePEM` and `computeFingerprint`.
   User-facing messages and string resources stay as they are.
   docs/contacts/engineering.md names the parser and the curve mapping.
