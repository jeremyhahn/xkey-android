# #216: one signature counter per passkey

## Objective

A passkey can be used by two paths: the credential provider
(`GetCredentialHandler.handleGetCredential`) and the phone backend
(`Handler.handleLocalSignFido2Assertion`). On main each path keeps its own
count. The provider reads `credential_metadata.sign_count` and writes both
stores. The phone backend reads `keys.sign_count` and writes only `keys`. So
a provider assertion that follows a phone-backend one signs a counter the
relying party has already seen. Both paths also read, sign and write in
separate steps, so two assertions running at once can sign the same value.

Both paths take the counter from one `PasskeySignCounter` (credential
package). It advances the counter before anything is signed and returns the
value to sign:

- one `Mutex` per credential id, shared by every instance in the process
  (the provider service and the protocol handler run in the app process);
- next = max(metadata counter, key counter) + 1, so stores that already
  disagree continue from the larger value;
- the value is written to both `CredentialMetadataDao` and `KeyDao` before it
  is returned. If a write fails, the error propagates and nothing is signed.

The counter advances before signing. A signature that fails afterwards leaves
a gap, which a relying party accepts because the next counter is still
larger. A value is never handed out twice, so a rollback is never signed.
Neither handler writes `sign_count` itself any more.

No Room schema or DAO interface change: the mutex makes the read and both
writes atomic for this process. A `@Transaction` method is not needed.

## Slices

1. This plan.
2. Failing tests, `PasskeySignCounterTest` (DAOs faked with mockk, backed by
   in-memory counters):
   - phone backend then provider for one passkey: the counter rises (main's
     split counters repeat a value);
   - provider then phone backend: the counter rises;
   - two concurrent advances return two different values, and the stored
     counter equals the larger;
   - after an advance both DAOs hold the same value;
   - a passkey whose two stores disagree continues from the larger.
   Both handlers call the same `next(credentialId)`, so the cross-path
   cases seed the store that main's other path left behind (the phone
   backend wrote only `keys`) and check that the next value rises above
   every value already signed. They fail on main, which has no shared
   counter.
3. Fix: `PasskeySignCounter`, used by both handlers before they build
   authenticator data. Tests go green.
4. Docs: one paragraph each in `docs/fido2-phone-backend/architecture.md`
   and `docs/passkey-provider/architecture.md`.

## Review fixes

1. Tests: `PasskeySignCounterTest` gains
   `aCounterThatCannotBePersistedRefusesBeforeAnySignature` (either DAO
   write throws: the assertion is refused and nothing is signed) and
   `theAssertionAfterAPersistenceFailureStillRises` (the next assertion
   signs above every value signed or persisted before the failure).
   `GetCredentialHandlerTest.assertion_refusesToSignSilentlyOnceItHasAssertedUserVerification`
   keeps its expectation, now with a message: a refused ceremony leaves the
   counter at 0. Early reservation broke it.
2. Fix: `GetCredentialHandler` refuses a UV=1 ceremony without a prompt,
   and runs the explicit verification of a key that is not auth-bound,
   before it reserves the counter. A refusal or a failed verification
   leaves the counter alone. A counter that cannot be persisted refuses the
   assertion (`CredentialAssertionException`) before anything is signed.
   An auth-bound key verifies inside `keystoreManager.sign`, over
   authenticator data that already holds the counter. So a cancelled
   prompt there consumes the reserved value. That is the gap the
   objective accepts: the value was never signed, and the next one is
   larger.

## Out of scope

- Room schema, DAO interfaces, `UserVerificationCompliance`, sharing-policy
  checks.
- Counters across processes or devices (synced passkeys); the 32-bit
  wrap of the authenticator-data counter.
