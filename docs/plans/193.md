# #193: per-key sharing edits in user-action order

Follow-up to #174 (merged in #182). Plan of record for the design:
`docs/plans/174.md`, section "#193: user-action order".

## Objective

Every edit of a key's peer rows from the key-sharing sheet (a grant, a
withdrawal, the key-wide clear when leaving Selected peers) is written in the
order the user made it, by one writer per key, off the main thread. A grant is
bound to the pairing the user saw when they tapped: if that pairing ended
before the write, the grant is refused and leaves no row.

## Design (short)

- `KeySharingPeers` owns a per-key serial queue: a fair `Mutex` shared by every
  instance for the same key id. A change takes its place in the queue when it
  is called, before any suspension, then runs on an injected IO dispatcher
  (`Dispatchers.IO` by default).
- `setAllowed(peer, allowed, pairing)` takes the pairing generation captured at
  the tap (`PairedDeviceRepository.pairingGeneration`).
- `setSharingPolicy(selectedPeers, store)` runs the key's policy column write
  and, unless Selected peers, `clearPoliciesForKey`, in the same queue.
- `PairedDeviceRepository.writeGrant(peer, expectedPairing, write)` refuses
  when the current pairing is not `expectedPairing`, under the store lock,
  before the marker is committed.
- `KeySharingBottomSheet` captures the generation in the checkbox listener and
  starts both edits with `CoroutineStart.UNDISPATCHED`, so the queue order is
  the tap order.

## r2: detached sheet after a refused grant

A queued edit runs under `NonCancellable`, so a grant still waiting when the
user dismisses the sheet completes, and its caller resumes even though the
sheet's lifecycle job is cancelled. A refused grant then redrew the peer list
of a detached sheet: `createPeerCard` calls `requireContext()` and throws.

- Seam: `KeySharingPeers.setAllowedOrRedraw(peer, allowed, pairing, attached,
  redraw)` in `KeySharingBottomSheet.kt`; the sheet passes
  `isAdded && view != null` and `populatePeerList(peersFlow.value)`.
- After `setAllowed` returns it checks the caller's job
  (`ensureActive`) and `attached()` before redrawing. The queued database
  edit itself still completes.
- Test, committed failing first:
  `KeySharingPeersTest.aRefusedGrantDoesNotRedrawASheetDismissedWhileItWaited`
  (the grant waits behind B's, A is unpaired, the sheet is dismissed, the
  queue drains: no row for A, no redraw).

## r3: queued revocations survive dismissal

`NonCancellable` in `inOrder` is what keeps a withdrawal or key-wide clear
queued behind a grant from being dropped when the sheet is dismissed; no test
held it. Tests only, no production change:

- `aWithdrawalQueuedBehindAGrantSurvivesTheSheetsDismissal`: A's withdrawal
  waits behind B's grant, its caller is cancelled, the grant is released: A's
  row is gone.
- `aKeyWideClearQueuedBehindAGrantSurvivesTheSheetsDismissal`: the same for
  leaving selected peers: the column is stored and the key has no peer rows.
- `aRefusedGrantDoesNotRedrawASheetDismissedWhileItWaited` also verifies the
  cancelled tap's grant reached `writeGrant` (and was refused there).

All three fail with `NonCancellable` removed from `inOrder` (checked by hand).

## durable policy edits

Two P1 findings on the merged #174 ordering (`be3bcd9`):

- local.setKeyPolicy answered `updated: true` even when its write failed and
  was only queued for retry; the retry and the enforced denial lived in
  memory, so a process restart restored the stored All Peers.
- A policy intent and a withdrawal retry named the key only by `key_id`. A
  key deleted and generated again under the same id during backoff got the
  old key's policy and lost its grant rows.

Design:

- **Reported only when durable.** `KeySharingPeers.setKeyPolicy` returns
  whether the intent landed. `handleLocalSetKeyPolicy` answers `updated: true`
  only then; otherwise an `INTERNAL_ERROR` "stored policy pending" error. The
  intent stays enforced and retried, as before.
- **Durable denial.** Before a narrowing intent is first attempted, its
  enforced policy (Private, or Selected peers once the rows are cleared) is
  committed to `PairedDeviceRepository` as `(key_id, instance, policy)`; it is
  updated as the intent's enforcement changes and removed when the intent
  lands or the key is deleted. `canShareKeyWithPeer` (and so `authorizeShare`)
  enforces a record matching the entity's `id` over the stored policy, so a
  restart denies until a later edit of the key lands.
- **Generation binding.** An intent and a withdrawal retry carry the key's
  instance, the `keys.id` row id (`KeySharingPolicyDao.keyInstance`), read
  under the edits lock when accepted. `land` and the withdrawal retry run
  under that same lock and drop themselves, writing nothing, when the key's
  current instance differs (deleted, or deleted and generated again).
- **Deletion under the lock.** `KeySharingPeers.forgetKey(keyId)` drops the
  key's intent, pending withdrawals and durable record under the edits lock;
  `handleLocalDeleteKey` deletes the row inside it, so no retry interleaves.

Tests, committed failing first (`KeySharingPendingIntentHandlerTest`):

- `aFailedRpcRevocationIsNotReportedAndSurvivesARestart` (a)
- `aFailedRpcWideningIsDroppedWhenTheKeyIsDeletedAndReused` (b)

## KeyPolicyStore

Review of the durable-policy round showed a key's policy state split across
Room (`keys.sharing_policy`, grant rows), SharedPreferences (the denial
record) and memory (`keyIntents`), each written on its own. Replaced by one
Room table, changed only through `storage/KeyPolicyStore`, in one transaction.

Table `key_policies` (XKeyDatabase 12 -> 13), one row per key:

| column | type | meaning |
|---|---|---|
| `key_id` | TEXT PK | the key id |
| `key_instance` | INTEGER NOT NULL, FK `keys.id` ON DELETE CASCADE | the key row the policy belongs to |
| `sharing_policy` | TEXT NOT NULL | stored policy, kept equal to `keys.sharing_policy` |
| `pending_policy` | TEXT NULL | an accepted change not yet applied (migrated records only) |
| `denial` | TEXT NULL | PRIVATE or SELECTED_PEERS enforced over `sharing_policy` |
| `clear_grants` | INTEGER NOT NULL | grant rows still owed a clear |

Invariants:
- Every key insert and delete goes through the store: the policy row is
  created and dropped with the `keys` row, in the same transaction.
- An edit names the instance it was accepted for; inside the transaction it
  reads `keys.id` and refuses (error, nothing written) if it differs or the
  key is gone. No unbound edit exists: a read failure is an error.
- A narrowing writes `keys.sharing_policy`, the row, and (when leaving
  Selected peers or when `clear_grants` is set) deletes the grant rows, all in
  one transaction; `clear_grants` and `denial` end cleared only in that same
  transaction. A failed transaction changes nothing and is returned as an
  error: there is no in-memory intent and no background retry of policy.
- `authorize` reads `denial` over `sharing_policy` from the row.
- Migration 12 -> 13 creates a row per key from `keys`, then moves each
  SharedPreferences `pending_key_policy:` record whose instance matches into
  `denial` (PRIVATE also sets `clear_grants`), and deletes the prefs keys.

Callers moved: `KeySharingPeers` (sheet edits, `setKeyPolicy`, `forgetKey`),
`Handler` (generation inserts, local.deleteKey, local.setKeyPolicy,
`canShareKeyWithPeer`), `KeyDetailActivity.deleteKey`,
`KeyManagementActivity.deleteKey`, PIV/remote KeyEntity inserts/deletes.
`PairedDeviceRepository` loses its pending key policy record. Per-peer
withdrawal retries stay as they are (not key policy state).

Tests, failing first: `KeyPolicyStoreTest` (a) throwing instance lookup fails
the edit, (b) failed Private clear + restart + Selected clears survivors,
(c) key replaced between check and write: old edit refused, new grants kept,
(d) failed denial removal reports failure and policy/denial agree after
restart. Migration: the project has no room-testing/MigrationTestHelper
(see `LegacySchemas`), so `XKeyDatabaseMigrationTest` gains 12 -> 13 in its
own form, plus `XKeyDatabaseRoomUpgradeTest` moves to 13.

As built:
- A failed narrowing leaves its denial in a second transaction, bound to the
  same instance; that is the only write after a failure. Leaving Selected
  peers, or any Private, records deny-all plus `clear_grants`; a failed
  Selected peers records a Selected peers denial. Grants are refused while
  `clear_grants` is set or the denial is deny-all.
- Key rows written outside the store (PIV and remote imports) get no policy
  row; a missing row, or one for another instance, means no denial, and ON
  DELETE CASCADE drops policy and grant rows with any key row.
- A prefs record that cannot be read during the migration is logged and
  skipped; the records moved are deleted once the database opens.
- The grant cleanup on unpairing still clears a peer's rows through
  `KeySharingPolicyDao` (per peer, not key policy state).
- `XKeyDatabaseMigrationTest` is an instrumented test: compiled here, not run.
