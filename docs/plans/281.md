# Plan: fido2-phone-backend, CTAP2 over BLE (#281)

## Objective

The SPEC row fido2-phone-backend requires CTAP2 over BLE. The phone becomes a
standard FIDO2 BLE authenticator (CTAP 2.1, "Bluetooth Smart / Bluetooth Low
Energy Technology"): a CTAP2 client such as a browser or `libfido2` uses the
phone's passkeys over BLE, with the phone's biometric prompt as user
verification. The JSON-RPC methods on the Noise session stay as they are.

## Slices

1. Docs (done). The row says CTAP2 over BLE is not yet shipped (#281).
2. Tests, in their own commit, in `app/src/test/.../ble/fido/`:
   - framing: fragment a message into CMD + CONT frames, reassemble, oversize
     length, bad sequence, CONT without CMD, unknown command, CANCEL;
   - CBOR: decoder round trip of maps, arrays, text, bytes, ints, bools;
     canonical map encoding;
   - CTAP2: authenticatorGetInfo, authenticatorGetAssertion (allowList,
     discoverable, no credentials, sharing policy hides, user verification
     declined or unavailable, rising sign counter, verifiable signature),
     authenticatorMakeCredential (attested credential data, unsupported
     algorithm, excludeList, up=false, user verification refusals);
   - session: PING echo, MSG answered, KEEPALIVE while waiting, CANCEL.
3. Code, in `ble/fido/`:
   - `FidoBleFraming`: constants, fragmenter, reassembler;
   - `crypto/CborEncoder.kt`: a general canonical encoder and a decoder;
   - `Ctap2Authenticator`: the three commands over a
     `FidoCredentialBackend` (credentials filtered by the sharing policy,
     user verification, counter and signing, credential creation);
   - `AndroidFidoCredentialBackend`: the backend on `KeyDao`,
     `SharePermission`, `PasskeySignCounter`, `UserVerificationCompliance`,
     `KeystoreManager` and `BiometricActivityLauncher`;
   - `FidoBleSession`: reassembly, dispatch, KEEPALIVE, CANCEL, replies;
   - `FidoGattServer`: the 0xFFFD service (fidoControlPoint, fidoStatus,
     fidoControlPointLength, fidoServiceRevisionBitfield = FIDO2 only), with
     encrypted, authenticated (bonded) access; started by `XKeyGattService`
     beside the xkey service; `Advertiser` adds the 0xFFFD UUID.
4. Docs: `docs/fido2-phone-backend/architecture.md`,
   `docs/ble-transport/architecture.md`, SPEC.md row and ROADMAP.md.

## Status

Slices 1 to 4 are done. The three commands are tested end to end over CBOR
bytes with a fake backend, the Android backend with mocked stores, and
`FidoGattServer` under Robolectric (permissions, revision, MTU-sized control
point, subscription, the bounded whole-message queue, no cross-client frame
below API 33). Later rounds added: phone prompts over the lock screen, the
sharing policy checked again before a signature is released, and account
choice by successive prompts when several discoverable passkeys match.

Later rounds also added notification retries (three attempts, then the
connection is cancelled) and the 3 s request timeout (ERR_REQ_TIMEOUT).

The SPEC.md fido2-phone-backend row keeps its approved text; only its closing
note changes, to "CTAP2 over BLE (#281): built and unit tested (FIDO GATT
service 0xFFFD, GetInfo, GetAssertion, MakeCredential), not yet verified on a
device". The row stays `in progress`, and the ROADMAP.md line reads "in
progress: CTAP2 over BLE built and unit tested, device verification left".
Design detail lives in `docs/fido2-phone-backend/architecture.md`.

Review round 6 closes five findings, each test first: resident replacement
runs under one process-wide registration lock (two concurrent registrations
leave one discoverable passkey); the replacement lookup is inside the
rollback, so a failed creation leaves the old passkey usable; a passkey's
Keystore key is deleted only once both of its rows are gone; a cancellation
on the prompt and sign path is rethrown, never a CTAP error; user handles
compare as decoded bytes.

Left:

- Verify on a device against a CTAP2 BLE client (bonding, the 0xFFFD
  advertisement, MTU-sized notifications) and against
  `xkey fido2 --backend phone`. Mark the row shipped only after that.
- clientPin, authenticatorGetNextAssertion, silent (`up` false) assertions,
  and a list screen for account choice.

## Out of scope

- clientPin / pinUvAuthToken (getInfo reports no clientPin; a request with
  pinUvAuthParam is refused).
- authenticatorGetNextAssertion, credential management, extensions.
- U2F (CTAP1) over BLE.
- Changes to the xkey GATT service, its framing or the JSON-RPC methods.
