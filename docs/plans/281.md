# Plan: fido2-phone-backend, CTAP2 over BLE (#281)

## Objective

The SPEC row fido2-phone-backend requires CTAP2 over BLE. The phone becomes a
standard FIDO2 BLE authenticator (CTAP 2.1, "Bluetooth Smart / Bluetooth Low
Energy Technology"): a CTAP2 client such as a browser or `libfido2` uses the
phone's passkeys over BLE, with the phone's biometric prompt as user
verification. The JSON-RPC methods on the Noise session stay as they are.

## Slices

1. Docs (done). The row says CTAP2 over BLE is not yet shipped (#281).
2. Tests, in their own commit, in `app/src/test/.../ble/fido/`:
   - framing: fragment a message into CMD + CONT frames, reassemble, oversize
     length, bad sequence, CONT without CMD, unknown command, CANCEL;
   - CBOR: decoder round trip of maps, arrays, text, bytes, ints, bools;
     canonical map encoding;
   - CTAP2: authenticatorGetInfo, authenticatorGetAssertion (allowList,
     discoverable, no credentials, sharing policy hides, user verification
     declined or unavailable, rising sign counter, verifiable signature),
     authenticatorMakeCredential (attested credential data, unsupported
     algorithm, excludeList, up=false, user verification refusals);
   - session: PING echo, MSG answered, KEEPALIVE while waiting, CANCEL.
3. Code, in `ble/fido/`:
   - `FidoBleFraming`: constants, fragmenter, reassembler;
   - `crypto/CborEncoder.kt`: a general canonical encoder and a decoder;
   - `Ctap2Authenticator`: the three commands over a
     `FidoCredentialBackend` (credentials filtered by the sharing policy,
     user verification, counter and signing, credential creation);
   - `AndroidFidoCredentialBackend`: the backend on `KeyDao`,
     `SharePermission`, `PasskeySignCounter`, `UserVerificationCompliance`,
     `KeystoreManager` and `BiometricActivityLauncher`;
   - `FidoBleSession`: reassembly, dispatch, KEEPALIVE, CANCEL, replies;
   - `FidoGattServer`: the 0xFFFD service (fidoControlPoint, fidoStatus,
     fidoControlPointLength, fidoServiceRevisionBitfield = FIDO2 only), with
     encrypted, authenticated (bonded) access; started by `XKeyGattService`
     beside the xkey service; `Advertiser` adds the 0xFFFD UUID.
4. Docs: `docs/fido2-phone-backend/architecture.md`,
   `docs/ble-transport/architecture.md`, SPEC.md row and ROADMAP.md.

## Status

Slices 1 to 4 are done. The three commands are tested end to end over CBOR
bytes with a fake backend, the Android backend with mocked stores, and
`FidoGattServer` under Robolectric (permissions, revision, MTU-sized control
point, subscription, the bounded whole-message queue, no cross-client frame
below API 33). Later rounds added: phone prompts over the lock screen, the
sharing policy checked again before a signature is released, and account
choice by successive prompts when several discoverable passkeys match.

Later rounds also added notification retries (three attempts, then the
connection is cancelled) and the 3 s request timeout (ERR_REQ_TIMEOUT).

The SPEC.md fido2-phone-backend row keeps its approved text; only its closing
note changes, to "CTAP2 over BLE (#281): built and unit tested (FIDO GATT
service 0xFFFD, GetInfo, GetAssertion, MakeCredential), not yet verified on a
device". The row stays `in progress`, and the ROADMAP.md line reads "in
progress: CTAP2 over BLE built and unit tested, device verification left".
Design detail lives in `docs/fido2-phone-backend/architecture.md`.

Review round 6 closes five findings, each test first: resident replacement
runs under one process-wide registration lock (two concurrent registrations
leave one discoverable passkey); the replacement lookup is inside the
rollback, so a failed creation leaves the old passkey usable; a passkey's
Keystore key is deleted only once both of its rows are gone; a cancellation
on the prompt and sign path is rethrown, never a CTAP error; user handles
compare as decoded bytes.

Later review rounds, each test first, make replacement safe for the passkey
it replaces. The old passkey's rows go in one Room transaction, and the
registration fails when they will not go. The old passkey is deleted only once
the new one is stored, so a cancellation before then leaves the old passkey in
place. Each candidate is read again just before the delete, and the delete
(`KeyDao.deletePasskeyRows`) removes a key row only while its id, policy
revision and sharing policy are still the ones read, in the same statement. A
passkey the owner makes private, or shares with selected peers only, at any
point before that delete keeps its rows and its Keystore key. Every passkey
delete in the BLE authenticator, the rollback of a new passkey included, goes
through that one path, and a source test checks it.

A client that disables the fidoStatus CCCD gets no more frames: the
unsubscribe drops the queued frames and the one being retried, and the one
send path (`sendNext`) sends nothing while the client is not subscribed,
whether a completion, a retry or a new reply calls it. A later subscription
starts with an empty queue. A source test checks that the stack is notified
and the subscription set nowhere else.

Review fix (cancelled prompt on screen): a BLE CANCEL or disconnect
cancels the session's job off the main thread; the withdrawal of a generic
prompt on screen (TransparentBiometricActivity.withdraw, the one choke
point the launcher calls before handing the screen on) now dismisses it on
the main thread and returns only then, so the next approval never launches
while it is still up. Test: FidoPromptCancellationTest, through the real
launcher and activity, for a registration and an assertion.

Review fix (write after stop): every GATT callback finds its client through
one lookup, which runs under the lock `stop()` takes and returns nothing once
the server has stopped; a control point write looks its client up once and
dispatches to that one, so a stop or disconnect after the check leaves it a
closed session, never a fresh one. Tests in FidoGattServerTest stop the
server between a write's check and its dispatch, and drive every callback
after `stop()`: no client, handler request or notification follows.

Review fix (Keystore deletion that fails): every Keystore key deletion in
the backend goes through one choke point, `deleteKey`. A passkey's key is
recorded in `PendingKeyDeletions` (a file under no-backup storage) before its
rows go and forgotten only once Keystore deletes it; a deletion that throws
stays recorded, and the next registration retries it under the registration
lock, never deleting a key a row still points at. Tests in
AndroidFidoCredentialBackendTest make deleteKey throw once during a failed
registration and during a resident replacement: a later registration, on a
fresh backend, deletes the key. PendingKeyDeletionsTest checks the record
survives a new instance.

Round 2 review fixes. A rollback no longer needs a second file write: when
the deletion record cannot be written, rolling back a failed registration
deletes its rows and its Keystore key directly (a replacement still fails
whole without the record). The GATT server admits a client only on its
connection callback, under the lifecycle lock that disconnect and stop take;
every other callback only looks its client up, so one that arrives after or
races a disconnect creates no client and no session. Clients already
connected when the server starts are admitted then. Tests:
AndroidFidoCredentialBackendTest makes PendingKeyDeletions.add throw after a
metadata write fails (nothing is left, nothing is offered); FidoGattServerTest
writes after a disconnect and during one.

Unit-test heap (CI fix round). `make coverage` ran out of the test JVM's
512 MiB heap (Gradle's default; one JVM for the whole suite). The heap dump
held about 127 000 MockK `Invocation`s, each with a captured stack trace:
an inline mock's handler entry keeps its recorded calls, and through them
the mock, for the rest of the run. Most came from the 10 000-delete ledger
test in RemoteShareClientTest, the rest from this row's FIDO tests (GATT
server, prompts, backend). Fix: a shared `ReleaseMocks` rule
(`testing/ReleaseMocks.kt`) clears every mock's recorded calls and answers
after each test, taken by those classes; the 10 000-delete test also drops
its recordings every 500 rounds, since alone it needed over 400 MiB. No
heap or metaspace raise. Measured on the test JVM's GC log:

| | heap after GC, peak | live after full GC, peak | full GCs | metaspace, peak |
|---|---|---|---|---|
| before (OOM) | 511 MiB of 512 | 511 MiB | 423 | 197 MiB |
| after (passes) | 374 MiB of 494 | 150 MiB | 1 | 201 MiB |

Metaspace is the same before and after (it is uncapped and holds the
Robolectric sandbox's classes), so it was never the limit.

Review round fix: the legacy shareable flag of a BLE passkey agreed with no
policy (shareable false beside ALL_PEERS), so local.listKeys and
local.getKeyInfo told a desktop the passkey was unshareable. ble/fido now
builds every key row in one place (`FidoKeyRows.passkey`), which derives
shareable from the sharing policy. Tests: `FidoBleRegistrationMetadataTest`
registers over BLE and reads both methods (test first); `FidoKeyRowsTest`
checks the flag for every policy and fails if any other ble/fido code builds
or copies a KeyEntity, or sets shareable or sharingPolicy, outside it.

Review fix (empty lists and incomplete registrations), each test first. An
explicit empty allowList, excludeList, extensions or options is treated as
absent where the request is decoded (`Ctap2Authenticator.decodeParams`), so
an empty allowList is discovery. A BLE passkey's key and metadata rows go in
one Room transaction (`KeyDao.insertPasskeyRows`). The registration is
recorded as incomplete in `PendingKeyDeletions` before its key or rows are
made and forgotten once it is whole; until then it is never offered, and the
record survives a rollback delete that throws, so the next registration
removes its rows and key. Tests: Ctap2AuthenticatorTest (empty allowList with
one and with several resident accounts, empty excludeList);
AndroidFidoCredentialBackendTest (a failed registration and a failed
replacement whose rollback delete fails are never offered and are cleaned up
on retry). Empty extensions and options maps have no test: before the fix an
empty options map already read as absent (no up, uv or rk) and nothing reads
extensions, so no input tells the two apart; they are normalized with the
lists so the decode stays one rule.

Step: completion at one storage point, and one signing algorithm. A BLE
registration's rows are written only by
KeyDao.completePasskeyRegistration: one transaction inserts the new key row
and metadata row and deletes the passkeys it replaces, all or none. Its commit
is the one point a passkey becomes whole, so a registration that fails, is
cancelled, or whose process dies has no row in `keys` or `credential_metadata`
for any reader: the credential provider (GetCredentialHandler), the local list
(Handler) and BLE need no filter of their own. The pending record now only
covers a Keystore key no row owns; a recorded registration whose rows exist is
whole and kept. The BLE backend offers only ES256 fido2 rows, the one
algorithm both signing paths use, so ES384, ES512 and RSA rows that
local.generateKey can store are never offered, signed with, replaced, or able
to shadow an ES256 passkey in an allowList. Tests: IncompleteRegistrationTest
(Room: replacement and rollback deletes failing, a registration stopped with
nothing undone, a whole passkey whose record cannot be cleared);
AndroidFidoCredentialBackendTest (ES384, ES512, RS256 rows; an unsupported row
ahead of an ES256 one in an allowList).

Step: the passkey approved is the passkey signed with, and its real security
level. Before any prompt or signing turn the backend snapshots the chosen
row and the public key under the one Keystore alias it signs with. One
helper (`signSelected`) then holds the stored key's lock, the one the
JSON-RPC approval path and local.deleteKey take (shared from Handler.kt),
rechecks that the row is the same key (same row id, key material, policy)
and still shared, and signs only while the key under that alias is the
snapshot's (`KeystoreManager.signApproved`; the key-bound prompt signs under
the snapshot alias and the alias is checked again after). Both signing paths
go through it, so a passkey deleted and recreated under its ID while the
prompt or signing turn waits yields no assertion. A BLE passkey's row records
`strongBoxBacked` from the generated key's KeyInfo (StrongBox or the TEE
fallback), through `FidoKeyRows.passkey`. Tests:
AndroidFidoCredentialBackendTest (delete and recreate during the key-bound
prompt, during its signature, and during the silent signing turn);
FidoBleRegistrationMetadataTest (StrongBox and TEE levels).

Step (review round, credential lifetime): every BLE step that reads, signs
with or deletes a passkey's key material runs under the per-key lock
(`storedKeyLockId`, the one local.generateKey and local.deleteKey take), in
one backend helper. The snapshot (row, alias, public key) is taken when the
credential is listed, before the account chooser or the user check, and
travels on `FidoCredential` to signing, so a passkey recreated during either
prompt is refused. Removing a replaced passkey's key and retrying a recorded
deletion check under that lock that no row owns the ID, so a passkey made
again over JSON-RPC meanwhile keeps its key. Tests:
PasskeyReplacedWhileSigningTest (recreated during the user check and the
account choice); AndroidFidoCredentialBackendTest (recreated during the
replacement cleanup and during the retry).

Step (review round, unusable candidates): the backend's `credentials` is the
one list every candidate comes from, and it takes each passkey's snapshot
before building its credential, leaving out one without a snapshot (row gone
or made private since it was listed, or its key not in Keystore). The
allowList match, the discoverable list, the account chooser and the
excludeList check in `Ctap2Authenticator` all read that list, and no response
carries a credential count, so a passkey that cannot sign never shadows a
usable one in an allowList nor is offered on discovery. Tests:
AndroidFidoCredentialBackendTest (an unusable first allowList entry, a keyless
discoverable passkey, every match unusable answering no credentials before
any prompt).

Step: an expired time-window passkey reauthenticates (review fix). A
time-window passkey (auth duration above 0) whose window closes while its
assertion waits behind another approval was handed to the key-bound signing
prompt, whose `Signature.initSign` fails on the expired key before it
prompts. `AndroidFidoCredentialBackend` now picks the prompt kind in one
place, as `RequestHandler.signWithBiometric` does: a time-window key takes a
fresh generic authentication and signs again in the new window (refused if it
closes again); a per-use key, or any other key Keystore binds to
authentication, signs behind its key-bound prompt. The generic prompt and the
signature are two consecutive queue turns: one turn for both needs a launcher
change outside this row. makeCredential makes keys that are not auth-bound
and signs nothing, so the assertion is the only BLE path that picks a prompt.
Tests: AndroidFidoCredentialBackendTest (expired time-window key behind
another approval, declined reauthentication, per-use key never takes a
generic prompt).

Step: parameter types and canonical map order (review fix). `decodeParams`,
the one decoder every CTAP2 command's parameters go through, dropped an
empty list or map for any optional parameter before its type was checked, so
an empty map sent as allowList entered discovery and signed. It now checks
each optional container against its expected type (allowList and excludeList
arrays; extensions and options maps), refuses any other type, empty or not,
with CTAP2_ERR_CBOR_UNEXPECTED_TYPE, and drops only an empty container of the
expected type. getInfo takes no parameters and clientPin is not implemented,
so getAssertion and makeCredential are the commands it covers. The CBOR
encoder sorted map keys length-first (-1 before 24); its one comparator now
orders by major type first, then length, then bytewise, the CTAP2 canonical
order. Tests: Ctap2AuthenticatorTest (each optional parameter as the wrong
container, empty and not, or a scalar), CborEncoderTest (24 vs -1, 1000 vs
"a", order within each type).

Step: every request entity validated at one choke point (review fix). The
pubKeyCredParams parser kept only each entry's alg, so an ES256 entry of any
type, or of none, reached `backend.create` and with rk could replace a
resident passkey. `Ctap2Requests` (beside the authenticator) now decodes and
validates each getAssertion and makeCredential request in full before the
command runs, so before any prompt, lookup or store write: rp (id text,
non-empty; name, icon text), user (id bytes, 1 to 64; name, displayName, icon
text), every pubKeyCredParams entry (type text, alg integer, both required),
every excludeList and allowList descriptor (type text, id bytes 1 to 1023,
transports a list of text), options and extensions (text keys, boolean
options), pinUvAuthParam (refused), pinUvAuthProtocol and enterpriseAttestation
(unsigned). Missing is MISSING_PARAMETER, wrong type CBOR_UNEXPECTED_TYPE,
out of range INVALID_LENGTH. ES256 is chosen only from a "public-key" entry,
else UNSUPPORTED_ALGORITHM. A descriptor of another type is checked, then
ignored (CTAP 2.1): it names no credential, so an allowList of only such
descriptors answers NO_CREDENTIALS, never discovery, and excludes nothing.
The commands read only the typed request it returns. Tests:
Ctap2RequestValidationTest (each malformed entity, no prompt, lookup or
creation, the resident passkey for the same RP and user kept).

Review fix (present null, ended connection), each test first. Every request
field is read through one helper that checks key presence: a field present as
CBOR null is CBOR_UNEXPECTED_TYPE, never an omitted one (a null allowList is
not discovery). A GATT client is marked closed under its queue lock when its
connection ends, and refuses every later enqueue, send, retry and completion;
a failed send cancels the connection only while its client is still the
device's admitted one. Tests: Ctap2RequestValidationTest (a real CBOR null in
each field), FidoGattServerTest (a reconnect during a fragmented reply).
