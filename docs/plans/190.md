# #190 local.pin* error codes

## Objective

The local.pin* handlers answer with the error code the condition deserves:
a wrong PIN is `PIN_INCORRECT`, a PIN that is not set (or a `currentPin` that
is required but missing) is `PIN_REQUIRED`, an unknown `pinType` on verify is
`INVALID_PARAMS` (an absent one still means the User PIN), and every
`PIN_LOCKED` carries `lockoutUntil` and `failedAttempts`.

## Slices

1. Failing tests in `PinOathHandlerErrorsTest` (one commit, red):
   - `pinVerify of the User PIN before it is set returns PIN_REQUIRED`
   - `pinSet of the SO PIN without currentPin while it is set returns PIN_REQUIRED`
   - `pinChange of a PIN that is not set returns PIN_REQUIRED`
   - `pinVerify with an unknown pinType returns INVALID_PARAMS`
   - `pinVerify with no pinType verifies the User PIN`
   - `pinSet pinChange and pinResetLockout PIN_LOCKED carry lockoutUntil and failedAttempts`
   - `a wrong PIN still returns PIN_INCORRECT and counts a failed attempt`

   The not-set and wrong-PIN tests drive a real `PinManager` over a mocked
   `PinSettingsRepository`, so they check what `PinManager` throws as well
   as how the handler maps it.
2. The fix (green):
   - `PinManager.kt`: `PinException` becomes open; `PinIncorrectException`
     (wrong PIN) and `PinRequiredException` (PIN not set, stored hash
     missing, or current SO PIN not supplied) subclass it, so existing
     `catch (e: PinException)` callers still compile.
   - `Handler.kt`: `handlePinVerify/Set/Change/ResetLockout` map
     `PinRequiredException` to `PIN_REQUIRED` and `PinIncorrectException`
     to `PIN_INCORRECT`; verify refuses an unknown `pinType`; one
     `pinLockedError` helper builds every `PIN_LOCKED` with its data.
   - `docs/pin/architecture.md` "Errors and refusals" table matches.

## Out of scope

- PIN UI screens and other `PinException` callers (they keep catching the
  base type).
- Desktop (go-xkms) handling of the codes.
