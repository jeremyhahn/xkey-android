# 338: Post-quantum ML-DSA keys

## Objective

ML-DSA-44, ML-DSA-65 and ML-DSA-87 (FIPS 204) signing keys, each held either
in software (Bouncy Castle, wrapped by a non-exportable Keystore AES-256-GCM
key) or in the Android Keystore where the device makes that parameter set.
They work end to end: `local.generateKey`, `local.sign`, `local.getPublicKey`,
`local.deleteKey`, `local.getCapabilities`, `local.piv*`, and the Key
Management and PIV dialogs. This row builds on key-algorithm-parity (#333).

## Slices, in order

1. Tests first. `PqcSoftwareKeyStoreTest` (SPKI OID and size per set, a
   signature that verifies, no PKCS#8 bytes on disk, a record moved to
   another alias is refused, delete once), `PqcKeysTest` (names, spellings,
   COSE ids), `LocalGenerateKeyMlDsaHandlerTest` (backing choice,
   FEATURE_UNAVAILABLE, INVALID_PARAMS, INVALID_ALGORITHM, sign, export
   formats, delete, capabilities), and the ML-DSA fixture swaps in the PIV
   and capability tests.
2. `PqcKeys.kt` (the parameter sets, `PqcBacking`, the hardware backend
   contract and `PqcHardware`) and `PqcSoftwareKeyStore.kt`.
3. KeystoreManager choke points: generate with a backing, existence, public
   key, security level, delete with audit, `signApprovedMlDsa`.
4. The wire: COSE -48/-49/-50, `keyBacking`, the handler paths and
   `hardwareAlgorithms` in `local.getCapabilities`.
5. PIV slot keys: `PivAlgorithm.ML_DSA_44/65/87` with no SP 800-78 id,
   generate, sign, export and delete for either backing.
6. Dialogs: ML-DSA in Key Management and PIV with a storage choice that
   offers hardware only for the sets `PqcHardware.supported()` reports.
7. Docs: SPEC row, ROADMAP, `docs/pqc-keys/architecture.md`, table rows.

The Android Keystore backend (`KeystorePqcBackend.kt`, registered in
`XKeyApplication`) is a parallel branch merged into this one before the PR
is ready; until then no hardware option shows and `keyBacking: "hardware"`
is FEATURE_UNAVAILABLE.

## Out of scope

- ML-KEM: no app path decapsulates (`local.decrypt` is RSA-OAEP,
  `local.ecdh` is ECDH, `.xkeyenc` is ECIES) and a one-sided wire method is a
  defect. Follow-up row: a hybrid ML-KEM-768 recipient in `.xkeyenc` and a
  decapsulate method designed with the desktop.
- File and media signing with ML-DSA (`signWithAlgorithm` refuses it).
- The software Ed25519 keys that signApproved, generalKeyExists and
  deleteGeneralKey do not reach.

## Open questions

- The desktop must learn the ML-DSA names and `keyBacking` before it sends
  them; the phone change is additive.
- Bouncy Castle 1.87 keeps the lightweight ML-DSA classes in
  `org.bouncycastle.crypto.{generators,params,signers,util}`, not
  `org.bouncycastle.pqc.crypto.mldsa`; the store uses those, so no JCA
  provider and no R8 keep rule is needed.
