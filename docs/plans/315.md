# #315: passkey authentication never reaches the biometric prompt

## Objective

Some devices (seen on Android 16) accept `Signature.initSign` for an
auth-bound key and refuse only at `sign()`, with a `SignatureException`
wrapping `android.security.KeyStoreException` "Key user not authenticated"
(public error code 2, `ERROR_USER_AUTHENTICATION_REQUIRED`).
`KeystoreManager.sign` falls back to the BiometricPrompt + CryptoObject path
only on `UserNotAuthenticatedException` from `initSign`, so the refusal at
`sign()` becomes a `SigningException` and no prompt ever shows.

Fix the class at one choke point in `KeystoreManager`: a private helper that
recognises "user authentication required" in both shapes
(`UserNotAuthenticatedException`, or a cause chain holding a Keystore
`KeyStoreException` whose numeric error code is
`ERROR_USER_AUTHENTICATION_REQUIRED`, API 33+ only).

## Slices

1. Tests first (`KeystoreManagerUserAuthTest`), failing on main:
   - `sign()` reaches the prompt when the silent `sign()` fails with the
     KeyStoreException shape, and when `initSign` fails with a
     `ProviderException` of that shape; the prompt signs with a fresh
     `Signature`;
   - `sign()` still prompts on `UserNotAuthenticatedException`;
   - `sign()` raises `SigningException` for any other Keystore error;
   - `signWithoutBiometric`, `signWithAlgorithm` and `symmetricEncrypt`
     raise `BiometricRequiredException` on the KeyStoreException shape.
2. Fix: the helper; `sign()` prompts on either shape at any silent step;
   every silent site that caught only `UserNotAuthenticatedException`
   (`signWithoutBiometric`, `signWithAlgorithm`, `signApproved`,
   `rsaDecryptWithAlgorithm`, `symmetricEncrypt`, `symmetricDecrypt`,
   `performECDH`) maps both shapes to `BiometricRequiredException`.
   The SDK level is a constructor parameter defaulting to
   `Build.VERSION.SDK_INT`, so JVM tests can stand in an API 33+ device.

3. Review round: the prompt fallback chooses its flow by key kind in one
   helper, `signWithPrompt`. A time-window key (validity > 0 s, from its
   KeyInfo) authenticates first without a CryptoObject, then initSign,
   update, sign. A per-operation key keeps initSign + CryptoObject. If
   initSign refuses for want of authentication, the time-window flow runs.
   Test first: both Signatures refuse initSign until authentication.

## Out of scope

No wire, schema or SPEC change; no change to key generation parameters
or to `BiometricHelper`.
