# Plan: #191 file operation staging files

## Objective

`FileOperationActivity` stages plaintext and ciphertext in `cacheDir` under
fixed or display-name-derived names (`xkey_sign_temp_<name>`,
`xkey_enc_temp`, `xkey_dec_temp`). A shared file's display name can carry
`../`, two operations share one path, and a failed write, failed copy or
cancelled save leaves the file behind. Stage every file under a generated
name in one cache subdirectory, delete it on every failure path and on a
cancelled save, sweep leftovers at start, and release owned files when the
activity finishes.

## Slices

1. Tests first (`FileOperationStagingTest`, JVM, temp directory as cache):
   - `staged name never contains the display name`
   - `a traversal display name stages inside the staging directory`
   - `staged file is deleted when the write step throws`
   - `staged file is deleted when the save is cancelled`
   - `staged file is deleted when the copy to the target throws`
   - `two staged files have different paths`
   - `startup sweep deletes leftovers only inside the staging directory`
   Committed red against a stub `FileOperationStaging`.
2. Fix: `ui/FileOperationStaging.kt`, plain Kotlin over a `File` cache dir:
   - `stage(prefix, write)`: `File.createTempFile` in
     `cacheDir/file-ops-staging/`, runs `write`, deletes on throw.
   - `deliver(file, copy)`: runs `copy`, deletes the file whether it throws
     or not.
   - `cancel(file)`, `releaseAll()`, `sweep()` (only the staging directory's
     own entries).
   `FileOperationActivity` stages sign/encrypt/decrypt through it, deletes
   the staged file when `CreateDocument` returns null, sweeps in `onCreate`
   and releases owned files in `onDestroy` when `isFinishing`.
3. Docs: `docs/file-operations/architecture.md` says where staging files
   live and when they go.

## r2: staging owned per instance, writers fenced at teardown

Review of r1 found the startup sweep deleting a live activity's staged
output (any app can open the exported activity), and teardown racing a
writer blocked in `openInputStream` that then recreates the plaintext.

1. Tests first: `a second instance's sweep keeps the first instance's
   staged output`, `a writer blocked in input at teardown leaves no staged
   file`, red against a `shutdown()` stub.
2. Fix: every instance is a session; its files are named
   `stage-<session>-*` and the session is registered live until
   `shutdown()`. `sweep()` deletes only entries of no live session.
   `shutdown()` closes the instance: `create` is refused after it, owned
   files go, and a write step still running deletes its file when it
   returns and ends cancelled. The activity sweeps only after intent
   validation and shuts its staging down in every `onDestroy`.

## r3: staged input opened before the destination

Review of r2 found JPEG signing opening the original for writing before
the staged input: a teardown while the provider blocks in
`openOutputStream` deleted the staged replacement, and the truncating open
then left the original empty.

1. Test first: `a destination open paused across teardown still completes
   from the staged file`, red against `deliverTo` in the old order.
2. Fix: `FileOperationStaging.deliverTo(file, openTarget)` opens and holds
   the staged input, refused after `shutdown()` (so the destination is
   never opened), then opens the destination and copies. `shutdown()`
   leaves a held file to its writer, which deletes it when the copy ends.
   The activity delivers sign, encrypt and decrypt through it.

## r4: staged output released when the picker handoff fails

Review of r3 found a decrypt or encrypt failing after `stage` returned
(`keyDao.recordUsage`, the audit write, `CreateDocument.launch`) keeping
its staged file until teardown, a new one per retry; and no test of
`deliverTo`'s failure cleanup.

1. Tests first: `deliverTo` when the destination open throws, opens as
   null, or the write fails (exception propagates, destination closed,
   staged file deleted); decrypt and encrypt handoffs whose prepare step
   or picker launch throws, three times over, leave no file and nothing
   pending. Red against stubs of the handoff helpers.
2. Fix: `stageForSave(staging, name, write, prepare, handOff)` releases the
   staged file when `prepare` or `handOff` throws; `PendingStagedSave`
   holds the file a picker is open for and, when the launch throws,
   releases it and clears the reference. Decrypt and encrypt hand off
   through both.

## Out of scope

- Encrypting staged files at rest; streaming without a staging file.
- Behaviour of the verify path (no staging file).
- Process death while a picker is open: the next start's sweep covers it.

## r5: the cancellation test drives the save-cancellation path

Review of r4 found the cancellation test calling `staging.release` itself:
it passed with the launchers' cancel handlers removed or `cancel()` not
releasing.

1. Tests first: a pending handoff then `cancel()` deletes the file and
   clears `pending.file`; a null picker result through
   `PendingStagedSave.onResult`, after a decrypt-shaped and an
   encrypt-shaped handoff, deletes the file, clears the reference and never
   saves; a destination goes to the save and keeps the file pending. Red
   against an `onResult` stub without its cancel branch.
2. Fix: `onResult(result, save)` saves a destination and cancels on null;
   the encrypt and decrypt `CreateDocument` launchers are exactly
   `pending.onResult(uri, ::save…ToUri)`, so the tests cover their
   callbacks (the unit suite has no Robolectric to dispatch a result).
