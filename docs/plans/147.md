# Plan: audit log retention tests and architecture page (#147)

## Objective

Pin the audit log retention behaviour with tests on a real Room database,
and bring `docs/audit-log/architecture.md` in line with the code.

## Slices, in order

1. **Retention constants visible to tests.** `AuditLogger.DEFAULT_RETENTION_MS`
   (90 days) and `MAX_ENTRIES` (10,000) go from `private` to `internal`
   with `@VisibleForTesting`. No other change to `AuditLogger`.
   Test: `AuditRetentionConstantsTest` (JVM, `app/src/test`) checks the two
   values, so the page and the code cannot drift apart unnoticed.
2. **DAO retention tests.** `AuditRetentionTest` (instrumented,
   `app/src/androidTest`, in-memory `XKeyDatabase`, the project's only Room
   test setup; there is no JVM Room or Robolectric setup):
   - `deleteOlderThan` deletes only rows strictly before the cutoff and
     returns that count;
   - `deleteExceedingCount(n)` keeps the newest n by timestamp, keeps exactly
     n when timestamps tie at the boundary, and returns the count deleted;
   - the retention policy: `deleteOlderThan(now - DEFAULT_RETENTION_MS)` then
     `deleteExceedingCount(MAX_ENTRIES)`, as `applyRetentionPolicy` runs them.
   Each test must fail with its query inverted (`<` to `>=`, `DESC` to `ASC`);
   the inversion is local only and never committed.
3. **Architecture page.** Retention limits and when the policy runs
   (`AuditLogger.initialize`, once per process), the audit screen's own
   30-day purge, the schema version from `XKeyDatabase.kt`, and
   "Last verified: 2026-11-12".

A defect a test exposes gets the failing test commit first, then the fix.

## Out of scope

- Restructuring `AuditLogger` or making the retention period configurable.
- The migration table for other entities; this page covers `audit_logs`.
- No go-xkms change, no SPEC wording change.
